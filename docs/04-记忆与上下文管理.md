# 第 04 章 · 记忆与上下文管理：跟上下文窗口抢空间

> 上一章你给模型装上了"手"，但它每动一次，历史就多几行。这一章解决的是：**那个能装下的空间是有限的，装不下怎么办。**
> 本章你需要记住的就一件事：**模型每次调用能"看见"的输入有硬上限（上下文窗口），Agent 的所有"记忆"技巧，本质都是在用有限窗口装下完成任务所需的最关键信息。**

---

## 04.1 上下文窗口和 token：为什么会爆

先讲两个词，后面全靠它们。

**token（词元）** 是模型切分文本的最小单位。它不等于"一个字"：英文大约 4 个字符 ≈ 1 token，中文大约 1 个字 ≈ 1 token，标点、数字、空格都占 token。为什么有这种差异？因为模型的词表（vocabulary）是按训练语料的出现频率切的——英文里常见词（如 "the"、"ing"）被整个编码成 1 个 token，中文则是按字切得更多。

**上下文窗口（context window）** 是模型一次调用能"看见"的最大 token 数，是一个硬上限。你发给模型的 `system + 历史消息 + 工具结果` 全部要挤进这个窗口，超了就被拒绝或截断。不同模型的窗口大小不同，从几 k 到几十万甚至上百万 token 都有，但**机制完全一样：窗口是有限的，输入超了就会出问题**。

为什么会"爆"？因为 Agent 是个**循环**。每循环一轮，`messages` 数组就多两条（assistant 的 tool_call + tool 的结果），历史越长，下一轮要发的输入就越大，直到撞上窗口上限。看个直观的例子（`examples/04-记忆管理.mjs` 里的一段订机票对话，共 27 条消息）：

```js
// 教学用粗略估算：中文 1 字 ≈ 1 token，其余约 4 字符 ≈ 1 token
function estimateTokens(text) {
  const cjk = (text.match(/[\u3000-\u303f\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff\uff00-\uffef]/g) || []).length;
  const other = text.length - cjk;
  return Math.ceil(cjk + other / 4);
}

function totalTokens(messages) {
  return messages.reduce((sum, m) => sum + estimateTokens(m.role + ': ' + (m.content ?? '')), 0);
}

// 27 条对话消息，全量塞进窗口
const messages = buildLongConversation();
console.log(`共 ${messages.length} 条消息，估算 ${totalTokens(messages)} token`);
```

```text
共 27 条消息，估算 600 token
```

假设窗口是 512 token（教学值），这 600 token 就**爆了**——超出 88 token。真实的后果有两种：要么 API 直接拒绝你的请求（OpenAI 会返回 `context_length_exceeded` 错误，具体文案以官方文档为准），要么框架/中间层悄悄把最老的消息截掉，模型"悄悄失忆"。

**注意这个估算是"量级"不是"精确"**。真实 token 数要用模型官方的 tokenizer（如 OpenAI 的 tiktoken）逐 token 切分才能得到，你手写的 `estimateTokens` 只能用来**判断量级、预估成本**，不能拿来做"正好卡在窗口边缘"的精确裁剪。

> 一句话记住它：token 是模型切文本的最小单位（中文约 1 字 1 token），上下文窗口是模型一次能看见的硬上限；Agent 循环会让输入越滚越大，迟早撞墙，所以"省空间"是 Agent 工程的第一要务。

## 04.2 记忆的三个层次：短期、长期、工作

**结论先说：Agent 的记忆不是一个东西，而是三个存放位置不同、生命周期不同的东西。搞混它们，是新手设计 Agent 最常犯的错误。**

| 层次 | 是什么 | 存放位置 | 生命周期 | 举例 |
|---|---|---|---|---|
| **短期记忆** | 当前会话的 `messages` 数组 | 内存 | 一次会话内 | 你前几轮说过的话、工具调用的历史 |
| **长期记忆** | 跨会话、需要持久化的知识 | 数据库 / 向量库 | 永久（直到删除） | 用户偏好、历史订单、知识库文档 |
| **工作记忆** | 任务进行中"正在用"的关键信息 | 短期记忆里的一条消息 | 单个任务内 | 刚查到的航班号、刚算出的中间结果 |

**短期记忆**就是你前面几章一直在操作的那个 `messages` 数组。它天然受上下文窗口限制——窗口多大，短期记忆的上限就多大。它的特点是"简单、直接、随用随丢"：

```js
const messages = [
  { role: 'system', content: '你是机票助手' },
  { role: 'user', content: '订周五北京到上海的机票' },
  { role: 'assistant', content: '周五有 CA1858，08:00 起飞。' },
];
// 这就是短期记忆：会话内有效，会话结束就没了
```

**长期记忆**解决的是短期记忆解决不了的两件事：**跨会话记住**（用户上次说喜欢靠窗，下次还记得）和**装下海量信息**（几千份文档塞不进窗口）。它要存到外部（数据库、文件、向量库），需要的时候再**检索**回来拼进窗口。这一章只讲概念，具体怎么接向量检索在 09 章实战里展开。

**工作记忆**是最容易被忽视的一层。它是"任务进行中，模型必须牢牢记住、不能丢的关键信息"——比如订票流程里刚查到的航班号、乘客身份证号。它本质上住在短期记忆里（就是某条工具返回的结果），但它的**重要性远高于其它消息**：丢了它，任务就废了。所以后面做压缩时，工作记忆往往是"打死不能删"的那几条。

**为什么这么分三层？** 因为窗口有限，你不能把所有东西都塞进短期记忆。分层的意义在于：**给每条信息贴上"它该住哪、该活多久"的标签**——会话内用的住内存，跨会话用的存数据库，任务关键信息重点保护。没有这个分层意识，你会要么把所有东西全塞窗口（爆掉），要么无脑截断（把关键信息删了）。

> 一句话记住它：短期记忆 = messages 数组（受窗口限制），长期记忆 = 外部存储（解决跨会话和海量），工作记忆 = 任务关键信息（压缩时最不能丢）；分层的本质是给信息标注"住哪、活多久"。

## 04.3 三种省空间策略：全量、滑动窗口、摘要

**结论先说：省空间只有三条路——砍掉（滑动窗口）、压缩（摘要）、外移（检索）。它们各有代价，没有银弹。**

`examples/04-记忆管理.mjs` 里实现了三种策略，直接看对比（27 条消息，窗口 512）：

```text
① 全量塞入（不做任何处理）
  → 条数 27，估算 600 token → 爆了（超出 88 token）

② 滑动窗口（保留 system + 最近 6 条）
  → 条数 7，估算 163 token → 没爆

③ 摘要（前段压成摘要 + 保留最近 6 条）
  → 条数 8，估算 234 token → 没爆
```

**策略一：全量塞入。** 什么都不做，历史一条不落全发。最简单，但窗口迟早爆。它是"默认的错误选项"——你以为自己"记得全"，实际上要么被 API 拒绝，要么被悄悄截断。

**策略二：滑动窗口（sliding window）。** 只保留 `system + 最近 N 条`，更早的直接丢弃：

```js
function strategySlidingWindow(messages, keepLast) {
  const system = messages[0];          // system 永远保留（它是行为约束）
  const tail = messages.slice(-keepLast); // 只留最近 N 条
  return [system, ...tail];
}
```

优点是简单、token 稳定可控。缺点是**丢早期信息**——上面那个订票对话里，乘客的身份证号在第 10 条，滑动窗口保留最近 6 条后，身份证号就没了。如果下一步要出票，模型只能猜。**滑动窗口适合"早期信息不重要、只看最近的"场景**，比如闲聊、实时问答。

**策略三：摘要（summary）。** 不丢信息，而是把早期历史**压缩**成一段摘要：

```js
async function strategySummary(messages, llm, keepLast) {
  const head = messages.slice(0, messages.length - keepLast); // 要压缩的前段
  const tail = messages.slice(-keepLast);                     // 保留的最近 N 条
  const headText = head.map((m) => `${m.role}: ${m.content}`).join('\n');
  const summaryReply = await llm.invoke([{ role: 'user', content: `把这段对话压缩成不超过 60 字的摘要：\n${headText}` }]);
  return [messages[0], { role: 'assistant', content: `[历史摘要] ${summaryReply.text}` }, ...tail];
}
```

摘要的好处是**既省空间又保留关键信息**（示例里摘要把航班号、身份证号、积分抵扣都留住了）。代价有两个：

1. **多一次模型调用**——摘要本身要调一次模型，这一步也要花钱、花时间。
2. **有幻觉和细节丢失风险**——摘要是模型重写的，可能记错数字、漏掉细节。摘要后模型"记得"的是摘要，不是原文，原文一旦丢弃就找不回来了。

所以摘要适合**"早期信息重要、但可以用概率方式概括"**的场景，比如长任务、多轮客服。

**三种策略怎么选？** 记住一句话的判据：**信息越不重要，越可以砍（滑动窗口）；信息越重要，越不能靠猜，要么摘要，要么干脆外移到长期记忆按需检索。** 实战里通常是组合拳：最近 N 条原样保留 + 更早的压缩成摘要 + 超重要的外移到向量库。

> 一句话记住它：省空间就三条路——滑动窗口"砍"（快但丢早期）、摘要"压缩"（省但要多花一次调用且有幻觉风险）、检索"外移"（最稳但要建存储）；选哪条看"早期信息重不重要"。

## 04.4 token 计数与成本估算

**结论先说：先会算 token，再会算钱。成本 = token 数 × 单价，输入和输出是分开计费的，输出通常比输入贵好几倍。**

先讲计费规则：大模型 API 按 token 收费，分**输入 token**（你发过去的，含所有历史消息）和**输出 token**（模型生成的，含工具调用的 arguments）。输出通常比输入贵 3~5 倍，因为生成更耗算力。

成本公式：

```text
单次调用成本 = 输入 token / 1_000_000 × 输入单价 + 输出 token / 1_000_000 × 输出单价
```

（单价一般按"每百万 token 多少美元"标，所以除以 1,000,000。）

写个能跑的成本估算函数，用教学假设价（真实价格以各家官方为准，这里只演示算法）：

```js
// 教学假设价：输入 $0.5/百万 token，输出 $1.5/百万 token
function estimateCost(inputTokens, outputTokens) {
  const inputPrice = 0.5 / 1_000_000;   // 每 token 单价（美元）
  const outputPrice = 1.5 / 1_000_000;
  return inputTokens * inputPrice + outputTokens * outputPrice;
}

// 场景 1：一次简单问答，输入 600 token，输出 100 token
console.log('单次问答成本 = $' + estimateCost(600, 100).toFixed(6));
```

```text
单次问答成本 = $0.000450
```

单次几毛钱，看着便宜。**但 Agent 是循环，成本是累加的**。回顾第 03 章那个工具调用循环：5 轮 = 5 次模型调用，而且每轮输入都在变长（历史越滚越大）。假设一个任务循环 10 次，平均每次输入 2000 token、输出 150 token：

```js
const rounds = 10;
const avgInput = 2000;
const avgOutput = 150;
const totalCost = estimateCost(avgInput, avgOutput) * rounds;
console.log(`一个 10 轮循环的任务成本 = $${totalCost.toFixed(4)}`);
```

```text
一个 10 轮循环的任务成本 = $0.0123
```

一个任务 1 分钱，还是便宜。但如果你把它做成一个服务，每天跑 1 万次，就是 $122.5/天，一个月约 $3675。**这就是为什么"能不用 Agent 就别用"——省的不是代码复杂度，是真金白银。**

估算 token 的实用技巧（`estimateTokens` 已在 04.1 给出）：中文 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token。真要精确到"会不会超窗口"的边界，必须用官方 tokenizer，别拿手写估算去做精确裁剪。

> 一句话记住它：成本 = token × 单价，输入输出分开计费（输出更贵）；Agent 是循环，成本按"轮数 × 每轮 token"累加，所以压缩上下文 = 直接省钱。

## 04.5 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 全量塞历史，不设上限 | 跑几轮就报错或"失忆" | 输入超上下文窗口 | 主动管理窗口：滑动窗口 / 摘要 / 检索 |
| 滑动窗口把 system 也删了 | 模型行为跑偏、乱答 | `slice(-N)` 连 system 一起切掉了 | system 永远单独保留，只裁 user/assistant/tool |
| 摘要把关键信息漏了 | 后续任务失败（如身份证号丢了） | 摘要模型有幻觉、丢细节 | 关键信息走"工作记忆"重点保护，或外移长期记忆 |
| 用估算 token 做精确裁剪 | 偶尔超窗口被拒 | 手写估算只是量级，不是 tokenizer | 边界裁剪用官方 tokenizer（tiktoken 等） |
| 忽略工具结果也占 token | 以为只有对话占空间 | 巨型工具结果（几千行文件）会瞬间吃掉窗口 | 工具结果也计入，必要时截断/摘要后再喂回 |
| 只算输入、不算输出成本 | 预算对不上 | 输出单价通常是输入 3~5 倍 | 输入输出分开估算 |

## 04.6 本章小结

- token 是模型切文本的最小单位，**中文约 1 字 1 token，英文约 4 字符 1 token**。
- 上下文窗口是硬上限，Agent 循环会让输入越滚越大，**迟早撞墙**。
- 记忆分三层：**短期（messages 数组）、长期（外部存储）、工作（任务关键信息）**，本质是给信息标注"住哪、活多久"。
- 省空间三条路：**滑动窗口（砍）、摘要（压缩）、检索（外移）**，各有利弊，按"早期信息重不重要"选。
- 摘要省空间但**多花一次调用 + 有幻觉风险**；滑动窗口快但**丢早期信息**。
- 成本 = token × 单价，**输入输出分开计费（输出更贵）**；压缩上下文 = 直接省钱。

## 04.7 动手练习

1. 一段纯中文 1000 字的文本，用 `estimateTokens` 粗算大概多少 token？一段纯英文 1000 字符呢？

   <details><summary>参考答案</summary>
   中文 1000 字 ≈ 1000 token（1 字 1 token）。英文 1000 字符 ≈ 1000/4 = 250 token。这就是为什么同样字数的中英文，token 数能差 4 倍——所以写中文 Prompt 时"字多"不代表 token 多到哪去，英文缩写反而省。
   </details>

2. 一个订票 Agent 把乘客身份证号放在了第 3 条消息，现在窗口要压缩。用滑动窗口只留最近 6 条，会发生什么？怎么避免？

   <details><summary>参考答案</summary>
   身份证号会被丢弃，下一步出票时模型就"忘"了乘客信息。避免方法：把身份证号这类任务关键信息标记为"工作记忆"，压缩时强制保留；或者干脆外移到长期记忆，需要时再检索回来。
   </details>

3. 为什么说"摘要比滑动窗口更贵"？它贵在哪？

   <details><summary>参考答案</summary>
   摘要多一次模型调用——要把早期历史发给模型生成摘要，这一步本身消耗输入 token（旧历史）+ 输出 token（摘要），都要花钱花时间。滑动窗口是纯本地切片，零成本。所以摘要的"省空间"是拿"多一次调用 + 幻觉风险"换来的。
   </details>

4. 一个工具返回了 8000 字符的日志，直接塞进 `role: 'tool'` 会怎样？怎么处理？

   <details><summary>参考答案</summary>
   8000 字符（中文约 8000 token）可能瞬间吃掉整个窗口，导致后续消息没空间。处理：先判断这段日志是否真的需要全文给模型，如果不需要，就截断/取关键几行/先用一段摘要替代，再把精简后的结果喂回。
   </details>
