# 第 09 章 · 实战：分层 Agent 应用

> 前面八章你学会了大脑、工具、记忆、循环、工程化，但它们是散着的。这一章把它们**装进一个能跑的项目**：一个「智能任务助手」，能查天气、能管待办、能做「如果下雨就帮我加一条带伞」这种多步推理。
> 本章你需要记住的就一件事：**把 Agent 拆成四层——接口层（llm）→ 工具层（tools）→ Agent 核心层（state + agent）→ 应用层（app），依赖方向单向朝下，每一层都能单独替换、单独测试。**

---

## 09.1 先给全景：为什么要分层

先给结论：**一个"一个文件写完所有逻辑"的 Agent，写的时候爽，改的时候哭。分层的目的只有一个——让每一层的"变化"被关在它自己那一层里。** 换模型不动工具，换工具不动循环，改业务不动底层。

你之前每一章的示例，都是一个 `.mjs` 文件从头写到尾。那没问题，因为一章只讲一件事。但实战项目不一样：它会持续加工具、持续换模型、持续改业务。如果你把「调模型」「注册工具」「跑循环」「拼提示词」全塞在一个函数里，任何一处改动都要在几百行里翻。

分层的做法，是把一个 Agent 纵向切成四块，**依赖方向从上到下、单向、不回头**：

```text
┌─────────────────────────────────────────────┐
│  应用层 app.mjs                               │  ← 业务：拼 system prompt、组装各层
│  （唯一知道「这是个任务助手」的地方）              │
└──────────────────┬──────────────────────────┘
                   │ import
┌──────────────────▼──────────────────────────┐
│  Agent 核心层 agent.mjs + state.mjs           │  ← 循环 + 状态 + trace
│  （跑「调模型→执行工具→喂回」的循环）            │
└──────┬─────────────────────────┬─────────────┘
       │ import                 │ import
┌──────▼──────────┐      ┌──────▼──────────────┐
│ 接口层 llm.mjs   │      │ 工具层 tools.mjs     │  ← 可插拔、可替换
│ （模型抽象）      │      │ （注册的工具）        │
└─────────────────┘      └─────────────────────┘
```

四条铁律，你记住就值回票价：

1. **依赖只能朝下，不能朝上，更不能横向。** `app` 可以 import `agent`，`agent` 可以 import `llm`，但 `llm` 永远不能 import `agent`。方向反了，就是"循环依赖"，改一行崩一片。
2. **上层通过"接口"使用下层，不关心下层怎么实现。** `agent` 只知道"有个 `llm.invoke(messages)` 能返回 `{ text }` 或 `{ toolCall }`"，至于它是 mock 还是真实 API，`agent` 一概不管。
3. **每一层都能单独替换。** 换模型 = 只改 `llm.mjs`；加工具 = 只改 `tools.mjs`；改循环逻辑 = 只改 `agent.mjs`。
4. **每一层都能单独测试。** 测试工具不需要模型，测试循环用 mock 模型，测试业务用 mock 循环——这就是第 08 章"可测试"的落地。

完整项目在 `examples/project/`，六个文件：

```text
examples/project/
├── llm.mjs        接口层：LLM 抽象（默认走 ../llm-mock.mjs）
├── tools.mjs      工具层：get_weather / add_todo / list_todos
├── state.mjs      Agent 核心层：状态（可序列化、可恢复）
├── agent.mjs      Agent 核心层：循环 + 工具分发 + trace
├── app.mjs        应用层：智能任务助手（组装 + 演示入口）
└── self-test.mjs  端到端自测（node:test，6 个用例、29 个断言）
```

先整体跑一遍，感受一下它到底做了啥。这个例子是「北京今天天气怎么样？如果下雨，帮我在待办里加一条出门带伞」——模型需要**先查天气、再判断下雨、再调加待办的工具、最后总结**，四步缺一不可：

```bash
node examples/project/app.mjs
```

```text
========== 智能任务助手运行结果 ==========
最终回答：北京今天小雨，18℃，我已经帮你把「出门带伞」加到待办清单了。
步数：3，模型调用次数：3

待办清单：
  1. 出门带伞

trace：
  [step=1 kind=llm]
  [step=1 kind=tool] tool=get_weather ok=true
  [step=2 kind=llm]
  [step=2 kind=tool] tool=add_todo ok=true
  [step=3 kind=llm]
  [step=3 kind=finish] text=北京今天小雨，18℃，我已经帮你把「出门带伞」加到待办清单了。
```

注意那个 trace：`get_weather` → `add_todo` → `finish`，正好对应模型的三步决策。这就是一个完整的多步推理闭环。下面一节一节拆开看每一层怎么写、为什么这么写。

> 一句话记住它：分层 = 把变化关进对应的层，依赖方向单向朝下；换模型、加工具、改业务，都只动它自己那一层。

## 09.2 接口层：LLM 抽象（换模型不改一行循环）

先给结论：**接口层只干一件事——把"调用模型"这个动作抽象成一个固定形状的接口，让上层永远只依赖这个形状，而不是依赖某个具体模型。** 换模型，就换这一层的实现。

先看这个接口的形状。它只有两个方法：

```js
// 本教程约定的 LLM 接口（interface）：
//   {
//     invoke(messages) => Promise<{ text } | { toolCall: { name, args } }>
//     getCallCount()  => number   // 统计调用了多少次模型（计费用）
//   }
```

`invoke` 的入参是消息数组，返回值只有两种可能：`{ text }`（模型直接说话）或 `{ toolCall }`（模型想调工具）。这个二选一的形状，就是你从第 03 章一路写下来的那个循环的"燃料入口"。上层 `agent` 只认这个形状。

`examples/project/llm.mjs` 的默认实现走 mock（离线可跑、退出码 0）：

```js
import { createMockLlm } from '../llm-mock.mjs';

// 默认实现：走 mock。传入一个「剧本」数组，模型按顺序返回剧本内容。
// 剧本里每条是 { content: '文字回答' } 或 { toolCall: { name, args } }。
export function createLlm(script = []) {
  return createMockLlm(script);
}
```

**为什么教程坚持用 mock 而不直接写 `fetch`？** 因为模型调用是概率性的、要花钱、要联网，测试和演示都需要"确定性"。mock 按剧本依次返回，每一轮的输入输出都可预测——这恰恰是写测试最需要的。而真实模型的接口形状和 mock **完全一致**，所以换真实模型时，你只需把 `createLlm` 的实现换掉，调用方一行不用改。

真实实现长这样（对照用，离线跑不通，写在注释里）：

```js
// 真实实现：把 mock 换成一次 fetch，接口形状完全一致。
// export function createLlm({ apiKey, model = 'gpt-4o' }) {
//   return {
//     async invoke(messages) {
//       const resp = await fetch('https://api.openai.com/v1/chat/completions', {
//         method: 'POST',
//         headers: {
//           'Content-Type': 'application/json',
//           Authorization: `Bearer ${apiKey}`,
//         },
//         body: JSON.stringify({ model, messages, tools: buildOpenAiTools(tools) }),
//       });
//       const data = await resp.json();
//       const msg = data.choices[0].message;
//       // 关键差异：真实 API 的 tool_calls 是数组、arguments 是 JSON 字符串，
//       // 这里要转换成我们约定的 { toolCall: { name, args } } 形状。
//       if (msg.tool_calls?.length) {
//         const fn = msg.tool_calls[0].function;
//         return { toolCall: { name: fn.name, args: JSON.parse(fn.arguments) } };
//       }
//       return { text: msg.content };
//     },
//   };
// }
```

看那段 `if (msg.tool_calls?.length)`——这就是第 03 章讲的真实 API 和 mock 的唯一差异：真实 API 的 `tool_calls` 是数组、`arguments` 是 JSON 字符串，要 `JSON.parse`。转换完之后，返回的还是 `{ toolCall: { name, args } }`，上层 `agent` 完全无感。

这就是"可插拔"的全部秘密：**变化的（模型）被隔离在一个薄薄的接口层里，稳定的（循环）在上层。** 你后面看到的所有测试，都是靠给 `createLlm` 传不同剧本、模拟不同模型行为来做的。

> 一句话记住它：接口层把"调用模型"收敛成 `invoke(messages)` 一个形状，上层只认形状不认实现；换模型 = 换这一层的实现，循环一行不动。

## 09.3 工具层：注册的工具（schema + 校验 + 执行）

先给结论：**工具层把"模型能调用的工具"集中注册，每个工具带四样东西——`description`（何时用）、`parameters`（怎么用）、`validate`（运行时校验）、`execute`（真正干活）。** 模型对你的工具一无所知，它唯一的认知来源就是 `description` 和 `parameters`；而真正干活、真正读写业务状态的，永远是 `execute`，模型碰不到。

`examples/project/tools.mjs` 注册了三个工具。看其中一个完整的：

```js
export function createTools(store) {
  return {
    get_weather: {
      description: '查询指定城市的实时天气，返回温度与天气状况。city 用中文城市名，例如「北京」。',
      parameters: {
        type: 'object',
        properties: {
          city: { type: 'string', description: '中文城市名，例如「北京」' },
        },
        required: ['city'],
      },
      // 运行时校验：模型给的参数是概率采样，可能是数字、空串、对象。
      validate(args) {
        if (typeof args?.city !== 'string' || args.city.trim() === '') {
          return { ok: false, error: `city 必须是中文城市名字符串，但收到 ${typeof args?.city}` };
        }
        return { ok: true };
      },
      execute(args) {
        const city = args.city.trim();
        if (city === '北京') return `${city}：小雨，18℃`;
        if (city === '深圳') return `${city}：晴，28℃`;
        return `${city}：多云，22℃`;
      },
    },
    // ... add_todo、list_todos 结构相同
  };
}
```

拆开讲三个设计决策：

**决策一：为什么 `description` 要写那么细？** 因为模型对工具的"理解"100% 来自文字。你写"查询指定城市的实时天气，city 用中文城市名"，模型才知道该传"北京"而不是"Beijing"或经纬度。写"返回温度与天气状况"，模型才知道这个结果能用来判断"下没下雨"。工具描述的模糊度 = 模型的决策出错率，这条在第 03 章就讲过，现在落到实战里。

**决策二：为什么 `validate` 和 `execute` 要分开？** 因为模型参数不可信。`execute` 里写了 `args.city.trim()`，如果模型传了个数字 `123`，`123.trim` 不是函数，直接炸。你可以亲手试：

```bash
node --input-type=module -e "
import { createTools } from './examples/project/tools.mjs';
const tools = createTools({ todos: [] });
tools.get_weather.execute({ city: 123 });
"
```

```text
TypeError: args.city.trim is not a function
```

所以 `validate` 就是"执行前的安检门"：先把非法参数拦在 `execute` 外面，报一个**带错误名、能喂回给模型**的具体错误（第 03 章），而不是让程序崩在 `trim` 上。两层各管一段：`validate` 管"参数形状对不对"，`execute` 管"活儿怎么干"。

**决策三：工具怎么读写业务状态？——通过 `store` 注入，而不是自己造全局变量。** 看 `add_todo`：

```js
add_todo: {
  description: '往待办清单里添加一条事项。content 是要做的事，例如「出门带伞」。',
  parameters: {
    type: 'object',
    properties: {
      content: { type: 'string', description: '待办内容，例如「出门带伞」' },
    },
    required: ['content'],
  },
  validate(args) {
    if (typeof args?.content !== 'string' || args.content.trim() === '') {
      return { ok: false, error: `content 必须是非空字符串，但收到 ${typeof args?.content}` };
    }
    return { ok: true };
  },
  execute(args) {
    // 注意：这里在「读写业务状态」。store.todos 就是 AgentState 里的 todos，
    // 是同一个数组引用，所以加进去的待办会被序列化保存下来。
    const content = args.content.trim();
    const id = store.todos.length + 1;
    store.todos.push({ id, content, done: false });
    return `已添加待办「${content}」（当前共 ${store.todos.length} 条）`;
  },
},
```

`createTools(store)` 接收一个 `store`（就是 `{ todos }`），工具通过闭包访问它。**为什么不让工具自己 `import` 一个全局的 `todos` 数组？** 因为全局状态无法序列化、无法测试、多个 agent 实例会互相污染。注入 `store` 后，每个 agent 实例有自己的 `store`，测试时可以传一个干净的 `{ todos: [] }`，互不干扰。下一节你会看到，这个 `store.todos` 和 `AgentState` 里的 `todos` 是**同一个数组引用**——工具加进去的待办，天然被状态序列化收走。

> 一句话记住它：工具 = description（何时用）+ parameters（怎么用）+ validate（参数安检）+ execute（真正干活）；模型只"看得见"前两个，"干活的"永远是后两个，业务状态通过 store 注入而非全局变量。

## 09.4 Agent 核心层：循环、状态、trace

先给结论：**Agent 核心层是整个项目的心脏，它只负责一件事——把「调模型 → 判断输出 → 执行工具 → 把结果喂回」这个循环跑起来，并把中间状态收进一个可序列化的"值"、把每一步记进 trace。** 它不关心模型是谁、工具是什么，这两样都从参数注入。

这一层拆成两个文件：`state.mjs` 管状态，`agent.mjs` 管循环。

### 状态：一个可序列化的"值"

`examples/project/state.mjs` 里的 `AgentState`，和你第 08 章看到的是同一个思路，多了一个业务字段 `todos`：

```js
export class AgentState {
  constructor({ messages = [], todos = [], maxIterations = 5 } = {}) {
    this.messages = messages;     // 对话历史：{ role, content } 数组
    this.todos = todos;           // 业务状态：待办事项数组
    this.steps = 0;               // 已走的步数
    this.finished = false;        // 是否已产出最终回答
    this.maxIterations = maxIterations; // 兜底：最多循环多少步
  }

  // 序列化：状态 → 字符串，可以写文件、存数据库
  serialize() {
    return JSON.stringify({
      messages: this.messages,
      todos: this.todos,
      steps: this.steps,
      finished: this.finished,
      maxIterations: this.maxIterations,
    });
  }

  // 反序列化：字符串 → 状态，崩溃后从这里续跑
  static deserialize(json) {
    const data = JSON.parse(json);
    const s = new AgentState({
      messages: data.messages,
      todos: data.todos,
      maxIterations: data.maxIterations,
    });
    s.steps = data.steps;
    s.finished = data.finished;
    return s;
  }
}
```

`serialize` 用的是 `JSON.stringify`，它有个硬约束：**状态必须是"纯数据"**——只有基本类型、数组、普通对象，不能有函数、不能有循环引用。你往状态里塞一个指向自身的引用，立刻炸：

```bash
node --input-type=module -e "
const a = {}; a.self = a;
JSON.stringify(a);
"
```

```text
TypeError: Converting circular structure to JSON
```

所以 `AgentState` 里只放 `messages`、`todos` 这些纯数据，**不放 `llm`、不放 `tracer`、不放工具函数**——那些是"运行时的东西"，不是"状态"。这跟第 08 章讲的是同一件事，实战里它多了一个作用：**业务数据（todos）也要进状态，才能跟着一起序列化、一起恢复。**

### 循环：每一步都留痕、错误喂回、步数兜底

`examples/project/agent.mjs` 的循环，把第 03 章的"工具调用闭环"和第 08 章的"trace"合成一处：

```js
export function createAgent({ llm, tools, state, tracer }) {
  async function run(userInput) {
    state.messages.push({ role: 'user', content: userInput });

    while (state.steps < state.maxIterations) {
      state.steps += 1;

      const res = await llm.invoke(state.messages);
      tracer.record({ step: state.steps, kind: 'llm', output: res });

      // 模型给了文字 → 最终回答，结束循环
      if (!res.toolCall) {
        state.finished = true;
        tracer.record({ step: state.steps, kind: 'finish', text: res.text });
        return { done: true, text: res.text, steps: state.steps };
      }

      // 模型想调工具 → 真正执行
      const { name, args } = res.toolCall;
      const out = dispatchTool(tools, name, args);
      tracer.record({ step: state.steps, kind: 'tool', name, args, ok: out.ok });

      // 把「模型的工具调用」和「工具的结果（或错误）」都拼回消息
      state.messages.push({ role: 'assistant', content: null, toolCall: { name, args } });
      state.messages.push({ role: 'tool', content: out.ok ? out.result : `[错误] ${out.error}` });
    }

    // 兜底：步数用完了还没结束，强制停止
    tracer.record({ step: state.steps, kind: 'stop', reason: 'maxIterations' });
    return { done: false, reason: 'maxIterations', steps: state.steps };
  }

  return { run };
}
```

三个关键点，你在前几章都学过，这里它们第一次**合体**：

1. **循环 = 调模型 → 判断 → 执行 → 喂回。** `while` 每走一圈，就是一次"想一步、动一步"。模型给文字就结束，给工具调用就执行后把结果 `push` 回消息、继续下一圈。
2. **工具报错不崩，喂回让模型自我修正。** `dispatchTool` 里 `try/catch`，把 `错误名: 错误信息` 塞进 `role: 'tool'` 喂回。模型看到错误能自己改参数重试——第 03 章的核心机制，在这里落地。
3. **每一步都 `tracer.record`，步数有 `maxIterations` 兜底。** 出 bug 时 trace 告诉你"一路怎么走的"；模型死循环时步数上限强制刹车，账单不会无限滚。

再看 `dispatchTool`，它才是真正"动手"的地方：

```js
function dispatchTool(tools, name, args) {
  const tool = tools[name];
  if (!tool) {
    return { ok: false, error: `未知工具：${name}，可用工具：${Object.keys(tools).join(', ')}` };
  }
  const check = tool.validate(args ?? {});
  if (!check.ok) {
    return { ok: false, error: check.error };
  }
  try {
    return { ok: true, result: tool.execute(args) };
  } catch (err) {
    return { ok: false, error: `${err.name}: ${err.message}` };
  }
}
```

注意它的返回值约定：**永远是 `{ ok: true, result }` 或 `{ ok: false, error }`，绝不 throw。** 未知工具、参数校验失败、执行异常，三种错误都收敛成 `{ ok: false, error }`，喂回给模型。这就是"不可靠的可靠系统"（第 00 章）在代码层面的体现。

`createAgent` 是个**工厂函数**，依赖（llm / tools / state / tracer）全部从参数注入，它自己不 import 任何具体实现。这就是它能被测试的原因：测试时塞一个 mock llm、一个干净的 state、一个假的 tracer，循环逻辑原封不动地跑。

> 一句话记住它：核心层 = 循环 + 状态 + trace；状态是纯数据（能序列化），循环每步留痕、错误喂回、步数兜底，依赖全靠注入所以可测。

## 09.5 应用层：把四层组装成「智能任务助手」

先给结论：**应用层是唯一"知道这是个什么应用"的地方。它干四件事——拼系统提示词、初始化状态、注入依赖、跑 agent。** 前面三层都是"通用零件"，到这一层才被组装成一个具体的"任务助手"。

`examples/project/app.mjs` 的组装函数：

```js
const SYSTEM_PROMPT = [
  '你是一个智能任务助手，能帮用户查天气、管理待办清单。',
  '规则：',
  '1. 先用工具查信息，得到足够信息后再回答，不要凭空编造。',
  '2. 如果用户说「如果下雨就……」，你必须先查天气，再决定是否执行后续动作。',
  '3. 待办清单的操作用 add_todo / list_todos 工具完成。',
  '4. 所有动作做完后，用一句话总结你做了什么。',
].join('\n');

export async function runTaskAssistant({ llm, userInput, initialState } = {}) {
  const state = initialState ?? new AgentState();
  state.messages.push({ role: 'system', content: SYSTEM_PROMPT });

  // 关键的一步：store.todos 和 state.todos 是「同一个数组引用」。
  // 工具往 store.todos 里加待办，等于往 state.todos 里加 —— 序列化时不会丢。
  const store = { todos: state.todos };
  const tools = createTools(store);
  const tracer = createTracer();
  const agent = createAgent({ llm, tools, state, tracer });

  const result = await agent.run(userInput);
  return { result, state, tracer };
}
```

看这四步，正好对应"依赖方向朝下"的组装顺序：

1. **拼 system prompt**：告诉模型它是谁、有哪些能力、什么规则。注意规则 2——「如果下雨就必须先查天气再决定」，这句话把"多步推理"的**业务约束**写进了提示词。没有它，模型可能偷懒直接编一个"今天晴"。
2. **初始化状态**：`new AgentState()`，或者传入一个 `initialState`（测试时、崩溃续跑时用）。
3. **注入依赖**：`store.todos = state.todos` 这一步是关键——它让工具的 `store.todos` 和状态的 `state.todos` 是**同一个数组引用**。工具加待办，状态立刻可见，序列化时不丢。
4. **跑 agent**：`agent.run(userInput)` 返回 `{ done, text, steps }`。

这个函数**返回三样东西**——`result`（跑完没）、`state`（中间状态，可序列化）、`tracer`（trace，可断言）。为什么要返回它们，而不是只返回一句回答？因为实战里你要**断言**结果对不对（测试）、要**保存**状态（续跑）、要**查看** trace（排错）。只返回一句话，这三件事一件都做不了。

演示入口的剧本，就是那个"查天气→判断下雨→加待办"的三步：

```js
const script = [
  { toolCall: { name: 'get_weather', args: { city: '北京' } } },  // 第 1 步：查天气
  { toolCall: { name: 'add_todo', args: { content: '出门带伞' } } }, // 第 2 步：判断下雨，加待办
  { content: '北京今天小雨，18℃，我已经帮你把「出门带伞」加到待办清单了。' }, // 第 3 步：最终回答
];

const llm = createLlm(script);
const { result, state, tracer } = await runTaskAssistant({
  llm,
  userInput: '北京今天天气怎么样？如果下雨，帮我在待办里加一条「出门带伞」。',
});
```

换真实模型时，`script` 这个数组就不存在了——它变成模型每次 `invoke` 真实的概率输出，`runTaskAssistant` 和 `agent` 的代码一行都不用改。这就是"分层"的最终收益：**业务逻辑稳定，概率的部分被关在接口层。**

> 一句话记住它：应用层是"组装"不是"实现"——拼提示词、初始化状态、注入依赖、跑 agent，并返回 result/state/tracer 供测试、续跑、排错。

## 09.6 端到端自测：怎么测一个分层的 Agent

先给结论：**分层最大的隐藏收益，是每一层都能被单独测试，而且测试锚点精确。** 你测工具不需要模型，测循环用 mock 模型，测业务用 mock 循环。整套测试零第三方依赖，用 Node 内置的 `node:test`。

`examples/project/self-test.mjs` 有 6 个用例、29 个断言。它们的组织顺序，正好是从底层往顶层：

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { AgentState } from './state.mjs';
import { createTools } from './tools.mjs';
import { createAgent, createTracer } from './agent.mjs';
import { createLlm } from './llm.mjs';
import { runTaskAssistant } from './app.mjs';
```

先看两个代表性的用例，体会"测结构、不测措辞"（第 08 章）：

**用例一：测完整多步推理（这是端到端测试，串起全部四层）。**

```js
test('完整多步推理：查天气后按条件加待办', async () => {
  const llm = createLlm([
    { toolCall: { name: 'get_weather', args: { city: '北京' } } },
    { toolCall: { name: 'add_todo', args: { content: '出门带伞' } } },
    { content: '北京今天小雨，已帮你把「出门带伞」加入待办。' },
  ]);

  const { result, state, tracer } = await runTaskAssistant({
    llm,
    userInput: '北京今天天气怎么样？如果下雨，帮我在待办里加一条「出门带伞」。',
  });

  assert.equal(result.done, true);                 // 正常结束
  assert.equal(result.steps, 3);                   // 恰好 3 步
  assert.equal(llm.getCallCount(), 3);             // 3 次模型调用 = 3 步
  assert.equal(state.todos.length, 1);             // 待办加进去了
  assert.equal(state.todos[0].content, '出门带伞'); // 内容正确
  assert.equal(state.finished, true);              // 状态标记已结束

  // 结构断言：trace 里恰好有一次 get_weather 和一次 add_todo
  const toolNames = tracer.list().filter((r) => r.kind === 'tool').map((r) => r.name);
  assert.deepEqual(toolNames, ['get_weather', 'add_todo']);
});
```

注意最后那个断言：它不检查模型"说了什么话"，只检查"**调用了哪两个工具、顺序对不对**"。这是概率系统测试的核心心法——锚点放在结构和行为上，不放在措辞上。

**用例二：测死循环兜底（边界测试）。**

```js
test('死循环会被最大步数兜底', async () => {
  const llm = createLlm(
    Array.from({ length: 100 }, () => ({ toolCall: { name: 'get_weather', args: { city: '北京' } } }))
  );
  const state = new AgentState({ maxIterations: 4 });
  const tracer = createTracer();
  const agent = createAgent({ llm, tools: createTools({ todos: state.todos }), state, tracer });

  const result = await agent.run('x');

  assert.equal(result.done, false);             // 没正常结束
  assert.equal(result.reason, 'maxIterations'); // 原因是步数用尽
  assert.equal(result.steps, 4);                // 恰好走了 4 步就停
});
```

给模型塞 100 个"永远想调工具"的剧本，但 `maxIterations = 4`，于是第 4 步就被强制刹车。这个测试的价值在于：**它证明了你的兜底逻辑真的生效**，而不是嘴上说说。

其余四个用例，覆盖另外三层的边界：

| 用例 | 测的层 | 断言什么 |
|---|---|---|
| 状态序列化后能无损恢复（含待办） | 状态层 | `steps`、`todos`、`finished` 能往返 |
| 工具校验会拦住非法参数 | 工具层 | `validate` 拦掉数字、空串 |
| 未知工具返回错误而不是崩溃 | 核心层 | 错误被 `{ ok:false }` 兜住，循环不崩 |
| 工具报错喂回后模型能自我修正 | 核心层 | 第一次 `ok=false`，修正后 `ok=true` |

跑起来：

```bash
node --test examples/project/self-test.mjs
```


> 一句话记住它：分层让测试变得精确——从状态、工具、循环到端到端逐层断言，用 mock LLM 固定剧本，测结构和边界、不测措辞。

## 09.7 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 依赖方向写反 | 改一个文件崩一片 | 上层 import 下层时形成了环（如 llm import 了 agent） | 依赖单向朝下：app → agent → {llm, tools}，永不回头 |
| 状态里塞运行时对象 | `TypeError: Converting circular structure to JSON` | `JSON.stringify` 遇循环引用/函数 | 状态只放纯数据，llm/tracer/工具函数都不进状态 |
| 工具不校验就执行 | `TypeError: args.city.trim is not a function` | 模型传了数字，`trim` 不是数字的方法 | `validate` 先拦非法参数，报带错误名的具体错误 |
| 工具报错就 throw | 整个 agent 崩溃 | 没把错误当可喂回的信息 | `try/catch` 后返回 `{ ok:false, error }`，喂回模型 |
| 忘把工具结果喂回 | 模型反复调同一工具 | 没 push `role:'tool'` 消息 | 执行完工具必 push assistant + tool 两条消息 |
| 业务状态用全局变量 | 测试互相污染、序列化丢数据 | 工具直接 import 全局数组 | 用 `store` 注入，且 `store.todos` 与 `state.todos` 同引用 |
| 循环不设步数上限 | 死循环 + 账单爆掉 | 模型可能反复犯同样的错 | `maxIterations` 兜底，超限返回 `{ done:false, reason:'maxIterations' }` |
| 测试断言措辞 | 测试随机通过/失败 | 模型输出是概率的 | 断言结构（调了哪些工具、几步、兜底），不测具体话术 |

## 09.8 本章小结

- **分层 = 把变化关进对应的层**，四层：接口层（llm）→ 工具层（tools）→ 核心层（state + agent）→ 应用层（app）。
- **依赖方向单向朝下**，永不回头；上层通过接口用下层，不关心实现。
- **接口层**把"调用模型"收敛成 `invoke(messages)` 一个形状，换模型只改这一层。
- **工具层** = description（何时用）+ parameters（怎么用）+ validate（参数安检）+ execute（干活），业务状态用 `store` 注入。
- **核心层** = 循环 + 状态 + trace：状态是纯数据（可序列化），循环每步留痕、错误喂回、步数兜底，依赖全注入所以可测。
- **应用层**是"组装"不是"实现"：拼提示词、初始化状态、注入依赖、跑 agent，并返回 result/state/tracer。
- **自测逐层断言**，用 mock LLM 固定剧本，测结构和边界、不测措辞，退出码 0 才算过。

## 09.9 动手练习

1. `examples/project/state.mjs` 的 `AgentState` 里，如果往 `messages` 里塞一个带循环引用的对象，再调 `serialize()`，会报什么错？为什么？

   <details><summary>参考答案</summary>
   会抛 `TypeError: Converting circular structure to JSON`。因为 `serialize` 底层用的是 `JSON.stringify`，它无法处理循环引用（对象 A 引用了对象 B，B 又引回 A）。这正是"状态必须是纯数据"的原因：状态里只能放基本类型、数组、普通对象，不能放函数、不能放指向自身（或任何运行时对象）的引用。
   </details>

2. 下面这段代码，如果把 `validate` 那行删掉、直接调 `execute`，会怎样？为什么 `validate` 是必须的？

   ```js
   const tools = createTools({ todos: [] });
   tools.get_weather.execute({ city: 123 });   // city 传了数字
   ```

   <details><summary>参考答案</summary>
   会抛 `TypeError: args.city.trim is not a function`，因为 `execute` 里写了 `args.city.trim()`，而 `123` 是数字、没有 `trim` 方法。`validate` 就是"执行前的安检门"，它先把非法参数拦在 `execute` 外面，报一个带错误名、能喂回给模型的具体错误（`city 必须是中文城市名字符串，但收到 number`），让模型能自我修正，而不是让程序崩在 `trim` 上。
   </details>

3. 为什么 `runTaskAssistant` 要把 `store.todos` 和 `state.todos` 设成"同一个数组引用"，而不是各建一个数组、跑完再手动合并？

   <details><summary>参考答案</summary>
   因为工具在 `execute` 里直接 `store.todos.push(...)` 修改待办。如果 `store.todos` 和 `state.todos` 是两个不同的数组，工具加进去的待办就只存在于 `store` 里，`state` 不知道，`serialize()` 序列化时就会把这些待办丢掉。设成同一个引用后，工具一改 `store.todos`，`state.todos` 立刻同步，序列化、续跑、断言都天然正确。
   </details>

4. `examples/project/self-test.mjs` 里"死循环兜底"这个测试，为什么要把剧本设成 100 个重复的 `toolCall`，而不是直接写一个 `while(true)` 让模型一直调工具？

   <details><summary>参考答案</summary>
   因为测试要模拟的是"模型在死循环"这个**真实场景**——模型反复想调同一个工具，而你无法控制模型的输出，只能靠 `maxIterations` 刹车。给 mock 塞 100 个重复的 `toolCall` 剧本，就是模拟"模型永远想调工具"，然后断言循环在第 4 步被 `maxIterations=4` 强制停止、返回 `{ done:false, reason:'maxIterations' }`。直接写 `while(true)` 是测自己的循环代码，不是测 agent 面对"失控模型"时的兜底能力。
   </details>

5. 现在你要给这个任务助手加一个 `delete_todo` 工具（按 id 删除待办），你会改哪些文件？哪些文件一行都不用动？为什么？

   <details><summary>参考答案</summary>
   只需改 `tools.mjs`：往 `createTools` 返回的对象里加一个 `delete_todo`，补上 `description`、`parameters`、`validate`、`execute`。`state.mjs`、`agent.mjs`、`llm.mjs` 一行都不用动——因为循环不知道具体有哪些工具（它只按名字 `dispatchTool`），状态只管存数据，接口层只管模型。这正是分层的收益：加工具只动工具层，其余层无感。
   </details>
