# 第 05 章 · 多步推理与规划

> 上一章你学会了让模型"调工具"，但现实任务往往不是"调一次工具就完事"，而是要
> **先想清楚、再动手、看结果、再想、再动**，反复好几轮。
> 本章你需要记住的就一件事：**复杂任务 = 一个循环，循环里模型反复做「想一步 → 动一步 → 看结果」。**
> 配套代码：`examples/05-多步推理.mjs`（可运行，退出码 0）。

---

## 05.1 为什么模型"一步出不了答案"

先给结论：**模型一次调用只能输出一段文本，"思考"和"回答"被压缩在同一次推理里。**
复杂任务需要多步，是因为**每一步的中间结果，必须作为下一步的输入**，而单次调用给不了你这些中间结果。

回想第 00 章讲过的"模型是无状态的"：每次调用都是独立的一次计算。这意味着，如果任务需要
"先查天气，再根据天气决定要不要查降水概率"，那么：

- 第 1 次调用，模型不知道天气，它只能"猜"，或者输出"我想查天气"。
- 拿到天气后，第 2 次调用，模型才能基于天气继续推理。

这中间"拿到天气 → 再推理"这一步，**必须由你的代码把结果拼回输入**，模型自己做不到。

我们用一个最小例子把这件事说死：一次调用，模型只能给你**一个**结果，中间过程你拿不到。

```js
// 单次调用：模型把"想"和"答"挤在同一次输出里，你只拿到一个最终字符串
function singleCall(model, question) {
  const answer = model(question); // 假设 model 是任意一次 LLM 调用
  return answer; // 你只拿到这个，中间"它想过什么"你完全不知道
}

// 如果一个任务天然需要两步，单次调用就卡住了：
// "查北京天气，如果下雨就提醒带伞" 需要：
//   步骤 A：查天气 → 得到"小雨"
//   步骤 B：基于"小雨"判断是否带伞
// 单次调用既查不了天气（模型不能上网），也看不到步骤 A 的结果。
```

```text
（这一节没有运行结果，因为它讲的是"单次调用"的结构边界，不是某个 API 的用法。
  真正能跑的多步循环在 05.3 和 examples/05-多步推理.mjs 里。）
```

所以问题变成：**怎么把一个需要多步的任务，拆成"模型能处理的多次单步调用"，再用代码串起来。**
这就是本章要解决的全部问题。

> 一句话记住它：模型的单次调用只有"一次输出"，多步任务必须靠你的代码把中间结果反复喂回去。

## 05.2 Chain-of-Thought：先写过程，再给答案

先给结论：**思维链（Chain-of-Thought，简称 CoT）就是"让模型在给最终答案之前，先把推理过程写出来"。**
它不改模型、不改 API 参数，只改 prompt，却能显著提升模型在算术、逻辑、多步推理上的准确率。

这个技巧来自 Google 2022 年的论文《Chain-of-Thought Prompting Elicits Reasoning in Large Language Models》
（Wei 等人，arXiv 2201.11903）。它的核心观察是一句反直觉的话：

> 模型不是"算完再说话"，而是"边说边算"。

模型生成文本是**逐 token 的**：先输出第 1 个字，再基于前文输出第 2 个字，以此类推。
这意味着，**已经输出的 token 会成为后续 token 的"工作记忆"**。

- 如果你让模型"直接给答案"，它就没有"草稿纸"，只能一次性蹦出结果，容易错。
- 如果你让模型"先写过程"，那些过程 token 就成了它自己的草稿纸，后续计算能"站在前面的结果上"。

看一个对比：

```text
【不写过程】请回答：(93 + 7) × 4 等于多少？
模型（容易翻车）：380   ← 一步蹦出来的，错了没人知道

【写过程】请一步步推理，先写算式过程，最后用「答案是：<数字>」结尾。(93 + 7) × 4 等于多少？
模型：
  先算括号里：93 + 7 = 100
  再乘 4：100 × 4 = 400
  答案是：400           ← 过程本身帮它算对了
```

写过程还有个额外好处：**过程让你能"抠出"最终答案，甚至能校验过程**。看代码：

```js
// 模型输出可能是一大段过程，你只需要最后那个答案
function extractAnswer(text) {
  const m = text.match(/答案是[：:]\s*(\d+)/);
  return m ? Number(m[1]) : null;
}

const modelOutput = '先算括号里：93 + 7 = 100。再乘 4：100 × 4 = 400。答案是：400';
console.log(extractAnswer(modelOutput));
```

```text
400
```

**什么时候用 CoT，什么时候别用？** 这是它最容易被滥用的地方：

| 该用（需要中间计算/推理） | 不该用（一步就能答） |
|---|---|
| 多位数算术、数学应用题 | 简单事实问答（"首都是哪"） |
| 多条件判断（"如果 A 且非 B 则 C"） | 翻译、改写、摘要 |
| 需要推导链的推理题 | 情感分类、命名实体识别 |

为什么不该用的场景别强行 CoT？因为 CoT 有代价：**过程会消耗更多 token（更贵更慢），而且过程可能胡说八道**。
在简单任务上，多写过程只会浪费钱。

> 一句话记住它：CoT 的本质是"让模型把过程当草稿纸写出来"，它只对"需要中间计算"的任务有效，且要付出 token 成本。

## 05.3 ReAct：把"想"和"动"接成循环

先给结论：**CoT 只能"想"，不能"查"。ReAct 把推理（Reasoning）和行动（Acting）拼成一个循环，让模型边想边调工具、边看结果边修正。**
这是今天几乎所有 agent loop 的鼻祖。

ReAct 来自 2022 年 10 月的论文《ReAct: Synergizing Reasoning and Acting in Language Models》
（Yao 等人，arXiv 2210.03629，NeurIPS 2023）。作者发现两个孤立方案各有短板：

- **纯 CoT**：只推理不行动，遇到"不知道的事实"（比如实时天气）只能编，产生幻觉。
- **纯行动**：只调工具不推理，容易迷失方向，不知道"下一步该调哪个工具"。

ReAct 把两者拼起来，让模型交替输出两种东西：

```text
Thought: 我现在想什么、下一步要干嘛        ← 推理（只存在于模型脑子里的独白）
Action: 调用哪个工具 + 参数                ← 行动（由你的代码真正执行）
Observation: 工具返回的结果                ← 观察（代码执行后喂回给模型）
（重复 Thought → Action → Observation，直到够了）
Final Answer: 最终回答                     ← 结束信号
```

关键点在于**分工**：模型只负责输出 `Thought` 和 `Action` 的**文本**，真正执行工具、拿到 `Observation` 的是**你的代码**。
这和第 00 章"模型只表达意愿、代码负责执行"完全一致。

下面是完整循环的核心代码（完整版在 `examples/05-多步推理.mjs`）：

```js
import { createMockLlm } from './llm-mock.mjs';

const tools = {
  get_weather({ city }) { return `${city}：小雨，22℃`; },
  get_rain_probability({ city }) { return `${city} 未来 3 小时降水概率 80%`; },
};

// 解析模型吐出的 ReAct 文本
function parseReAct(text) {
  const thought = text.match(/Thought:\s*([\s\S]*?)(?=\n(?:Action|Final Answer):|$)/)?.[1]?.trim() ?? '';
  const finalMatch = text.match(/Final Answer:\s*([\s\S]+)/);
  if (finalMatch) return { type: 'final', thought, answer: finalMatch[1].trim() };
  const actionMatch = text.match(/Action:\s*([A-Za-z_]\w*)/);
  const inputMatch = text.match(/Action Input:\s*(\{[\s\S]*\})/);
  if (actionMatch) {
    let input = {};
    try { input = inputMatch ? JSON.parse(inputMatch[1]) : {}; } catch { input = {}; }
    return { type: 'action', thought, action: actionMatch[1], input };
  }
  return { type: 'unknown', thought };
}

async function runReAct(question, script) {
  const llm = createMockLlm(script);
  const messages = [
    { role: 'system', content: REACT_PROMPT },
    { role: 'user', content: question },
  ];
  const MAX_STEPS = 5; // 兜底：防死循环

  for (let step = 1; step <= MAX_STEPS; step++) {
    const text = (await llm.invoke(messages)).text ?? '';
    const parsed = parseReAct(text);

    if (parsed.type === 'final') {
      return parsed.answer; // 模型说完了，结束
    }
    if (parsed.type === 'action') {
      const tool = tools[parsed.action];
      const observation = tool ? tool(parsed.input) : `未知工具：${parsed.action}`;
      // 关键：把模型的"发言"和工具的"观察"都拼回消息
      messages.push({ role: 'assistant', content: text });
      messages.push({ role: 'tool', content: `Observation: ${observation}` });
      continue;
    }
    return '[兜底] 模型输出无法解析';
  }
  return '[兜底] 达到最大步数';
}
```

运行 `node examples/05-多步推理.mjs` 的真实输出：

```text
用户问题：北京今天天气怎么样？下雨的话我要不要带伞？

--- 第 1 步 ---
[模型思考] 用户想知道北京的天气情况，我需要先调用天气工具获取数据。
[调用工具] get_weather({"city":"北京"})
[观察结果] 北京：小雨，22℃

--- 第 2 步 ---
[模型思考] 天气是小雨，但我还不确定下雨的可能性有多大，再查一下降水概率。
[调用工具] get_rain_probability({"city":"北京"})
[观察结果] 北京 未来 3 小时降水概率 80%

--- 第 3 步 ---
[模型思考] 降水概率 80%，超过 50%，很可能下雨，我应该提醒用户带伞。
[最终答案] 北京今天有小雨，降水概率 80%，出门记得带伞。

✅ 循环结束：共 3 步，调用模型 3 次。
```

注意三件事：

1. **每一轮模型都"看见"了上一轮的结果**（`Observation: 北京：小雨，22℃` 被拼回了消息）。
2. **模型自己决定走几步**——这里走了 3 步，如果模型觉得信息够了，第 1 步就能给 `Final Answer`。
3. **`MAX_STEPS` 是保命符**——模型可能永远觉得"信息不够"，没有这个上限，它会一直烧钱循环下去。

ReAct 和后面第 03 章会讲的 function calling 是什么关系？**ReAct 是一种"纯文本协议"**，任何能吐字的模型都能用；
**function calling 是厂商把"工具调用"做成了结构化的 API 返回**，你不需要自己写正则去抠。两者思想相同，实现层级不同。

> 一句话记住它：ReAct = Thought（想）+ Action（动）+ Observation（看）的循环，模型只负责"想和说"，动手的是你的代码，而 MAX_STEPS 是防死循环的保命符。

## 05.4 任务拆解：把大目标切成子任务

先给结论：**一个复杂目标，模型很难一次做完，你要先让它（或你）把它拆成一个个小任务，再逐个解决。**
拆解的收益是：每个子任务都变小了，模型更容易做对；而且你能**单独追踪每个子任务的状态**。

拆解这件事，两种做法：

1. **让模型拆**：把大目标喂给模型，要求它输出一个 JSON 数组的子任务列表。
2. **你拆（工作流）**：如果流程是固定的，直接用代码写死子任务，不需要模型参与。

第 00 章讲过的判断标准在这里再次生效：**能画成确定流程图的，就别让模型拆，自己写死更稳。**

一个最小演示——把"做攻略"拆成子任务并逐个执行、跟踪状态：

```js
const goal = '帮我做一份北京三日游攻略';

// 让模型拆解出来的子任务（mock：预置结果）
const subtasks = [
  { id: 1, title: '查询北京三日天气', done: false },
  { id: 2, title: '列出必去景点', done: false },
  { id: 3, title: '按天气排行程', done: false },
];

// 逐个执行，跟踪完成状态
for (const t of subtasks) {
  t.done = true; // 这里省略了"真正执行子任务"的细节
  console.log(`[完成] ${t.id}. ${t.title}`);
}
console.log('所有子任务完成，攻略生成完毕');
```

```text
[完成] 1. 查询北京三日天气
[完成] 2. 列出必去景点
[完成] 3. 按天气排行程
所有子任务完成，攻略生成完毕
```

这个例子里每个子任务还是"假执行"（直接标 done）。真实情况下，每个子任务本身可能又是一次模型调用或一次工具调用。
拆解的价值不在于"列表"，而在于：**每个子任务成了独立的、可验证的单元，一个失败不会让整个目标崩掉。**

> 一句话记住它：大目标要拆成小任务，拆完的每个子任务都是独立的、可单独追踪和验证的单元；能写死流程就别让模型拆。

## 05.5 计划-执行-反思（plan-execute-reflect）

先给结论：**这是比"拆完就一口气做完"更稳的三段式——先出计划，再执行，最后反思结果、必要时改计划重来。**
它多出来的"反思"一步，专门解决"计划是错的"这个高频问题。

为什么需要反思？因为**模型第一次做的计划经常是错的**。比如它计划"第一天去长城"，结果查到"第一天暴雨"，
原计划就废了。没有反思环节，它只能带着错误计划硬着头皮做完。

三段式的骨架：

```js
// plan-execute-reflect：计划 → 执行 → 反思 → （改计划）→ 再执行
let plan = ['查天气', '查景点', '排行程'];

for (let round = 1; round <= 3; round++) {
  console.log(`\n=== 第 ${round} 轮 ===`);
  console.log('[计划]', plan.join(' → '));

  // 1. 执行计划里的每一步
  for (const step of plan) {
    console.log(`  [执行] ${step}`);
  }

  // 2. 反思：检查结果是否满足目标（mock：模拟模型反思）
  const reflect = '查到明天有暴雨，露天行程需要调整';
  console.log(`[反思] ${reflect}`);

  // 3. 根据反思决定：改计划重来，还是结束
  if (reflect.includes('暴雨')) {
    plan = ['查室内景点', '重排行程']; // 修改计划
  } else {
    break; // 反思通过，结束
  }
}
```

```text
=== 第 1 轮 ===
[计划] 查天气 → 查景点 → 排行程
  [执行] 查天气
  [执行] 查景点
  [执行] 排行程
[反思] 查到明天有暴雨，露天行程需要调整

=== 第 2 轮 ===
[计划] 查室内景点 → 重排行程
  [执行] 查室内景点
  [执行] 重排行程
[反思] 查到明天有暴雨，露天行程需要调整
```

（为了演示，这里 mock 的"反思"永远返回"有暴雨"，所以会一直循环到 `round` 上限——这恰好暴露了一个真问题：**反思这一步必须有一个"可以结束"的判定条件，否则反思本身也会死循环。**）

反思的本质是什么？是**让模型拿"结果"和"目标"做对比，输出"是否继续、改什么"**。落地时它通常是这样一个函数：

```js
// 反思 = 把「目标 + 计划 + 已执行结果」喂给模型，问它：够了吗？不够改什么？
async function reflect(llm, { goal, plan, results }) {
  const prompt = [
    `目标：${goal}`,
    `已执行计划：${JSON.stringify(plan)}`,
    `执行结果：${JSON.stringify(results)}`,
    '判断：目标达成了吗？如果没有，输出新的计划（JSON 数组）；如果达成，输出 DONE。',
  ].join('\n');
  return (await llm.invoke([{ role: 'user', content: prompt }])).text;
}
```

反思返回 `DONE` 就退出，返回新计划就替换 `plan` 进入下一轮——这就是 plan-execute-reflect 的完整闭环。

> 一句话记住它：计划-执行-反思在"拆解"上多加了"反思"一环，专门修复"第一次计划就是错的"；反思必须有明确的结束条件，否则自己会死循环。

## 05.6 "先想再动"的两种写法：内部独白 vs 显式 plan 字段

先给结论：**让模型"先想再动"，有两种落地方式——把思考过程写进文本（内部独白），或者把计划存成结构化的数据字段（显式 plan）。前者简单但要用正则抠，后者更可控但要求模型输出格式严格。**

这两种写法对应着两代 agent 的进化：早期 ReAct 用"内部独白"（`Thought: ...` 混在文本里），
后来的框架（比如 LangGraph、以及很多生产实现）倾向于"显式 plan 字段"（计划是一个 JSON 对象，直接可读）。

对比代码：

```js
// 写法一：内部独白 —— 思考和动作混在一段文本里
const monologue = 'Thought: 先查天气\nAction: get_weather({"city":"北京"})';
// 代码要用正则把动作从文本里"抠"出来
console.log('独白需正则 =>', /Action: (\w+)/.exec(monologue)[1]);

// 写法二：显式 plan 字段 —— 计划是一个结构化对象，代码直接读
const structured = {
  plan: [
    { step: 1, action: 'get_weather', args: { city: '北京' } },
    { step: 2, action: 'get_attractions', args: { city: '北京' } },
  ],
};
console.log('显式字段直接读 =>', structured.plan[0].args.city);
```

```text
独白需正则 => get_weather
显式字段直接读 => 北京
```

两者的取舍，一句话表格：

| 维度 | 内部独白 | 显式 plan 字段 |
|---|---|---|
| 实现难度 | 低（模型随便写，你正则抠） | 高（要求模型严格输出 JSON，见第 06 章） |
| 可控性 | 差（正则可能抠错、格式乱） | 好（数据结构化，代码直接读） |
| 灵活性 | 高（模型想写啥写啥） | 低（必须符合 schema） |
| 泄漏风险 | 高（思考过程混在文本里，容易被用户看到） | 低（plan 可以单独存，不展示给用户） |
| 适用场景 | 快速原型、单轮工具调用 | 生产环境、多轮规划 |

**一个关键工程决策**：思考过程（`Thought`）要不要展示给用户？很多产品会把模型的"思考"单独存起来，**只把 `Final Answer` 展示给用户**——因为思考过程可能包含不严谨、甚至冒犯性的中间内容。这正是"显式 plan 字段"的一大优势：它能和"给用户看的内容"干净地分离。

> 一句话记住它：内部独白简单但脏（要用正则抠、易泄漏），显式 plan 字段干净但要求模型严格输出 JSON；生产环境倾向显式 plan，把"思考"和"给用户看的答案"分开。

## 05.7 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 循环死循环 | 模型一直调同一个工具，程序跑不完 | 模型不觉得"信息够了"，没有终止条件 | 设 `MAX_STEPS` 上限，超限强制停止 |
| 模型输出格式乱 | `parseReAct` 抠不出 Action | 模型没严格按 `Thought/Action` 格式写 | 用 function calling（第 03 章）或显式 plan 字段，别依赖正则 |
| 忘把 Observation 拼回 | 第 2 步模型"不知道"第 1 步结果 | 只 push 了 assistant 消息，没 push tool 结果 | 每轮把 assistant 发言和 tool 结果都 push 进 messages |
| CoT 到处乱用 | 简单任务也写一堆过程，又贵又慢 | 没区分"需要中间计算"和"一步能答" | 简单任务直接答，复杂任务才 CoT |
| 反思自己死循环 | plan-execute-reflect 永远进不了结束分支 | 反思的结束条件没写或永远不满足 | 反思返回明确的 `DONE`，并有最大轮数兜底 |
| 计划一次做完不重来 | 计划错了也硬着头皮执行到底 | 缺反思环节 | 加 plan-execute-reflect，执行后检查结果 |
| 思考过程直接展示给用户 | 用户看到模型的"内心戏" | 没把 thought 和 answer 分离 | 单独存 plan/thought，只展示 Final Answer |
| 用正则抠 JSON 参数 | `JSON.parse` 参数解析失败 | 模型参数里多了逗号、引号没转义 | 交给健壮解析器（第 06 章），失败给默认值 |

---

## 05.8 本章小结

- 模型**一次调用只有一次输出**，多步任务靠代码把中间结果反复喂回输入。
- **CoT（思维链）**：让模型先把过程写出来，过程 token 就是它的"草稿纸"，只对需要中间计算的任务有效，且要花 token。
- **ReAct**：Thought + Action + Observation 的循环，是 agent loop 的鼻祖；模型只"想和说"，代码才"动手"。
- **MAX_STEPS 是保命符**，防死循环烧钱。
- **任务拆解**：大目标切成小任务，每个子任务独立、可追踪、可验证；能写死流程就别让模型拆。
- **plan-execute-reflect**：计划 → 执行 → 反思 → 改计划，专门修复"第一次计划是错的"。
- **内部独白 vs 显式 plan**：前者简单但脏（正则抠、易泄漏），后者干净但要求严格 JSON 输出；生产环境倾向显式 plan，把思考与答案分离。

## 05.9 动手练习

1. 给下面这个 ReAct 循环加一个"重复调用检测"：如果模型连续两次调用同一个工具，就强制停止并输出警告。
   <details><summary>参考答案</summary>

   ```js
   let lastAction = null;
   let repeatCount = 0;
   // 在循环里，每次拿到 parsed.action 后：
   if (parsed.action === lastAction) {
     repeatCount++;
     if (repeatCount >= 2) {
       console.log('[兜底] 连续重复调用同一工具，强制停止');
       break;
     }
   } else {
     repeatCount = 0;
   }
   lastAction = parsed.action;
   ```
   </details>

2. 为什么 CoT 对"翻译一段话"没用，但对"(93 + 7) × 4"有用？
   <details><summary>参考答案</summary>
   翻译不依赖中间计算，模型"一步蹦出"就行，写过程纯属浪费 token；而多位数算术需要"先算括号、再乘"的中间结果，把过程写出来，前面的结果就成了后面的"草稿纸"，能显著降低出错率。
   </details>

3. 一个 plan-execute-reflect 循环，反思环节永远返回"需要调整计划"，会发生什么？怎么修？
   <details><summary>参考答案</summary>
   会死循环，一直改计划一直执行。修法：给反思设定明确的结束信号（比如返回 `DONE` 就退出），同时加最大轮数兜底，超限强制停止。
   </details>

4. 把 05.3 的 ReAct 循环里的 `messages.push` 那两行删掉，运行会发生什么？为什么？
   <details><summary>参考答案</summary>
   模型从第 2 步起"失忆"——它看不到自己第 1 步的思考和工具的观察结果，只能重复问同一个问题或瞎猜。因为模型无状态，历史全靠代码每次 push 进 messages 拼回来（第 00 章的核心结论）。
   </details>
