## 第一部分：高频面试题（50 题）

### 1. 基础概念与心智模型（8 题）

**Q1: 什么是 AI Agent？和普通 LLM 调用有什么区别？**

**答：** Agent 是"让模型在循环里自主决定流程、调用工具直到完成任务"的系统；普通 LLM 调用只是一次"提问 → 回答"。

- 普通调用：一次 `invoke(messages)`，模型吐一段文字，结束。
- Agent：把这次调用放进循环，模型每轮判断"直接回答"还是"调工具"，调工具就执行、回填、再来一轮。
- 本质区别：**Agent 有"循环 + 工具 + 记忆"三个额外零件**，模型在循环里反复"想一步、动一步"。

**Q2: 为什么说 LLM 是"无状态"的？**

**答：** 模型每次调用都是独立计算，不保存任何跨调用的信息；"记忆"是应用层每次把历史拼回输入。

- 调用一结束，模型就"失忆"，它记得的一切都是你重新喂给它的。
- 所以 Agent 的记忆机制 = 每次调用前把 `messages` 数组完整传进去。
- 工程含义：忘喂了，模型立刻失忆；喂多了，窗口就爆。

**Q3: Agent 的四件套（大脑/记忆/工具/循环）分别是什么？代码里长什么样？**

**答：** 大脑 = 模型接口；记忆 = messages 数组；工具 = 函数表；循环 = for/while + if。

- 大脑：`llm.invoke(messages)`，返回 `{ text }` 或 `{ toolCall }`。
- 记忆：`const messages = [{ role, content }, ...]`，普通数组。
- 工具：`const tools = { get_weather: (args) => '...' }`，键是工具名，值是函数。
- 关键：**四件套里只有"大脑"是别人的，另外三个全是你的代码**——你的水平体现在这三样上。

**Q4: Agent 和 Workflow（工作流）的本质区别？**

**答：** 流程是否由**模型自主决定**。工作流的流程是代码写死的，Agent 的下一步是模型现决定的。

- 工作流：用户输入 → 固定调分类 → 固定调翻译 → 固定输出，走哪条路程序员写死。
- Agent：模型自己判断"该调哪个工具、调几次、下一步干什么"。
- 判据一句话：能画成确定性流程图的，就该用工作流。

**Q5: 什么时候该用 Agent，什么时候该用工作流？**

**答：** 能不用 Agent 就不用。能画成确定性流程的任务用工作流（或纯代码），只有"模型必须自主决定流程"时才上 Agent。

- Agent 的"自主"要付代价：更贵、更慢、更容易跑偏、更难调试。
- 务实顺序：先问能不能不用 Agent → 简单 Agent 自建 → 复杂状态机才上 LangGraph。

**Q6: 模型真的能"调用函数"吗？工具调用到底发生了什么？**

**答：** 不能。模型只输出一段"我想调 X 工具、参数是 Y"的结构化文字，由你的代码解析、执行、再喂回结果。

- 四步：模型输出 tool_call → 代码解析 → 代码执行工具 → 结果以 `role: 'tool'` 喂回。
- 模型只参与"想要什么"和"看懂结果"，真正动手的是你的代码。
- 这是第 00 章"模型负责想，代码负责动"的落地。

**Q7: 为什么说 Agent 是"不可靠的可靠系统"？工程上要为此做什么？**

**答：** 因为模型是概率性的，同样的输入可能得到不同输出；所以 Agent 代码里必须到处是"重试、校验、兜底"。

- `add(1,2)` 跑一百万次都是 3，Agent 总结一篇文章跑一百次有一百种总结。
- 三件套：重试（出错再来）、校验（模型说"完成了"要验证）、兜底（跑偏/死循环强制停或降级人工）。

**Q8: 上下文窗口是什么？为什么它是 Agent 的第一物理约束？**

**答：** 上下文窗口是模型一次调用能"看见"的最大 token 数，是硬上限；Agent 每轮循环都在加消息，迟早撞墙。

- 撞墙后果：API 拒绝（如 `context_length_exceeded`）或框架悄悄截断、模型"悄悄失忆"。
- 所有"记忆、压缩、检索"技巧，本质都是在跟这个窗口抢空间。

### 2. 消息结构与提示词（8 题）

**Q1: 四种消息 role 分别是什么？各自语义？**

**答：** `system`（规则）、`user`（提问）、`assistant`（模型回复）、`tool`（工具结果）。

- `system` 放最前面，写身份 + 规则 + 约束，全程生效。
- `tool` 是代码回填的、紧跟对应 `assistant` 之后，模型自己不能生成它。

**Q2: tool 消息为什么必须由代码回填？位置有什么要求？**

**答：** 因为模型"只说不动手"，它没有执行环境；工具结果必须由代码执行后 push 成 `role: 'tool'`，且紧跟那条"要调工具"的 `assistant`。

- 位置错了，模型会搞混"这个结果回答的是哪个问题"。
- 忘了回填，模型下一轮"看不见"结果，会反复调同一个工具（死循环）。

**Q3: system prompt 应该怎么写？**

**答：** 三段式——身份 + 规则 + 约束，写到"让模型没有第二种解释"。

- 身份：你是谁（消除"这次以什么身份干活"的歧义）。
- 规则：该怎么做（如"问天气先调工具"）。
- 约束：输出成什么样（如"50 字以内、只输出 JSON"）。
- 只写"你是一个助手"是不够的，模型不知道要干嘛。

**Q4: 提示词工程的核心原则有哪些？**

**答：** 三条——指令清晰、给示例（few-shot）、约束输出格式，共同动机是消除歧义、压住随机性。

- 指令清晰：把"要什么、不要什么"写死。
- few-shot：给 1~3 个输入输出示例，比抽象描述有效。
- 约束格式：让输出能被代码消费（如 JSON）。

**Q5: 什么是 few-shot？为什么它比描述更有效？**

**答：** few-shot 是在 prompt 里给几个"输入 → 输出"的示例，让模型照着模仿；因为模型的训练方式就是"看大量输入输出对"学出来的。

- 示例是 prompt 里信息密度最高的部分，一个例子胜过十句描述。
- 代价：示例也占 token，只给 1~3 个最能代表目标的例子。

**Q6: role 拼错（如大写 System）会发生什么？**

**答：** 不报错，静默失效——模型认不出 `System`，你的规则被当成普通对话忽略。

- 比报错更坑，因为它没有报错提示，行为悄悄漂移。
- 真实 API 层会返回 400 拒绝，但 mock 省掉了校验，这类错得自己盯。

**Q7: 上下文里信息的"顺序"有什么讲究？**

**答：** 模型是顺序读消息的：放前面 = 优先级高，越靠后的消息对模型"此刻"影响越大。

- `system` 必须最前（最高优先级）。
- 当前任务放最后（模型要回应它），历史放前面。

**Q8: 为什么提示词要"惜字如金"？**

**答：** 因为每个字都在消耗上下文窗口和 token（钱），多塞一条废话就多花一份钱、多占一份窗口。

- 判断标准：每个字要么在消除歧义、要么在传递必要信息，否则就删。

### 3. 工具调用（9 题）

**Q1: 工具调用的完整四步闭环是什么？**

**答：** ① 模型输出 tool_call → ② 代码解析工具名和参数 → ③ 代码执行工具 → ④ 结果以 `role: 'tool'` 喂回。

- 模型只参与 ① 和 ④，执行（②③）完全在你的代码里。
- 一次工具调用 = 多一次模型调用 = 多花钱。

**Q2: 什么是工具的 schema？description 和 parameters 各管什么？**

**答：** schema 是给模型的"说明书"，`description` 决定"什么时候用我"，`parameters`（JSON Schema）决定"怎么用我"。

- 模型不认识你的工具，它唯一的认知来源就是你写的描述。
- 写清单位、边界、给参数示例，是性价比最高的优化。
- 工具描述的模糊度 = 模型的决策出错率。

**Q3: 为什么模型给的参数不可信？怎么校验？**

**答：** 模型输出是概率采样，参数可能是错类型、缺字段、越界；执行前必须分层校验。

- 校验要分层、报错要具体（带错误名），这样模型才能看懂并修正。
- 校验（validate）和执行（execute）要拆开，纯检查无副作用，测试时不用真执行。

**Q4: 工具执行出错该怎么办？为什么把错误喂回而不是 throw？**

**答：** 不 `throw`，把 `错误名: 错误信息` 塞进 `role: 'tool'` 喂回，让模型自我修正。

- 错误对模型来说是"信息"不是"灾难"，它能读懂自然语言错误并重试/换工具/承认失败。
- 但要配合兜底：最大循环次数 + 连续报错计数，防止死循环烧钱。

**Q5: 真实 OpenAI function calling 和简化 mock 的字段差异？**

**答：** 三处——`toolCall` 变 `tool_calls`（数组）、`args` 变 `function.arguments`（JSON 字符串）、`tool` 消息要带 `tool_call_id` 对应。

- `tool_calls` 是数组，因为模型一次可能想调多个工具。
- `arguments` 是字符串，要 `JSON.parse` 后才是对象。
- `tool_call_id` 对不上，API 返回 400。

**Q6: 为什么 arguments 是字符串而不是对象？**

**答：** 因为模型每次只输出文本，所谓"结构化参数"其实是模型生成的一段 JSON 文本，OpenAI 只是原样塞进 `arguments` 字段。

- 你的代码要 `JSON.parse` 转回对象，还要 try/catch 解析失败（模型可能生成非法 JSON）。

**Q7: 工具调用有什么成本？为什么一次工具调用 = 一次模型调用？**

**答：** 每次工具调用后，都要再把结果喂回模型、让模型"看结果并决定下一步"，这就是一次新的模型调用。

- 循环 5 轮 = 5 次模型调用，成本按轮数累加。
- 这是"能不用 Agent 就别用"的底层原因之一。

**Q8: 怎么防止模型调用不存在的工具？**

**答：** 执行前查白名单：`const fn = tools[name]`，`undefined` 就返回"未知工具"信息喂回，而不是直接调用崩掉。

- 直接 `tools[name](args)` 会报 `TypeError: tools[name] is not a function`。
- 模型会幻觉出工具名，所以白名单校验是必须的。

**Q9: 一次能调多个工具吗？怎么处理？**

**答：** 能，真实 API 的 `tool_calls` 是数组，模型一次可能想调多个工具。

- 处理时要按顺序逐个执行，并把每个结果都用对应 `tool_call_id` 喂回。
- mock 简化成了单个 `toolCall`，但接真实 API 时要意识到它是数组。

### 4. 记忆与上下文管理（8 题）

**Q1: token 是什么？中英文 token 数差异？**

**答：** token 是模型切分文本的最小单位；中文约 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token。

- 差异来自词表：英文常见词整个编码成 1 token，中文按字切得更多。
- 所以同样字数，中英文 token 数能差 4 倍。

**Q2: 上下文窗口为什么会爆？**

**答：** 因为 Agent 是循环，每轮都在往 `messages` 里加消息（assistant 的 tool_call + tool 的结果），历史越滚越大，直到撞上窗口硬上限。

- 巨型工具结果（几千行文件）会瞬间吃掉窗口。
- 后果：API 拒绝，或框架悄悄截断最老消息、模型失忆。

**Q3: 记忆分哪三个层次？**

**答：** 短期（messages 数组）、长期（外部存储）、工作（任务关键信息），本质是给信息标注"住哪、活多久"。

- 短期受窗口限制、随用随丢；长期存数据库/向量库、跨会话；工作是最不能丢的几条关键信息。

**Q4: 省上下文空间的三种策略？各自代价？**

**答：** 滑动窗口（砍）、摘要（压缩）、检索（外移）。

- 滑动窗口：快、token 稳定，但丢早期信息。
- 摘要：既省又保关键信息，但多一次模型调用 + 有幻觉/丢细节风险。
- 检索：最稳但要建存储。实战常是组合拳。

**Q5: 滑动窗口和摘要各适合什么场景？**

**答：** 滑动窗口适合"早期信息不重要、只看最近"的场景（闲聊、实时问答）；摘要适合"早期信息重要、但可用概率方式概括"的场景（长任务、多轮客服）。

- 判据：信息越不重要越可以砍；越重要越不能靠猜，要么摘要要么外移。

**Q6: 怎么估算一次调用的成本？**

**答：** 成本 = token × 单价，输入输出分开计费（输出通常贵 3~5 倍）。

- 公式：`输入token/1e6 × 输入单价 + 输出token/1e6 × 输出单价`。
- Agent 是循环，成本按"轮数 × 每轮 token"累加，压缩上下文 = 直接省钱。

**Q7: 为什么工具结果也要计入 token？**

**答：** 因为工具结果会作为 `role: 'tool'` 消息塞进 messages，下一轮要整个发给模型，它和对话一样占窗口。

- 一个 8000 字符的工具返回可能瞬间吃掉整个窗口。
- 处理：先判断是否真需要全文，不需要就截断/取关键部分/摘要后再喂回。

**Q8: 长期记忆怎么实现？检索（RAG）是什么？**

**答：** 长期记忆存外部（数据库/向量库），需要时检索回来拼进窗口；RAG 就是"先检索相关资料、再让模型基于资料回答"。

- 它把"回答所需的事实"从模型脑子里搬出来放到输入里，模型从"命题作文"变成"阅读理解"。
- 是抗幻觉最有效、最常用的手段。

### 5. 多步推理与结构化输出（8 题）

**Q1: 为什么复杂任务模型"一步出不了答案"？**

**答：** 模型一次调用只有一次输出，复杂任务的每一步中间结果必须作为下一步的输入，单次调用给不了这些中间结果。

- 多步任务靠代码把中间结果反复喂回输入（如 ReAct 循环）。

**Q2: 什么是 CoT？原理是什么？什么时候别用？**

**答：** 思维链（Chain-of-Thought）是"让模型在给最终答案前先把推理过程写出来"；原理是逐 token 生成，已输出的过程 token 成为后续计算的"草稿纸"。

- 只对"需要中间计算/推理"的任务有效（算术、多条件判断、推导链）。
- 简单任务（翻译、改写、摘要、事实问答）别用，写过程纯浪费 token。

**Q3: 什么是 ReAct？Thought/Action/Observation 谁生成？**

**答：** ReAct 是"推理 + 行动"交替的循环；Thought 和 Action 是模型生成的文本，Observation 是代码执行工具后喂回的。

- 结构：`Thought → Action → Observation` 循环，直到 `Final Answer`。
- 模型只负责"想和说"，动手的是你的代码。

**Q4: ReAct 和 function calling 是什么关系？**

**答：** 思想相同、实现层级不同。ReAct 是纯文本协议（任何模型都能用，你正则抠），function calling 是厂商把工具调用做成了结构化 API 返回。

- 都遵循"模型输出意图 → 代码执行 → 结果喂回"的循环。

**Q5: 什么是 plan-execute-reflect？为什么需要反思？**

**答：** 计划 → 执行 → 反思 → 改计划的三段式；反思专门修复"第一次计划就是错的"。

- 模型第一次做的计划经常是错的（如"第一天去长城"，结果查到暴雨）。
- 反思必须有明确结束条件（如返回 `DONE`），否则反思自己会死循环。

**Q6: 为什么需要结构化输出？约束手段分几档？**

**答：** 让模型输出 JSON，代码从"正则抠文本"变成"直接读字段"，摆脱正则地狱；约束分四档：prompt → JSON mode → JSON Schema → 函数式输出。

- 约束力递增、通用性递减。
- 无论哪一档，后面都要接健壮解析器兜底。

**Q7: 模型输出的 JSON 是"脏"的，怎么清洗？**

**答：** 一条流水线——剥壳 → 修复 → 解析 → 校验。

- 剥壳：抠掉 json 代码块外壳。
- 修复：去尾逗号、换中文引号（只在 parse 失败后才修）。
- 校验：补默认值、查必填字段，缺省和必填分开处理。

**Q8: JSON 的转义陷阱是什么？为什么无法自动修复？**

**答：** 字符串里的双引号必须写成 `\"`；漏转义时字符串的结束位置产生二义性，任何"修复"都可能是错的，所以只能报错重试。

- 源头堵：prompt 提醒 + JSON mode + 永远用 `JSON.stringify` 生成。

### 6. 安全、工程化与成本（9 题）

**Q1: 什么是幻觉？为什么它无法彻底消除？**

**答：** 幻觉是模型在"编词"而非"查事实"；因为训练目标是"输出像人写的文本"，不确定时它会硬编而不是说"不知道"，这是它的工作方式而非 bug。

- 在 Agent 里的三种危害：编工具名、编参数、编"已完成"。
- 你只能假设它一定会编，用校验兜底。

**Q2: 怎么缓解幻觉？**

**答：** 两条路一起上——① RAG：把事实检索进上下文，让模型"照稿念"；② 允许说不知道：降低它编造的动机。

- 黄金组合：先检索给足资料，再允许它对资料外的问题说"不知道"。

**Q3: 什么是提示注入？为什么防不住？**

**答：** 把恶意指令藏进"看似无辜的数据"里诱导模型越权；防不住是因为模型分不清"指令"和"数据"——系统提示和用户输入对模型来说都是"一段文字"。

- 注入还可能来自你主动检索进去的文档。

**Q4: 提示注入的分层防御？**

**答：** 三层——规则过滤（拦明显注入）、数据隔离（分隔符切开指令区/数据区）、最小权限（控制损失上限）。

- 规则过滤成本低、确定性高，但拦不住变体，只是第一层。
- 最小权限最根本：给模型的工具越少，被骗的代价越小。

**Q5: 工具调用安全有哪些要点？**

**答：** 三点——先校验后执行、最小权限、绝不 `eval` 模型生成的代码。

- 校验和执行拆开（validate/execute 分离）。
- 给模型的能力只到"完成任务所需的最小程度"。
- 模型生成的代码可能被注入污染，`eval` 一次就可能泄露密钥。

**Q6: Agent 死循环/成本失控怎么防？几道刹车？**

**答：** 三道独立刹车——最大步数（管次数）、预算上限（管钱）、人工审批（管不可逆动作）。

- 最大步数：`while (steps < maxIterations)` 结构性兜底。
- 预算上限：每次工具调用累计花费，超了就停（与步数正交）。
- 人工审批：转账、发邮件、删数据这类不可逆动作，最终决定权交回人手里。

**Q7: 敏感数据怎么处理？**

**答：** 顺序是"能不外发就不外发，实在要发就脱敏，脱敏放调用模型的唯一入口处，日志同样脱敏"。

- 能交给确定性代码（如 SQL 求和）的，别把原始数据塞给模型。
- 脱敏用正则替换成占位符（如手机号 `138****5678`）。

**Q8: 怎么测试一个概率系统（Agent）？**

**答：** 测结构和边界，不测措辞——用 mock LLM 固定剧本，断言"字段/步骤/兜底"。

- 不能断言精确措辞，否则测试随机失败。
- 该测：调了正确的工具、循环在步数上限内停止、状态能序列化恢复。

**Q9: 什么时候该上 LangChain / LangGraph？顺序是什么？**

**答：** 先自建懂原理，再按复杂度选框架——简单 Agent 自建，复杂状态机上 LangGraph，要现成组件局部用 LangChain。

- LangChain 偏"工作流"（预定义链），LangGraph 偏"真 Agent"（有状态的图）。
- 框架的价值是"你已经知道该写什么后帮你少写样板"，不是替你遮住原理。

### 手写题（10 题）

**手写 1：最小 agent loop**

```js
async function runAgent(llm, messages, tools, { maxIterations = 10 } = {}) {
  for (let steps = 0; steps < maxIterations; steps++) {
    const r = await llm.invoke(messages);
    if (!r.toolCall) return r.text;
    const fn = tools[r.toolCall.name];
    messages.push({ role: 'tool', content: fn ? fn(r.toolCall.args) : `未知工具：${r.toolCall.name}` });
  }
  return `超过最大步数 ${maxIterations}`;
}
```

**手写 2：工具分发器（先校验后执行）**

```js
function dispatchTool(name, args) {
  const tool = tools[name];
  if (!tool) return { ok: false, error: `未知工具：${name}` };
  const check = tool.validate(args ?? {});
  if (!check.ok) return { ok: false, error: check.error };
  return { ok: true, result: tool.execute(args) };
}
```

**手写 3：健壮 JSON 解析器骨架**

```js
function parseJsonOutput(text) {
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  let s = fenced ? fenced[1].trim() : text.trim();
  try {
    return { ok: true, data: JSON.parse(s) };
  } catch {
    s = s.replace(/,\s*([}\]])/g, '$1').replace(/[\u201C\u201D]/g, '"');
    try { return { ok: true, data: JSON.parse(s) }; }
    catch (e) { return { ok: false, error: e.message }; }
  }
}
```

function slidingWindow(messages, keepLast) {

function estimateTokens(text) {

const INJECTION_PATTERNS = [

**手写 7：状态序列化（纯数据，无循环引用）**

```js
class AgentState {
  constructor(messages = [], { maxIterations = 5 } = {}) {
    this.messages = messages; this.steps = 0;
    this.maxIterations = maxIterations; this.finished = false;
  }
  serialize() {
    return JSON.stringify({
      messages: this.messages, steps: this.steps,
      maxIterations: this.maxIterations, finished: this.finished,
    });
  }
  static deserialize(json) {
    const d = JSON.parse(json);
    const s = new AgentState(d.messages, { maxIterations: d.maxIterations });
    s.steps = d.steps; s.finished = d.finished;
    return s;
  }
}
```

### 读代码说结果（3 题）

**读 1：**

```js
const list = ['a', 'b', 'c', 'd', 'e'];
console.log(list.slice(-2));
```

**结果：** `[ 'd', 'e' ]`——`slice(-2)` 取最后两条，是滑动窗口"只留最近 N 条"的底层。

**读 2：**

```js
try {
  JSON.parse('{"a":1,}');
} catch (e) {
  console.log(e.name);
}
```

**结果：** `SyntaxError`——尾逗号是非法 JSON，这是模型最爱犯的错，所以要 `repairJson` 去尾逗号。

**读 3：**

```js
const a = {};
a.self = a;
try { JSON.stringify(a); } catch (e) { console.log(e.name); }
```

**结果：** `TypeError`——循环引用会让 `JSON.stringify` 抛 `TypeError: Converting circular structure to JSON`，所以状态里只能放纯数据。

## 第三部分：一页速查表

### 核心概念

| 概念 | 一句话定义 |
|---|---|
| Agent | 模型在循环里自主决定流程、调用工具直到完成任务的系统 |
| Workflow | 流程由预定义代码路径编排，模型没有选择权 |
| 无状态 | 模型每次调用独立计算，不保存跨调用信息 |
| token | 模型切分文本的最小单位（中文 1 字≈1，英文 4 字符≈1） |
| 上下文窗口 | 模型一次调用能看见的最大 token 数（硬上限） |
| function calling | 模型输出"想调工具"的结构化文字，代码解析执行后喂回 |
| ReAct | Thought（想）+ Action（动）+ Observation（看）的循环 |
| CoT | 让模型先写出推理过程，过程 token 当"草稿纸" |
| RAG | 先检索资料再让模型基于资料回答，抗幻觉 |
| 幻觉 | 模型在编词而非查事实，是默认行为不是 bug |
| 提示注入 | 把恶意指令藏进数据里诱导模型越权 |
| 最小权限 | 给模型的能力只到完成任务所需的最小程度 |
| trace | 每一步"时间/步数/动作/输入输出"的流水账 |

### 消息 role 速查

| role | 语义 | 谁说的 | 时机 |
|---|---|---|---|
| `system` | 最高优先级规则 | 开发者 | 对话最前，通常一次 |
| `user` | 要回应的对象 | 用户 | 每次提问 |
| `assistant` | 模型说过的话 | 模型 | 每次回复后 |
| `tool` | 工具返回的事实 | 代码回填 | 工具执行后，紧跟对应 assistant |

### 工具调用流程速查

```text
模型输出 tool_call（结构化文字）
      ↓
代码解析工具名 + 参数（arguments 是字符串，要 JSON.parse）
      ↓
代码校验参数（validate：类型/范围/格式，失败喂回错误）
      ↓
代码执行工具（execute，真正动手）
      ↓
结果以 role:'tool' 喂回（真实 API 要带 tool_call_id）
      ↓
回到循环顶部，再问模型（受 maxIterations / budget 兜底）
```

### 常见报错速查

| 报错 | 触发场景 | 含义 / 对策 |
|---|---|---|
| `TypeError: Cannot read properties of undefined (reading 'length')` | `llm.invoke()` 漏传 messages | 永远 `invoke(messages)` |
| `TypeError: tools[name] is not a function` | 调用不存在的工具 | 执行前查白名单，未知工具喂回 |
| `TypeError: "一百块".toFixed is not a function` | 模型返回错误类型参数 | validate 先做类型校验 |
| `TypeError: Converting circular structure to JSON` | 状态里有循环引用 | 状态只放纯数据 |
| `SyntaxError: Unexpected token ... is not valid JSON` | 脏 JSON（代码块/尾逗号） | 剥壳 + repairJson + 重试 |
| `SyntaxError: Expected ',' or '}' after property value in JSON` | 漏转义双引号 | 源头堵，无法自动修复 |
| `context_length_exceeded` | 输入超上下文窗口 | 滑动窗口 / 摘要 / 检索 |
| `400 invalid_request_error`（真实 API） | role 拼错 / tool_call_id 对不上 | role 只写四种，id 原样对应 |

## 第四部分：面试技巧

### 不会时怎么救场

1. **先给框架，再给细节**：不会具体答案时，说"这个问题我理解的核心是 X，我可以从 Y 和 Z 两个角度讲"，然后把你知道的相关知识组织起来。面试官更看重思路，不是标准答案。
2. **坦白 + 类比**：真不会就说"这块我接触不多，但根据我理解的类似机制（比如……），我的判断是……"。宁可诚实地推导，也别硬编一个错的——编错比不会扣分更多。
3. **引导到你会的地方**：把话题接回你熟悉的领域——"您问的是工具调用安全，我在这方面做过的实践是 validate/execute 分离……"。
4. **用"代价"补深度**：任何概念，如果你能补一句"它的代价是 X，所以什么时候不该用"，立刻显得你懂设计动机，而不是背定义。

### 可以反问面试官什么

1. "你们现在用 Agent 的典型场景是什么？是偏工作流还是偏自主 Agent？"——显得你关心"能不能不用 Agent"这个关键判断。
2. "团队里现在工具调用的校验和护栏是怎么做的？有没有用框架，还是自建循环？"——探技术栈深度，也展示你懂工程化。
3. "Agent 的可观测性（trace）现在是怎么做的？出问题怎么定位？"——展示你关注"能跑 vs 能维护"的分界。
4. "模型调用成本这块，有没有预算或兜底机制？"——展示你懂"概率系统要装刹车"。

### 面试前一晚的最后一页

- 背熟五个"一句话"：Agent 定义、无状态、工具调用闭环、上下文窗口、Agent vs 工作流。
- 每个概念都准备一句"代价/什么时候不该用"。
- 手写一遍最小 agent loop 和工具分发器，确保白板时肌肉记忆能写出来。
- 记住 8 个常见报错码，被问到"你遇到过什么坑"时能立刻报出真实错误名。
