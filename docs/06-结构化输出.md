# 第 06 章 · 结构化输出

> 上一章你让模型"多步推理"，但每一步模型吐出来的都是**自由文本**。
> 代码要"看懂"这些文本，就得解析——而自由文本是解析的噩梦。
> 本章你需要记住的就一件事：**让模型输出 JSON（结构化），代码才能可靠地消费；但模型吐出的 JSON 常常是"脏"的，你必须写一个健壮的解析器。**
> 配套代码：`examples/06-结构化输出.mjs`（可运行，退出码 0）。

---

## 06.1 为什么需要结构化输出

先给结论：**模型输出的是自由文本，代码想从里面提取"温度""情绪""关键词"这些字段，只能靠正则硬抠——而正则一遇到"模型换种说法"就崩。**
结构化输出（JSON）就是让模型把结果**直接组织成代码能 `JSON.parse` 的格式**。

看一个具体对比。假设你让模型报天气，想拿到"温度"这个数字：

```js
// 模型输出自由文本，你想拿到温度，只能正则硬抠
const freeText = '今天北京天气是小雨，气温 22 摄氏度，湿度 65%。';
const temp = freeText.match(/气温\s*(\d+)/)?.[1];
console.log(temp);

// 但模型换一种说法，你的正则就失效了
const freeText2 = '北京今天 22 度，有小雨';
console.log(freeText2.match(/气温\s*(\d+)/)?.[1]);
```

```text
22
undefined
```

看到了吗？同样一句话，模型换个说法，正则就拿到 `undefined`，接下来代码一 `Number(undefined)` 就 `NaN`，然后污染整个下游。

换成结构化输出，让模型直接给你 JSON：

```js
// 让模型直接输出 JSON，代码一行就能拿到字段
const json = '{"city":"北京","weather":"小雨","temperature":22,"humidity":65}';
const data = JSON.parse(json);
console.log(data.temperature); // 22，不管模型"怎么说"，字段就在那
```

```text
22
```

这就是结构化输出的全部动机：**把"从文本里抠数据"这个不可靠的动作，变成"直接读字段"这个可靠的动作。**
你从正则的地狱里被解救出来，代码变得可验证、可测试。

> 一句话记住它：自由文本让代码陷入正则地狱，JSON 让代码直接读字段；结构化输出的本质是把"解析"变成"读取"。

## 06.2 约束输出的几种手段（从弱到强）

先给结论：**约束模型输出 JSON 有四档手段，约束力从弱到强、成本从低到高——prompt 约束 → JSON mode → JSON Schema → 函数式输出。**
大部分场景，前两档就够；只有严格到"字段一个都不能错"时才上后两档。

### 手段 1：prompt 约束（最弱，但最通用）

就是在提示词里告诉模型"只输出 JSON，不要其他文字"。**它对任何模型都生效**，但约束力最弱——模型可能仍然多写个解释、或者格式出错。

```js
const PROMPT = [
  '你是天气助手。请把结果组织成一个 JSON 对象，字段包括：',
  'city（城市）、weather（天气）、temperature（温度，数字）。',
  '只输出 JSON，不要输出任何解释性文字。',
].join('\n');

// 发给模型的 system 消息就是这段。模型"通常"会配合，但"通常"不等于"一定"。
// 它仍可能输出：
//   好嘞，结果如下：{"city":"北京", ...}   ← 多了前缀，JSON.parse 直接失败
```

### 手段 2：JSON mode（强一点，但要看 API 支不支持）

OpenAI 等厂商提供了 `response_format` 参数，把输出锁定成 JSON：

```js
// 伪代码：换成真实 API 时，请求体里加这个字段（这里用注释说明，不真实发请求）
const response = await fetch('https://api.openai.com/v1/chat/completions', {
  method: 'POST',
  headers: { Authorization: 'Bearer ...' },
  body: JSON.stringify({
    model: 'gpt-4o',
    messages: [{ role: 'user', content: '报一下北京天气' }],
    response_format: { type: 'json_object' }, // ← 关键：强制输出合法 JSON
  }),
});
```

它的作用是**保证输出是合法 JSON**（`JSON.parse` 不会失败），但**不保证字段结构**——模型可能给你
`{"天气":"小雨"}`（中文键）而不是你要的 `{"weather":"小雨"}`。字段对不对，仍要靠你校验。

### 手段 3：JSON Schema（更强，约束字段结构）

在 JSON mode 的基础上，再传一个 JSON Schema，明确每个字段的名字、类型、必填：

```js
// 伪代码：用 json_schema 约束结构（OpenAI 的 structured outputs）
const schema = {
  type: 'object',
  properties: {
    city: { type: 'string' },
    weather: { type: 'string' },
    temperature: { type: 'number' },
  },
  required: ['city', 'weather', 'temperature'], // 这些字段必须有
  additionalProperties: false,                  // 不允许出现多余字段
};

// 请求体里带上它：
// response_format: {
//   type: 'json_schema',
//   json_schema: { name: 'weather_report', schema },
// }
```

这一档能**在模型侧就保证字段对**，省去你大量校验代码。代价是：不是所有模型都支持，而且 schema 越严格，模型输出越可能"被卡住"（生成失败或变慢）。

### 手段 4：函数式输出（最强，工具调用的副产品）

第 03 章讲的 function calling / tool use，本质就是**模型输出"调用某个函数的参数"，而参数天然是结构化 JSON**。

```js
// 模型的 toolCall 返回（第 03 章的结构）：
// { name: 'report_weather', args: { city: '北京', weather: '小雨', temperature: 22 } }
// 这里的 args 已经是解析好的 JSON 对象，你连 JSON.parse 都不用写。
```

四档的取舍一张表：

| 手段 | 约束力 | 通用性 | 代价 |
|---|---|---|---|
| prompt 约束 | 弱（可能多字、可能格式错） | 任何模型 | 几乎为零 |
| JSON mode | 中（保证合法 JSON，不保证字段） | 部分厂商 | 依赖 API 支持 |
| JSON Schema | 强（保证字段名/类型/必填） | 更少厂商 | schema 设计成本，太严会卡生成 |
| 函数式输出 | 最强（参数即对象） | 依赖 function calling | 需要定义工具 schema |

**实战经验**：不管用哪一档，**永远假设模型输出是脏的，后面一定要接健壮解析器**（下一节）。因为哪怕 JSON mode 保证"合法 JSON"，也可能缺字段、类型不对。

> 一句话记住它：约束输出有 prompt → JSON mode → JSON Schema → 函数式输出四档，约束力递增、通用性递减；无论哪一档，后面都要接健壮解析器兜底。

## 06.3 健壮解析器：脏 JSON 怎么清洗

先给结论：**模型吐出的 JSON 常常是"脏"的——被 ```json 包裹、带尾逗号、用中文引号、缺字段。健壮解析器就是一条流水线：剥壳 → 修复 → 解析 → 校验。**

这一节是本章最实用的一节，代码就是 `examples/06-结构化输出.mjs` 的核心。

### 第一步：剥掉 markdown 代码块

模型以为你在聊天框里看结果，经常把 JSON 包进 ```json ... ```：

```js
function extractJsonBlock(text) {
  // 优先匹配 ```json ... ``` 或 ``` ... ```
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  if (fenced) return fenced[1].trim();

  // 没有代码块：找第一个 { 到最后一个 } 之间的内容
  const start = text.indexOf('{');
  const end = text.lastIndexOf('}');
  if (start !== -1 && end > start) return text.slice(start, end + 1).trim();

  return text.trim();
}
```

### 第二步：修复常见的脏 JSON

模型真实会犯的两种错：**尾逗号**（JSON 标准不允许 `{"a":1,}` 和 `[1,2,]`）和**中文引号当定界符**：

```js
function repairJson(text) {
  let s = text;
  // 1) 去尾逗号：{... ,} 和 [... ,] 是非法 JSON，但模型极爱写
  s = s.replace(/,\s*([}\]])/g, '$1');
  // 2) 中文引号当定界符：模型偶尔用 “ ” 代替 "
  s = s.replace(/[\u201C\u201D]/g, '"');
  return s;
}
```

**注意**：修复是有损的（尤其替换中文引号会误伤字符串内部的中文引号），所以**只在 `JSON.parse` 失败后才调用修复，而不是无脑预处理**。

### 第三步：校验字段

`JSON.parse` 成功，只代表"这是合法 JSON"，不代表"这是我要的 JSON"。还得查必填字段：

```js
function validateFields(obj, required) {
  const missing = required.filter((k) => obj[k] === undefined || obj[k] === null);
  return missing.length > 0
    ? { ok: false, error: `缺失字段：${missing.join(', ')}` }
    : { ok: true };
}
```

### 组合起来

```js
function parseJsonOutput(text, { required = [], defaults = {} } = {}) {
  const cleaned = extractJsonBlock(text);
  let data;
  try {
    data = JSON.parse(cleaned);
  } catch {
    try {
      data = JSON.parse(repairJson(cleaned)); // 第一次失败，修复后再试
    } catch (e2) {
      return { ok: false, error: `JSON 解析失败：${e2.message}` };
    }
  }
  for (const [k, v] of Object.entries(defaults)) {
    if (data[k] === undefined) data[k] = v; // 补默认值
  }
  const check = validateFields(data, required);
  return check.ok ? { ok: true, data } : { ok: false, error: check.error, data };
}
```

运行 `node examples/06-结构化输出.mjs`，看它对 6 种真实脏输出的处理：

```text

[原始] {"summary":"天气不错","sentiment":"positive","keywords":["天气","不错"]}
[解析] ✅ {"summary":"天气不错","sentiment":"positive","keywords":["天气","不错"]}
--- 第 2 种输出 ---
[原始] ```json
{"summary":"天气不错","sentiment":"positive","keywords":["天气"]}
```
[解析] ✅ {"summary":"天气不错","sentiment":"positive","keywords":["天气"]}
--- 第 3 种输出 ---
[原始] {"summary":"天气不错","sentiment":"positive","keywords":["天气","不错",]}
[解析] ✅ {"summary":"天气不错","sentiment":"positive","keywords":["天气","不错"]}
--- 第 4 种输出 ---
[原始] {"summary":"天气不错"}
[解析] ❌ 缺失字段：sentiment
--- 第 5 种输出 ---
[原始] {“summary”:“天气不错”,“sentiment”:“positive”,“keywords”:[“天气”]}
[解析] ✅ {"summary":"天气不错","sentiment":"positive","keywords":["天气"]}
--- 第 6 种输出 ---
[原始] {"quote":"他说"你好"","sentiment":"neutral","keywords":[]}

```

注意第 4 种：`keywords` 缺了但没报错，因为 `defaults` 给了 `keywords: []`；`sentiment` 没默认值，所以报缺失。
这正是**"缺省字段"和"必填字段"要分开处理的理由**——不是所有字段都同等重要。

第 6 种的解析失败，就是我们下一节要单独拎出来讲的**转义陷阱**——它连修复函数都救不回来。

> 一句话记住它：健壮解析器 = 剥壳 → 修复 → 解析 → 校验四步；先 `JSON.parse`，失败再修复重试，最后校验字段，缺省和必填要分开对待。

## 06.4 JSON 的转义陷阱

先给结论：**JSON 字符串里的双引号必须写成 `\"`，反斜杠必须写成 `\\`。模型经常漏转义，导致整段 JSON 直接报废，且无法自动修复。**

这是结构化输出里最隐蔽、最致命的一个坑。看真实报错：

```js
// 模型想输出一句话，里面带英文双引号，但它忘了转义
const bad = '{"quote":"他说"你好""}';
try {
  JSON.parse(bad);
} catch (e) {
  console.log(`坏转义 ${bad}`);
  console.log(`报错：${e.name}: ${e.message}`);
}

// 正确的写法：字符串里的双引号前面加反斜杠
const good = '{"quote":"他说\\"你好\\""}';
console.log(`好转义 ${good} → ${JSON.stringify(JSON.parse(good))}`);
```

```text
坏转义 {"quote":"他说"你好""}
报错：SyntaxError: Expected ',' or '}' after property value in JSON at position 13 (line 1 column 14)
好转义 {"quote":"他说\"你好\""} → {"quote":"他说\"你好\""}
```

为什么这个坑"无法自动修复"？因为坏转义的字符串**语法上是二义性的**——解析器看到 `"他说"` 之后，认为这个字符串已经结束了，后面的 `你好` 是凭空冒出来的，它无法判断你到底是"想转义但忘了"，还是"真的写错了"。尾逗号能修、中文引号能修，唯独漏掉的转义**没有安全的修法**。

所以正确的策略是**在源头堵**，而不是事后修：

1. **prompt 里明确告诉模型**："字符串里如果出现英文双引号，必须转义成 `\"`。"
2. **用 JSON mode / JSON Schema**：厂商会在模型侧强制它输出合法 JSON，从根上避免漏转义。
3. **代码里对无法解析的 JSON 直接报错重试**：与其拿一个错的值硬跑，不如重来一次（第 00 章的"重试"哲学）。

还有一个**更容易踩的反向坑**：你在写代码时，用 `JSON.stringify` 生成的字符串里，双引号会被**自动转义**，看起来是 `\"`，实际是合法的。所以**永远别手写 JSON 字符串，用 `JSON.stringify` 生成**：

```js
// ✅ 永远用 JSON.stringify 生成 JSON，转义它自动帮你处理
const obj = { quote: '他说"你好"' }; // 值里有双引号
console.log(JSON.stringify(obj));     // 自动变成合法的 {"quote":"他说\"你好\""}
```

```text
{"quote":"他说\"你好\""}
```

> 一句话记住它：JSON 字符串里的双引号要 `\"`，反斜杠要 `\\`；漏转义无法自动修复，要在源头堵（prompt 提醒 + JSON mode + 永远用 JSON.stringify 生成）。

## 06.5 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 用正则抠自由文本 | `match(...)` 返回 `undefined`，下游 `NaN` | 模型换种说法，正则就失效 | 让模型输出 JSON，直接读字段 |
| JSON 被 ```json 包裹 | `JSON.parse` 报 `Unexpected token '\n'` 之类 | 模型以为你在聊天框看，加了代码块 | 先 `extractJsonBlock` 剥壳 |
| 尾逗号 | `JSON.parse` 报 `Unexpected token ']' ... is not valid JSON` | 模型按"人类写列表"的习惯加了逗号 | `repairJson` 去尾逗号 |
| 中文引号当定界符 | 报 `Expected property name or '}' in JSON at position 1` | 模型用 `“ ”` 代替 `"` | 失败后替换中文引号再试 |
| 缺必填字段 | 解析成功但 `data.xxx` 是 `undefined` | 模型没吐全字段 | `validateFields` 校验必填，缺省给默认值 |
| 漏转义双引号 | 报 `Expected ',' or '}' after property value in JSON` | 字符串里的 `"` 没写成 `\"` | 源头堵：prompt 提醒 + JSON mode + JSON.stringify 生成 |
| 手写 JSON 字符串 | 转义写错、引号漏了 | 人肉拼字符串容易错 | 一律用 `JSON.stringify` 生成 |
| 把"合法 JSON"当"对的 JSON" | 字段名不对、类型不对 | `JSON.parse` 只保证语法 | 解析后再校验字段名和类型 |

## 06.6 本章小结

- 结构化输出的动机：把**"从文本抠数据"变成"直接读字段"**，摆脱正则地狱。
- 约束输出四档：**prompt 约束 → JSON mode → JSON Schema → 函数式输出**，约束力递增、通用性递减。
- 无论哪一档，**都要接健壮解析器**：剥壳 → 修复 → 解析 → 校验。
- 缺省字段和必填字段要**分开处理**：缺省给默认值，必填缺失直接报错。
- **转义陷阱**：JSON 字符串里的 `"` 要写成 `\"`，漏转义无法自动修复，要在源头堵。
- 生成 JSON 永远用 **`JSON.stringify`**，别手写字符串。

## 06.7 动手练习

1. 给 `parseJsonOutput` 加一个"类型校验"：`temperature` 必须是数字，如果是字符串 `"22"` 就转成数字 `22`；如果既不是数字也不是数字字符串，就报错。
   <details><summary>参考答案</summary>

   ```js
   function coerceTemperature(data) {
     if (typeof data.temperature === 'number') return data.temperature;
     if (typeof data.temperature === 'string' && !Number.isNaN(Number(data.temperature))) {
       data.temperature = Number(data.temperature);
       return data.temperature;
     }
     throw new Error(`temperature 类型非法：${data.temperature}`);
   }
   ```
   </details>

2. 模型输出 `{"a": 1,}` 这种尾逗号，`repairJson` 是怎么修好的？它会不会误伤"合法的字符串内容里的逗号"？
   <details><summary>参考答案</summary>
   `repairJson` 用正则 `s.replace(/,\s*([}\]])/g, '$1')`，只匹配"逗号后面紧跟 `}` 或 `]`"的情况，把 `,}` 换成 `}`、`,]` 换成 `]`。字符串内容里的逗号（比如 `"你好，世界"`）后面跟的不是 `}` 或 `]`，所以不会被误伤。
   </details>

3. 为什么说"漏转义的双引号无法自动修复"，而"尾逗号能修"？
   <details><summary>参考答案</summary>
   尾逗号是明确的语法错误，删掉逗号只有一种正确结果。但漏转义的双引号让字符串的结束位置产生二义性——解析器无法判断 `你好` 到底是字符串内容还是非法 token，任何"修复"都可能是错的，所以只能报错重试。
   </details>

4. 你用 `JSON.stringify` 输出一个含换行的字符串，结果里的 `\n` 是什么？为什么？
   <details><summary>参考答案</summary>
   结果里是字面的 `\n`（两个字符：反斜杠 + n），因为 JSON 字符串不能包含真实的换行符，`JSON.stringify` 会把它转义成 `\n`。这是合法的转义，`JSON.parse` 之后会还原成真实的换行。
   </details>
