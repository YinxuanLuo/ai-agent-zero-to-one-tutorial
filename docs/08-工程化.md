# 第 08 章 · 工程化：把玩具变成系统

> 前面几章你写的 Agent 能跑，但还只是个"玩具"：状态散落在局部变量里、出错时你看不见它干了什么、想改一行又不敢改因为怕改坏。这一章解决三个问题：**状态怎么存、过程怎么看得见、代码怎么测**，最后聊 TypeScript 化和框架选型。
> 本章你需要记住的就一件事：**能跑（it works）和能维护（it's maintainable）之间，隔着状态管理、可观测性、测试这三样东西。**

---

## 08.1 状态管理：把中间状态变成"值"

先给结论：**Agent 的中间状态（对话历史、已走步数、是否结束）必须是一个"值"，而不是散落在各处的局部变量。** 是"值"才能序列化存库、才能在崩溃后恢复、才能被测试断言。

### 为什么局部变量不行

回想你之前写的循环，大概率长这样：

```js
async function runAgent(llm) {
  const messages = [];   // 局部变量
  let steps = 0;          // 局部变量
  while (true) {
    // ...
  }
}
```

`messages` 和 `steps` 困在这个函数的作用域里。结果就是三个麻烦：

1. **存不下来**：程序一退出，状态就没了。你想"从上次断点继续跑"？做不到。
2. **看不见**：调试时你没法在函数外部看一眼"现在跑到第几步了"。
3. **测不了**：测试没法在调用前后检查状态，因为它根本没暴露出来。

所以工程化的第一步，是**把状态提升成一个显式的对象**。`examples/08-工程化.mjs` 里的 `AgentState`：

```js
class AgentState {
  constructor(messages = [], { maxIterations = 5 } = {}) {
    this.messages = messages;   // 对话历史，纯数据
    this.steps = 0;             // 已走的步数
    this.maxIterations = maxIterations;
    this.finished = false;      // 是否已产出最终回答
  }

  // 序列化：状态变成字符串，可以写文件、存数据库
  serialize() {
    return JSON.stringify({
      messages: this.messages,
      steps: this.steps,
      maxIterations: this.maxIterations,
      finished: this.finished,
    });
  }

  // 反序列化：从字符串恢复状态，崩溃后从这里续跑
  static deserialize(json) {
    const data = JSON.parse(json);
    const s = new AgentState(data.messages, { maxIterations: data.maxIterations });
    s.steps = data.steps;
    s.finished = data.finished;
    return s;
  }
}
```

关键在 `serialize` / `deserialize` 这对方法。它们把"内存里的对象"和"磁盘上的字符串"打通了——这是状态能持久化、能恢复的前提。

### 序列化的一个真实陷阱：状态里不能有循环引用

`serialize` 用的是 `JSON.stringify`。如果你的状态对象里不小心混进了循环引用（比如消息里引用了某个又指回消息的对象），序列化会直接炸。运行这段：

```js
const a = {};
a.self = a;        // 制造一个循环引用
JSON.stringify(a);
```

会看到：

```text
TypeError: Converting circular structure to JSON
```

所以状态管理有个硬约束：**状态必须是"纯数据"**——只有基本类型、数组、普通对象，不能有函数、不能有循环引用、不能有 DOM 节点或 EventEmitter 这类运行时对象。这也是为什么 `AgentState` 里只存 `messages`（纯数组）和几个数字/布尔，不存 `llm`、不存 `tracer`——那些是"运行时的东西"，不是"状态"。

> 一句话记住它：状态是"值"不是"变量"——把它显式化、序列化、纯数据化，你才谈得上持久化、恢复和测试。

## 08.2 可观测性：让每一步都留痕

先给结论：**Agent 出了 bug，你不能靠"猜"，要靠 trace——一份"每一步做了什么"的流水账。** 它要能回答三个问题：模型这一步输出了什么？工具这一步执行了什么？循环为什么没停？

### trace 记什么

一份有用的 trace，每条至少带四个字段：**什么时候、第几步、做了什么动作、输入输出是什么**。`examples/08-工程化.mjs` 里的 tracer：

```js
function createTracer() {
  const records = [];
  return {
    record(entry) {
      records.push({ ts: new Date().toISOString(), ...entry });
    },
    list() {
      return records;
    },
  };
}
```

然后在循环的每个关键节点调用 `tracer.record(...)`：

```js
async function runAgent(llm, state, tracer) {
  while (state.steps < state.maxIterations) {
    state.steps += 1;
    const res = await llm.invoke(state.messages);
    tracer.record({ step: state.steps, kind: 'llm', output: res });   // 记录模型这一步

    if (!res.toolCall) {
      state.finished = true;
      tracer.record({ step: state.steps, kind: 'finish', text: res.text });
      return { done: true, text: res.text };
    }

    const out = dispatchTool(res.toolCall.name, res.toolCall.args);
    tracer.record({ step: state.steps, kind: 'tool', name: res.toolCall.name, ok: out.ok }); // 记录工具这一步
    state.messages.push({ role: 'tool', content: out.ok ? out.result : `[错误] ${out.error}` });
  }
  tracer.record({ step: state.steps, kind: 'stop', reason: 'maxIterations' });
}
```

运行 `node examples/08-工程化.mjs`，演示 1 输出一份真实 trace：

```text
[trace] step=1 kind=llm
[trace] step=1 kind=tool tool=get_weather
[trace] step=2 kind=llm
[trace] step=2 kind=finish text=北京今天晴，25℃
```

现在你一眼就能看出：第 1 步模型要调工具、工具执行了、第 2 步模型给出最终回答。**每一步都有 `kind` 标记，`llm` / `tool` / `finish` / `stop` 就是这次运行的故事线。**

### trace 和日志的区别

很多人把 trace 和日志混为一谈，这里划清界线：

| | 日志（log） | 追踪（trace） |
|---|---|---|
| 记录什么 | 单条事件："某时刻发生了什么" | 一次完整运行的"步骤序列" |
| 粒度 | 离散 | 结构化、按 step 串联 |
| 用途 | 定位"哪里崩了" | 回答"这一路是怎么走的" |

真实项目里两者都要：日志给你"有没有报错、报错在哪一行"，trace 给你"报错之前，模型和工具都干了什么"。它们是互补的，不是二选一。

> 一句话记住它：可观测性的核心是 trace——每一步的"时间、步数、动作、输入输出"都留痕，出 bug 时你才有据可查，而不是靠猜。

## 08.3 测试：怎么测一个概率系统

先给结论：**概率系统测不了"精确输出"，但能测两样东西——结构约定（数据长什么样）和确定性边界（兜底、校验、状态机）。** 你的测试要瞄准这两样，而不是"模型这次说了什么话"。

### 为什么不能断言"精确内容"

一个函数 `add(1, 2)` 永远返回 3，你测 `assert.equal(add(1,2), 3)`。但一个 Agent"总结这篇文章"，跑两次给你的措辞可能不同——因为模型是概率的。如果你写 `assert.equal(agent(), '这篇文章讲了……')`，这个测试会**随机地**通过或失败，毫无意义。

所以测试的锚点要换：**不测"它说了什么"，测"它做对了什么"**。比如：

- 测"调用了正确的工具"（结构）
- 测"循环在步数上限内停止"（边界）
- 测"状态能序列化并恢复"（状态机）

### 用 mock LLM 把概率变成确定

测试的第一步是**把模型换成一个确定性的 mock**。你的生产代码依赖 `llm.invoke(messages)`，测试时塞一个"剧本固定"的 mock 进去，代码不用改。这正是 `examples/llm-mock.mjs` 里的 `createMockLlm` 干的事——它按预置剧本依次返回，可预测。

`examples/08-工程化.mjs` 里的三个测试，用 `node:test`（Node 内置，零依赖）：

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('状态序列化后能无损恢复', () => {
  const s = new AgentState([{ role: 'user', content: 'hi' }]);
  s.steps = 3;
  const restored = AgentState.deserialize(s.serialize());
  assert.equal(restored.steps, 3);
  assert.equal(restored.messages.length, 1);
  // 断言结构：每条消息都有 role 和 content 两个字段（不关心具体内容）
  assert.deepEqual(Object.keys(restored.messages[0]).sort(), ['content', 'role']);
});

test('死循环会被最大步数兜底', async () => {
  // 模型永远想调工具 → 只能靠 maxIterations 刹车
  const llm = createMockLlm(
    Array.from({ length: 100 }, () => ({ toolCall: { name: 'get_weather', args: { city: '北京' } } }))
  );
  const state = new AgentState([{ role: 'user', content: 'x' }], { maxIterations: 4 });
  const tracer = createTracer();
  const result = await runAgent(llm, state, tracer);
  assert.equal(result.done, false);
  assert.equal(result.reason, 'maxIterations');
  assert.equal(result.steps, 4);
});
```

注意第一个测试里那句注释：**断言结构而非内容**。`assert.deepEqual(Object.keys(...).sort(), ['content', 'role'])` 检查的是"每条消息必须恰好有 `role` 和 `content` 两个字段"，而不是"content 是什么"。这是概率系统测试的核心心法。

运行 `node examples/08-工程化.mjs`，你会看到测试部分输出（TAP 格式，Node 内置测试框架的标准输出）：

```text
# Subtest: 状态序列化后能无损恢复
ok 1 - 状态序列化后能无损恢复
# Subtest: 死循环会被最大步数兜底
ok 3 - 死循环会被最大步数兜底
1..3
# pass 3
# fail 0
```

`# pass 3`、`# fail 0` 就是结果；退出码 0 表示全部通过。

### 快照测试：把"这次运行"存下来当基准

还有一种适合 trace 的测试叫**快照（snapshot）测试**：第一次跑，把 trace 序列化成 JSON 存成"快照文件"；以后每次跑，把新的 trace 和快照对比。如果结构变了（比如多了一步、少了一个字段），就提醒你"行为发生了变化"——这正是 trace 该被测的东西。

思路示意（不依赖第三方快照库）：

```js
// 第一次：生成快照
const snapshot = JSON.stringify(tracer.list(), null, 2);
// fs.writeFileSync('snapshot.json', snapshot);

// 之后每次：对比
const expected = JSON.parse(fs.readFileSync('snapshot.json', 'utf8'));
assert.deepEqual(tracer.list(), expected);   // 行为变了这里就会失败
```

它测的依然是**结构**（trace 的步骤序列），不是模型的"话术"。这跟"断言精确内容"有本质区别。

> 一句话记住它：概率系统测结构和边界，不测措辞——用 mock LLM 固定剧本、断言"字段/步骤/兜底"，快照测 trace 的结构漂移。

## 08.4 TypeScript 化：让类型替你守住边界

先给结论：**从 `.mjs` + JSDoc 迁移到真正的 `.ts`，核心收益是让类型系统替你守住"消息结构、工具参数、循环返回值"这三处边界，把运行时才爆的错提前到编译期。** 但你要清楚它的边界：类型在编译后被擦除，运行时还得靠校验。

### 迁移的第一步：给核心数据结构上类型

你之前的 `.mjs` 里，消息对象、工具、循环返回值都是"约定俗成"的，没人保证。迁移到 `.ts`，先把它们定死：

```ts
// 消息的 role 只能是这四种，拼错成 'uesr' 直接编译报错
type Role = 'system' | 'user' | 'assistant' | 'tool';
type Message = { role: Role; content: string };

// 模型要么返回文字，要么返回一次工具调用——二选一
type LlmResponse =
  | { text: string; toolCall?: never }
  | { toolCall: { name: string; args: Record<string, unknown> } };

// 工具定义：校验器 + 执行器，参数类型泛化
type Tool = {
  validate: (args: Record<string, unknown>) => { ok: true } | { ok: false; error: string };
  execute: (args: Record<string, unknown>) => string;
};

// 循环结果：要么成功结束，要么因某种原因被刹车
type RunResult =
  | { done: true; text: string; steps: number }
  | { done: false; reason: 'maxIterations' | 'budget'; steps: number };
```

这三组类型，正好对应你在前几章反复写的三样东西：消息、工具、循环。它们是你 Agent 的"骨架"，骨架定了型，后面所有函数签名都能挂上去。

### 类型能拦住什么：一个真实案例

假设你在 `.mjs` 里把消息的 role 拼错了：

```js
messages.push({ role: 'uesr', content: 'hi' });   // 'uesr' 拼错了
```

在纯 JavaScript 里，这**不会报任何错**——`role` 就是个普通字符串，`'uesr'` 照样能存进去。等到后面某处写 `if (msg.role === 'tool')` 时，这个错就静静地潜伏着，让你 debug 到怀疑人生。

换成 `.ts` 后，`role: 'uesr'` 会在编译期就报错（`uesr` 不在 `Role` 联合类型里），你在写代码的那一刻就被拦住了。这就是类型系统的价值：**它把"发现错误的时间点"从运行时提前到了写代码时。**

### 类型系统的边界：它管不了运行时

但你必须清醒：**TypeScript 的类型在编译后会被擦除，运行时它一个都不剩。** 换句话说，类型保证的是"你写的代码里，传给函数的东西形状对"，**保证不了**"运行时从 JSON 反序列化出来的数据符合这个形状"。

看这个真实可复现的报错。假设你的 `deserialize` 拿到了一份缺字段的数据（比如旧版本存的、或被人改过）：

```js
const bad = JSON.stringify({ maxIterations: 5 });   // 注意：没有 messages 字段
const s = AgentState.deserialize(bad);
s.messages.push({ role: 'user', content: 'hi' });   // 运行时炸在这里
```

运行会看到：

```text
TypeError: Cannot read properties of undefined (reading 'push')
```

因为 `data.messages` 是 `undefined`，`new AgentState(undefined)` 之后 `s.messages` 就是 `undefined`，`.push` 自然报错。**类型系统在这里帮不上忙**——反序列化是运行时的事，类型已经被擦除了。所以工程化的正确姿势是：**编译期靠 TS 类型，运行时靠校验（validate）**，两者各管一段，谁都替代不了谁。

### Node 22 能直接跑 .ts，但别误会

一个容易误会的点：Node 22 支持 `--experimental-strip-types` 直接运行 `.ts` 文件。比如上面那段类型代码存成 `.ts`，直接跑：

```bash
node --experimental-strip-types demo.ts
```

能跑通，退出码 0。但注意它的名字：**strip-types（剥离类型）**，不是"检查类型"。它只是把类型注解剥掉再执行，**不做任何类型检查**。你就算把 `role: 'uesr'` 写进去，它照样跑、不报错。所以它适合"本地快速试跑 .ts 脚本"，**不能替代 `tsc` 的类型检查**——真正的类型约束还是要靠编译器的 `tsc --noEmit`。

> 一句话记住它：TS 类型替你在编译期守住消息/工具/循环的边界，但类型编译后会被擦除——编译期靠类型、运行时靠校验，两件事分开做。

## 08.5 框架对比：什么时候该上 LangChain / LangGraph

先给结论：**先手写过一遍，再考虑框架。** 你前面亲手写的消息管理、工具分发、循环、trace，就是 LangChain / LangGraph 这些框架在内部帮你做的事。你理解原理后，框架对你来说只是"把轮子标准化了"，而不是黑盒。

### 三者的定位

| 维度 | 自建（你前几章写的） | LangChain | LangGraph |
|---|---|---|---|
| 核心抽象 | 自己写 while 循环 | 链（Chain）+ 大量现成组件 | 图（Graph）+ 状态机 |
| 控制流 | 你完全掌控 | 偏"预定义路径"（工作流） | 支持"模型决定路径"（真 Agent） |
| 状态管理 | 自己管 | 弱，靠记忆组件 | 内建持久化状态 |
| 可观测性 | 自己加 trace | 有基础回调 | 内建 tracing |
| 上手成本 | 高（要懂原理） | 中 | 中高 |
| 灵活度 | 最高 | 中 | 高 |

一个关键的认知：**LangChain 和 LangGraph 不是一回事，别混用。**

- **LangChain** 更偏"工作流"：把 LLM 调用、提示词模板、检索、输出解析等封装成"链"，适合流程相对固定的场景（分类 → 翻译 → 输出这类确定性链路）。它的问题恰恰是"太能封装"——组件套组件，出 bug 时你很难看清内部。
- **LangGraph** 是专为 Agent 设计的：它把 Agent 建模成一张**有状态的图**，节点是"步骤"（调用模型、执行工具），边是"下一步去哪"，状态在节点间流转。这跟你在第 00 章看到的"Agent 循环"是同一个东西，只是它帮你把循环、状态、tracing 都内建了。

### 什么时候该用框架

一个务实的判断标准，按这个顺序问自己：

1. **先问：能不能不用 Agent？** 能画成确定性流程图的任务，用工作流（甚至纯代码）就够了，别上 Agent，更别上框架。
2. **要写 Agent，但逻辑简单**（一个循环 + 两三个工具）：**自建**。代码不过百行，你完全掌控，出问题看得清。上一整套框架反而是负担。
3. **逻辑复杂、要分支、要持久化、要多人协作**：**上 LangGraph**。当你的 Agent 开始有"多路径决策、中断恢复、人工审批节点、多 Agent 协作"时，手写状态机很快就失控，LangGraph 的图模型和持久化状态就值回票价了。
4. **只是想要现成组件**（比如现成的检索器、输出解析器）：可以**局部用 LangChain**，但别把它当 Agent 框架使。

记住一个反直觉但重要的结论：**框架的价值，是在你"已经知道该写什么"之后，帮你少写样板代码；而不是在你"不知道原理"的时候，替你遮住原理。** 顺序反了，框架就是黑盒，出了问题你只能对着报错干瞪眼。

> 一句话记住它：自建帮你懂原理，LangGraph 帮你管复杂状态机，LangChain 给你现成组件——先自建跑通再谈框架，顺序不能反。

## 08.6 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 状态是局部变量 | 程序退出就丢、断点续跑不了 | 状态困在函数作用域 | 提升成显式 `AgentState`，可序列化 |
| 状态里混入循环引用 | `TypeError: Converting circular structure to JSON` | `JSON.stringify` 遇循环引用 | 状态只放纯数据，不放运行时对象 |
| 出错只能靠猜 | 看不到模型/工具干了什么 | 没有 trace | 每个关键节点 `tracer.record` |
| 测试断言精确内容 | 测试随机通过/失败 | 模型输出是概率的 | 断言结构、边界，不测措辞 |
| 测试依赖真实模型 | 离线跑不了、不稳定 | 没隔离 LLM | 用 mock LLM 固定剧本 |
| 以为 Node 跑 .ts 就是类型检查 | `role: 'uesr'` 照样跑 | strip-types 只剥离不检查 | 用 `tsc --noEmit` 做类型检查 |
| 只靠类型不管运行时 | `Cannot read properties of undefined (reading 'push')` | 类型编译后已擦除 | 运行时反序列化必须校验 |
| 一上来就上框架 | 看不懂内部、出 bug 干瞪眼 | 没先懂原理 | 先自建跑通，再上 LangGraph |

---

## 08.7 本章小结

- **状态是"值"不是"变量"**：显式化、序列化、纯数据化，才谈得上持久化、恢复、测试。
- **可观测性靠 trace**：每一步记录"时间、步数、动作、输入输出"，出 bug 有据可查。
- **概率系统测结构和边界**：mock LLM 固定剧本，断言"字段/步骤/兜底"，不测措辞；快照测 trace 漂移。
- **TS 类型守编译期**：用类型约束消息、工具、循环返回值，把错误提前到写代码时。
- **类型管不了运行时**：类型编译后擦除，反序列化数据必须运行时校验，两者各管一段。
- **框架的顺序**：先自建懂原理，再按复杂度选 LangGraph（复杂状态机）或 LangChain（现成组件）。

## 08.8 动手练习

1. 下面的 `serialize` 为什么会在运行时抛 `TypeError: Converting circular structure to JSON`？怎么改？

   ```js
   const state = { messages: [] };
   state.self = state;          // 关键在这一行
   console.log(JSON.stringify(state));
   ```

   <details><summary>参考答案</summary>
   因为 `state.self = state` 制造了一个循环引用（对象指向自己），`JSON.stringify` 无法处理循环引用，所以抛 `TypeError: Converting circular structure to JSON`。改法：状态里只放纯数据，不要往里塞"指向状态自身（或任何运行时对象）"的引用——`messages`、`steps` 这类基本数据就够了。
   </details>

2. 你要测一个 Agent"会调用 `get_weather` 工具"，下面两种断言哪种对？为什么？

   ```js
   // 写法 A
   assert.equal(result.text, '北京今天晴，25℃');
   // 写法 B
   assert.ok(tracer.list().some((r) => r.kind === 'tool' && r.name === 'get_weather'));
   ```

   <details><summary>参考答案</summary>
   写法 B 对。写法 A 断言的是模型的"具体措辞"，而模型输出是概率的，换一次运行措辞可能就变，测试会随机失败。写法 B 断言的是"结构事实"——trace 里确实出现了一次 `get_weather` 的工具调用，这个不受措辞影响。测概率系统，锚点要放在结构和行为上，而不是文本内容上。
   </details>

3. Node 22 用 `node --experimental-strip-types demo.ts` 跑一段 `.ts`，能当作类型检查吗？为什么？

   <details><summary>参考答案</summary>
   不能。`--experimental-strip-types` 只做"剥离类型注解"，不做类型检查——你把 `role: 'uesr'` 这种拼错写进去，它照样运行、不报错。真正的类型检查要靠编译器，比如 `tsc --noEmit`。一个是"让 .ts 能跑"，一个是"让类型约束生效"，两回事。
   </details>

4. 一个 Agent 现在只是"一个循环 + 两个工具"，同事建议直接上 LangGraph。你会怎么做？理由是什么？

   <details><summary>参考答案</summary>
   先自建跑通，暂不上 LangGraph。因为当前逻辑简单（一个循环 + 两三个工具），自建不过百来行，你完全掌控、出问题看得清；上框架反而引入黑盒和额外心智负担。等到 Agent 出现多路径决策、状态持久化、中断恢复、人工审批、多 Agent 协作这些复杂需求时，再迁到 LangGraph，那时框架的价值（状态机 + 持久化 + tracing）才真正体现。顺序是：先懂原理，再谈框架。
   </details>
