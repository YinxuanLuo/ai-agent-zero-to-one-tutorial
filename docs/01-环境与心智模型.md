# 第 01 章 · 环境与心智模型

> 上一章给你灌了一堆哲学，这一章把它落成能跑的代码。
> 本章你需要记住的就一件事：**Agent 骨子里就是一个 `messages` 数组 + 一个 `for` 循环 + 一个"要不要调工具"的 `if`，其余全是包装。**

---

## 01.1 环境准备：你只需要一个 Node.js

结论先说：**本教程核心章节不需要 `npm install` 任何东西，只需要一个 Node.js 22。** 没有 Python 依赖、没有框架、没有 API key 也能把每一章的例子跑通。

为什么这么设计？因为 Agent 的"骨架"（消息管理、循环、工具分发）本质就是几个数组和几个函数，用不到任何第三方库。等你理解了骨架，再去看 LangChain、LangGraph，你会发现它们只是把你手写的这些轮子"标准化"了。**先不用框架，你才看得见框架在替你做什么。**

验证一下你的环境：

```bash
node -v
```

```text
v22.22.2
```

本教程实测版本是 22.22.2。只要大版本是 22 就够用（我们用到的特性 22 里都有，别用 24 才有的新 API）。

关于"模型从哪来"：真实项目里你要调 OpenAI 或国产模型的 API，但那样离线跑不了、还得花钱。所以本教程用一个**可插拔 mock**——所有示例的模型调用都走同一个 `llm` 接口，默认返回预置结果。等你哪天真要接真实模型，只把 mock 换成一个 `fetch` 调用，循环代码一行不用改。这个接口长这样：

```ts
import { createWeatherMockLlm } from './llm-mock.mjs';

const llm = createWeatherMockLlm();        // 离线 mock，免费、可重复
const response = await llm.invoke(messages); // 输入消息数组，输出 { text } 或 { toolCall }
```

> 一句话记住它：环境只有 Node.js 一件事；模型被抽象成一个 `llm.invoke(messages)` 接口，mock 和真实 API 可以随时互换。

## 01.2 四个零件：大脑、记忆、工具、循环

结论先说：**任何 Agent，拆到最底层，就是四个零件在协作。** 上一章 00.4 引用的 Lilian Weng 定义里说 Agent = LLM + 规划 + 记忆 + 工具，这里的"规划"落到工程里，就是那个**循环**——循环让模型能"想一步、动一步"，重复到任务完成。

先看一张总表，每列都问"代码里它到底是个啥"：

| 零件 | 是什么 | 在代码里长什么样 | 谁在管它 |
|---|---|---|---|
| **大脑** | 做决策的模型 | 一个 `llm` 接口，`invoke(messages)` 返回文字或工具调用 | 外部 API（或 mock） |
| **记忆** | 所有跨轮次的状态 | 一个普通数组 `messages`，元素是 `{ role, content }` | 你的代码 |
| **工具** | 真正干活的函数 | `tools = { get_weather: () => '...' }` 一个对象 | 你的代码 |
| **循环** | 把上面三个串起来 | 一个 `for`/`while` + 一个 `if` | 你的代码 |

注意一个关键事实：**四个零件里，只有"大脑"不是你的代码，另外三个全是你在写。** 这句话很重要——它意味着 Agent 的工程质量，主要取决于你写的 `messages`、`tools`、循环这三样写得清不清楚，而不是模型本身有多强。

对应到代码骨架，就是下面这四块（先看个形状，01.3 逐行讲）：

```ts
// 记忆：一个数组
const messages = [
  { role: 'system', content: '你是天气助手。' },
  { role: 'user', content: '查北京天气。' },
];

// 工具：一个对象，键是工具名，值是函数
const tools = {
  get_weather: ({ city }) => `${city}：小雨，22℃`,
};

// 大脑：一个接口（mock 或真实 API）
const llm = createWeatherMockLlm();

// 循环：串起前面三个
for (let i = 0; i < 10; i++) {
  const r = await llm.invoke(messages);
  if (r.toolCall) {
    messages.push({ role: 'tool', content: tools[r.toolCall.name](r.toolCall.args) });
    continue;
  }
  console.log(r.text);
  break;
}
```

> 一句话记住它：Agent 四件套里，"大脑"是别人的，"记忆、工具、循环"全是你的代码；你的水平就体现在这三样上。

## 01.3 最小 Agent 循环，逐行讲透

结论先说：**整个 Agent 的核心，就是下面这 20 来行。** 看懂它，你就看懂了所有 Agent 框架的底层。`examples/01-最小Agent.mjs` 是它的完整打印版，可以自己跑一遍看每一步。

```ts
import { createWeatherMockLlm } from './llm-mock.mjs';

const tools = {
  get_weather: ({ city }) => `${city}：小雨，22℃`,   // ① 工具：真正干活的代码
};

const llm = createWeatherMockLlm();                    // ② 大脑：离线 mock

const messages = [                                      // ③ 记忆：初始只有两条
  { role: 'system', content: '你是天气助手，问天气先调 get_weather 工具。' },
  { role: 'user', content: '帮我查一下北京天气，下雨提醒我带伞。' },
];

const MAX_TURNS = 10;                                   // ④ 防死循环的硬上限

for (let turn = 0; turn < MAX_TURNS; turn++) {          // ⑤ 循环：最多转 10 轮
  const response = await llm.invoke(messages);          // ⑥ 把记忆整段交给模型

  if (response.toolCall) {                              // ⑦ 模型想"调工具"？
    messages.push({ role: 'assistant', content: '要调工具' });
    const result = tools[response.toolCall.name](response.toolCall.args); // ⑧ 代码真正执行
    messages.push({ role: 'tool', content: result });   // ⑨ 结果回填记忆
    continue;                                           // ⑩ 回到循环顶部，再问模型
  }

  messages.push({ role: 'assistant', content: response.text });
  console.log(response.text);                           // ⑪ 模型给了最终回答
  break;                                                // ⑫ 任务完成，退出
}
```

逐行拆开讲：

- **①②③ 是"零件初始化"**：工具、大脑、记忆各就各位。注意 ③ 里初始 `messages` 已经有两条消息——一条 `system` 定规矩，一条 `user` 提出问题。**模型不是凭空开始干的，它需要一个起点。**

- **⑥ `llm.invoke(messages)` 是唯一跟模型打交道的地方**。你把整个数组塞进去，模型返回一个对象。这个对象只有两种可能：`{ text }`（"我直接回答"）或 `{ toolCall }`（"我要调工具"）。**模型永远只输出"文字"或"调工具的意愿"，它不执行任何东西。**

- **⑦ 是整个循环的分叉点**，也是 Agent 和普通程序最不一样的地方。普通程序的流程是写死的（先 A 后 B），而这里**下一轮干什么，取决于模型这次返回了什么**。这就是 00 章说的"模型自主决定流程"。

- **⑧ 是全程序唯一"真正干活"的一行**。`tools[...]` 从工具表里取出函数，调用它，拿到真实结果。模型从头到尾没碰过这个结果的计算过程——**动手的是你的代码，模型只是"点菜"。**

- **⑨⑩ 是 Agent 的记忆机制**：工具结果必须作为一条 `tool` 消息塞回 `messages`，然后 `continue` 回到循环顶部。下一轮 ⑥ 再把包含结果的整段记忆交给模型，模型这才"看到"工具干了啥，从而给出最终回答。**如果忘了 ⑨ 这一步，模型永远不知道工具返回了什么。**

- **⑪⑫ 是正常出口**：模型给了文字回答，任务结束，`break` 退出。

你此刻可能注意到 ⑧ 有个隐患：如果模型要求调一个不存在的工具，`tools[response.toolCall.name]` 是 `undefined`，直接 `undefined(args)` 会报错：

```text
TypeError: tools[name] is not a function
```

所以完整示例 `examples/01-最小Agent.mjs` 里给 ⑧ 加了一个三元兜底：工具不存在时返回 `未知工具：xxx`，而不是让程序崩掉。**这就是 00 章"为不确定性做设计"的第一个具体体现——模型的输出你永远不能全信，必须先校验再执行。**

> 一句话记住它：Agent 循环 = 把记忆交给模型 → 判断返回的是"文字"还是"工具调用" → 工具调用就执行并回填、继续循环，文字就结束。

## 01.4 messages 数组：记忆其实是个普通数组

结论先说：**Agent 的"记忆"没有任何魔法，就是一个普通的 JavaScript 数组，每个元素是一条消息对象。** 模型每次调用都是无状态的，它一个字都不记；所谓"记得上一轮"，全靠你的代码把这个数组原样塞回去。

每条消息只有两个字段：

```ts
{ role: 'system', content: '你是天气助手。' }
```

`role` 决定"这句话是谁说的、模型该怎么对待它"，`content` 就是内容。`role` 一共四种，本教程全用这一套：

| role | 谁说的 | 什么时候出现 | 模型怎么看待 |
|---|---|---|---|
| `system` | 你（开发者） | 对话最开始，只放一次 | 最高优先级指令，持续生效 |
| `user` | 用户 | 用户每次提问 | 要回应的对象 |
| `assistant` | 模型 | 模型每次的回复 | 自己说过的话（历史） |
| `tool` | 工具 | 工具执行后 | 工具返回的事实数据 |

四种 role 的细节和写法，第 02 章会展开。这里你只要先建立一个大直觉：**`messages` 就是"发给模型的完整上下文"，模型看到的全部世界，就是这个数组转成的文本。**

看一个真实的完整数组（跑 `examples/01-最小Agent.mjs` 结束时打印的那 5 条）：

```text
[system]   你是天气助手。用户问天气时，先调用 get_weather 工具拿到结果再回答。
[user]     帮我查一下北京天气，要是下雨提醒我带伞。
[assistant] [决定调用工具 get_weather]
[tool]     北京：小雨，22℃
[assistant] 根据查询结果：北京：小雨，22℃。提醒你出门带伞。
```

注意两点：

1. **`assistant` 出现了两次**——一次是模型"决定调工具"，一次是模型"最终回答"。所以一条 `assistant` 消息，内容可以是"一段话"，也可以是"我要调工具"这个意愿。真实 API 里，后者会用结构化字段（`tool_calls`）表示，而不是塞进 `content`。本教程的 mock 把它简化了。

2. **`tool` 消息是"代码回填"的，不是模型说的**。它紧跟在某条 assistant（调工具）之后，内容是工具函数的返回值。模型下一轮就是靠读到这条 `tool` 消息，才知道工具结果。

这个数组有个最常犯的错——**忘了把它传给模型**。如果你写 `await llm.invoke()`（漏传参数），会直接报：

```text
TypeError: Cannot read properties of undefined (reading 'length')
```

因为 mock（以及真实 API）要读 `messages.length` 来取最后一条消息。**模型必须有一个输入数组，这是硬约束，不是可选项。**

> 一句话记住它：记忆就是一个 `messages` 数组；模型无状态，它记得的一切，都是你每次把这个数组重新喂给它的结果。

## 01.5 system prompt：给模型定的规矩

结论先说：**`system` 消息是"写在对话最前面的规则"，它不参与对话，但全程约束模型的行为。** 你用一句话告诉模型"你是谁、该干什么、不能干什么"，模型会一直遵守。

为什么需要它？因为模型是个"什么都懂但不知道这次该干嘛"的通用脑子。同一个模型，不加 `system` 它可能跟你闲聊，加了 `system: '你是客服，用简短专业的话术回答'` 它立刻就切换成客服。**`system` 就是给这个通用脑子套上的"工作身份"。**

对比一下效果（`examples/02-提示词与消息.mjs` 的 Part 2 有可运行版本）：

```ts
// 有 system：模型知道自己要翻译
const withSystem = [
  { role: 'system', content: '你是翻译助手，只输出译文，不解释。' },
  { role: 'user', content: '把"你好"翻译成英文。' },
];

// 没有 system：模型不知道你想干嘛，只能靠猜
const withoutSystem = [
  { role: 'user', content: '把"你好"翻译成英文。' },
];
```

```text
[有 system prompt] 译文：Hello.
[无 system prompt] 我不确定你想让我做什么，请补充指令。
```

`system` 放在 `messages` 的**最前面**，并且通常整个对话只放一次（除非你要中途切换身份）。它的位置很重要：模型是顺序读消息的，最前面就是"最高优先级"。

`system` 里一般写三样东西，第 02 章会展开教你怎么写：

```ts
const systemPrompt = [
  '你是一个天气助手。',                          // ① 角色：你是谁
  '用户问天气时，必须先调用 get_weather 工具。',   // ② 规则：该怎么做
  '用一句话回答，不要输出多余的解释。',            // ③ 约束：输出成什么样
].join('\n');
```

> 一句话记住它：`system` 是对话开头的"身份 + 规则 + 约束"，放在最前面、全程生效，它决定模型"这次以什么身份干活"。

## 01.6 agent loop 的完整生命周期

结论先说：**一次 Agent 任务的完整生命周期只有三个阶段——初始化、循环、终止。** 你已经看过循环的内部，这一节把"从开始到结束"的完整过程串起来，并说清楚每个阶段可能出什么岔子。

用状态图看（`→` 表示"下一步"）：

```text
初始化 → [循环] → 终止
          ↑  ↓
          └──┘
  循环内部：
    调模型 → 判断输出
              ├─ 是文字 → 终止（正常出口）
              └─ 是工具调用 → 执行工具 → 回填结果 → 回到"调模型"
```

三个阶段拆开讲：

**阶段一：初始化。** 你的代码要准备好三样东西：`messages`（至少一条 `system` + 一条 `user`）、`tools`（工具表）、`llm`（模型接口）。**如果 `messages` 里只有 `user` 没有 `system`，模型也能跑，但行为不可控**——它没有身份约束，只能靠猜。

**阶段二：循环。** 这是 Agent 的"工作状态"。每一轮做四件事：调模型、判断输出、执行工具、回填结果。这个阶段可能出的岔子最多：

- **死循环**：模型一直要求调同一个工具，永远给不出最终回答。所以必须有 `MAX_TURNS` 上限（01.3 里的 ④），超了强制退出。
- **空转**：模型直接回了文字，但内容没完成任务（比如它说"我查不了"）。循环会正常退出，但任务失败了——这是"校验"要管的，第 07 章讲。
- **越滚越长的上下文**：每调一次工具，`messages` 就多两条，数组越来越长，最终超出模型的上下文窗口。第 04 章讲怎么压缩。

**阶段三：终止。** 只有两种正常结束：模型给了最终回答（`break`），或者达到 `MAX_TURNS` 上限（`for` 自然结束）。注意第二种其实是"异常终止"——它意味着模型没在限定轮次内完成任务。**真实工程里，这两种终止要区别对待：前者是成功，后者要么重试、要么降级给人工。**

把三个阶段写成带生命周期的完整代码（这是 `examples/01-最小Agent.mjs` 的骨架，去掉了打印）：

```ts
// 阶段一：初始化
const messages = [
  { role: 'system', content: '你是天气助手。' },
  { role: 'user', content: '查北京天气。' },
];
const tools = { get_weather: ({ city }) => `${city}：小雨，22℃` };
const llm = createWeatherMockLlm();
const MAX_TURNS = 10;

// 阶段二：循环
for (let turn = 0; turn < MAX_TURNS; turn++) {
  const response = await llm.invoke(messages);
  if (response.toolCall) {
    messages.push({ role: 'tool', content: tools[response.toolCall.name](response.toolCall.args) });
    continue;
  }
  console.log(response.text); // 阶段三（成功）
  break;
}
// 走到这里且没 break，就是达到 MAX_TURNS 的"异常终止"
```

> 一句话记住它：Agent 生命周期 = 初始化（备好记忆/工具/模型）→ 循环（调模型/判断/执行/回填）→ 终止（模型回答或超限），其中"超限终止"是异常，要单独处理。

## 01.7 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 漏传 `messages` | `TypeError: Cannot read properties of undefined (reading 'length')` | `llm.invoke()` 没传参数，模型读不到消息数组 | 永远 `invoke(messages)`，传整个数组 |
| 调未注册的工具 | `TypeError: tools[name] is not a function` | 模型要求调一个 `tools` 里不存在的函数 | 执行前先判断 `tools[name]` 是否存在，不存在就返回错误信息 |
| 忘回填工具结果 | 模型反复调同一个工具、答非所问 | 工具结果没 `push` 成 `tool` 消息，模型看不见结果 | 每次执行工具后必须 `messages.push({ role: 'tool', content: result })` |
| 死循环 | 程序一直跑不停、工具被反复调用 | 模型始终给不出最终回答 | 加 `MAX_TURNS` 上限，超限强制退出并告警 |
| 文件存成 `.js` | `Warning: Module type ... not specified` | ESM 的 `import` 写进了无 `"type": "module"` 的 `.js` | 统一用 `.mjs` 后缀，一劳永逸 |
| 初始漏 `system` | 模型回答风格飘忽不定 | 没有身份约束，模型只能猜你要干嘛 | `messages` 第一条就放 `system` |

> 一句话记住它：大多数坑都出在"消息数组没喂对"和"工具结果没回填"这两件事上——它们是 Agent 的地基。

## 01.8 本章小结

- Agent 四件套 = **大脑（llm）+ 记忆（messages）+ 工具（tools）+ 循环（for + if）**，其中后三个都是你的代码。
- 环境只有 **Node.js 22** 一件事，核心章节零第三方依赖。
- 模型被抽象成 **`llm.invoke(messages)`**，mock 和真实 API 可互换。
- 循环的骨架是：**调模型 → 判断返回（文字/工具调用）→ 执行工具并回填 → 继续循环或结束**。
- `messages` 是普通数组，元素 `{ role, content }`；**模型无状态，记忆全靠你每次重喂**。
- 四种 role：`system`（规则）、`user`（提问）、`assistant`（模型回复）、`tool`（工具结果）。
- `system` 放在最前面，写"身份 + 规则 + 约束"，全程生效。
- 生命周期 = **初始化 → 循环 → 终止**；"超限终止"是异常，要单独处理。

## 01.9 动手练习

1. 下面这段代码哪里错了？会导致什么结果？

   ```ts
   const messages = [
     { role: 'user', content: '查北京天气' },
   ];
   const r = await llm.invoke(messages);   // 假设返回 toolCall
   if (r.toolCall) {
     const result = tools[r.toolCall.name](r.toolCall.args);
     // 忘了把 result push 回 messages
     const r2 = await llm.invoke(messages); // 再次调用
   }
   ```

   <details><summary>参考答案</summary>
   工具结果 `result` 没有 `push` 成 `tool` 消息。第二次 `invoke(messages)` 时，`messages` 里还是原来的内容，模型根本不知道工具执行过、结果是什么，于是很可能再次要求调用同一个工具，陷入死循环。
   </details>

2. 模型要求调用一个工具 `get_stock`，但你的 `tools` 里只有 `get_weather`。直接写 `tools[response.toolCall.name](args)` 会报什么错？怎么防？

   <details><summary>参考答案</summary>
   会报 `TypeError: tools[name] is not a function`，因为 `tools['get_stock']` 是 `undefined`，对它调用就崩。防法：执行前判断 `if (tools[name])`，不存在就返回一条 `tool` 消息告知"未知工具"，让模型据此调整，而不是让程序崩溃。
   </details>

3. 为什么 `messages` 数组的第一条几乎总是 `system`，而不是 `user`？把它放最后行不行？

   <details><summary>参考答案</summary>
   因为模型是顺序读消息的，最前面的信息权重最高。`system` 是"身份 + 规则 + 约束"，必须让模型先入为主地看到，才会全程遵守。放最后不仅权重低，还容易被前面长长的对话淹没，甚至被模型当作普通历史忽略掉。
   </details>
