# 第 02 章 · 提示词与消息结构

> 上一章你搭起了 Agent 的骨架，这一章解决一个更基础的问题：**怎么跟模型"说话"，它才听得懂、答得对。**
> 本章你需要记住的就一件事：**模型只看得见你塞给它的那一串消息，所以"写好提示词"= 把这串消息的每条 role、顺序、措辞都安排对。**

---

## 02.1 模型看到的不是一句话，是一串消息

结论先说：**你以为你在"写一段提示词"，实际上你在构造一个消息数组，模型按顺序、逐条地把这个数组读完。** 没有"一句 prompt"这回事，只有"一串 message"。

这个认知很重要，因为它决定了你后面所有技巧的落脚点：改提示词，本质是**改这个数组里某些消息的内容、角色或顺序**。用 `examples/02-提示词与消息.mjs` 的 Part 1 看一个完整例子（已真实运行）：

```ts
import { createMockLlm } from './llm-mock.mjs';

const messages = [];
messages.push({ role: 'system', content: '你是翻译助手，必要时调用 lookup 工具查词。' });
messages.push({ role: 'user', content: '把"你好"翻译成英文。' });

const r1 = await llm.invoke(messages);   // 模型回答 Hello.
messages.push({ role: 'assistant', content: r1.text });
```

```text
[system   ] 你是翻译助手，必要时调用 lookup 工具查词。
[user     ] 把"你好"翻译成英文。
[assistant] Hello.
```

模型读这个数组时，它看到的不是"三个孤立字段"，而是一段**按顺序拼接起来的对话剧本**：先被告知身份，再看到用户提问，再看到自己刚才的回答。**顺序本身就是信息**——谁先谁后，模型会据此理解"这是规则、这是问题、这是历史"。

一个关键推论：**模型不会"跳着读"，也不会有选择地忽略某条消息。** 数组里的每一条都会进入它的上下文窗口，消耗一份 token（字数）。所以多塞一条废话，就多花一份钱、多占一份窗口。这就是 00 章说的"上下文窗口是硬约束"在消息层面的具体体现。

> 一句话记住它：没有"一句 prompt"，只有"一串按顺序排列的消息"；你写的每个字都在消耗上下文窗口。

## 02.2 四种 role 的语义与时机

结论先说：**四种 role 各有唯一职责、唯一出现时机，混用或拼错不会报错，只会让模型"会错意"。** 下面这张表你要背下来：

| role | 语义（模型怎么看） | 出现的时机 | 内容举例 |
|---|---|---|---|
| `system` | 最高优先级指令，不是对话内容 | 对话最开始，通常只一次 | 身份、规则、输出约束 |
| `user` | 要回应的对象 | 每次用户/外部输入 | 问题、指令、数据 |
| `assistant` | 模型自己说过的话 | 每次模型回复之后 | 回答，或"我要调工具"的意愿 |
| `tool` | 工具返回的事实 | 每次工具执行之后 | 函数返回值（字符串） |

四种 role 里，前三种好理解，**`tool` 是最容易被搞错的**。它的两条铁律：

1. **`tool` 消息是代码回填的，不是模型生成的。** 模型永远"只说不动手"，工具结果必须由你的代码 `push` 进数组。你在 01.3 已经见过这一步。

2. **`tool` 消息必须紧跟在那条"要调工具"的 `assistant` 之后。** 模型要顺着"助手说调工具 → 工具返回了结果"这个因果链，才能正确理解结果。看完整时序：

```text
[user     ] 那"再见"呢？
[assistant] [调用工具 lookup]        ← 模型表达"我要调工具"
[tool     ] lookup("再见") = Goodbye ← 代码回填的工具结果
[assistant] Goodbye.                 ← 模型基于工具结果作答
```

如果中间插一条别的 `user` 消息，模型就会困惑"这个工具结果是回答哪个问题的"。

**还有一个比报错更坑的情况：role 拼错会"静默失效"。** mock 不做校验，所以你写 `role: 'System'`（大写）或 `role: '人类'`，程序照跑不误，但模型根本认不出这是 `system`——你的规则被当成普通对话忽略了。这不是报错，是**静默的行为漂移**，比报错更难排查：

```ts
// 手滑写错了 role，程序不报错，但 system prompt 失效了
const messages = [
  { role: 'System', content: '你是翻译助手，只输出译文。' }, // 大写 S，模型不认
  { role: 'user', content: '把"你好"翻译成英文。' },
];
```

（真实 API 层会直接拒绝这种请求，报 `400 invalid_request_error`，但 mock 不会——它省掉了校验，代价是这类错你得自己盯。）

> 一句话记住它：四种 role 各司其职；`tool` 必须由代码回填且紧跟对应 `assistant`；role 拼错不会报错，只会让规则静默失效。

## 02.3 system prompt 怎么写：先给模型一个"身份"

结论先说：**`system` 是写给模型的"身份 + 规则 + 约束"三段式，放在数组最前面，全程生效。** 它的存在是为了解决一个根本问题：模型是个"什么都懂、但不知道这次该干嘛"的通用脑子，你必须先告诉它"这次你是谁"。

为什么需要身份？因为同一个模型，你让它扮演翻译、客服、代码审查，它会给出完全不同的回答。**没有 `system`，模型只能靠 `user` 消息去猜你的意图，而猜就意味着不可控。** 这是"为什么 prompt 要这样写"的第一动机：**消除身份歧义**。

一个合格的 `system`，三句话就够：

```ts
const system = [
  '你是一个专业的天气助手。',                        // ① 角色：你是谁
  '用户问天气时，必须先调用 get_weather 工具，再基于结果回答。', // ② 规则：该怎么做
  '回答控制在 50 字以内，不要输出多余解释。',          // ③ 约束：输出成什么样
].join('\n');
```

对比一个"不合格"的 `system`，你就知道差距在哪：

```ts
// 坏：只给了角色，没给规则和约束
'你是一个助手。'          // 模型不知道要调工具，也不知道怎么答

// 坏：规则含糊
'帮用户解决问题。'         // "解决"太宽泛，模型无从下手
```

设计动机就一句话：**`system` 要写到"让模型没有第二种解释"的程度。** 角色告诉它立场，规则告诉它动作，约束告诉它边界。三者缺一，模型都会用"它自己的默认理解"来补，而默认理解大概率不是你想要的。

`system` 应该只在数组开头出现一次。中途改 `system`（比如任务到一半换身份）是很强的信号，会打断模型，一般只在"角色切换"这种刻意场景才用。

> 一句话记住它：`system` = 身份 + 规则 + 约束，写到"没有第二种解释"为止；它解决的是"模型不知道这次该以什么身份、按什么规矩干活"的问题。

## 02.4 提示词工程三条原则（以及背后的动机）

结论先说：**提示词工程没有玄学，就三条原则——指令清晰、给示例（few-shot）、约束输出格式，三条背后是同一个动机：消除歧义。** 模型是概率机器，它不会"读心"，你留的每一个含糊之处，它都会随机填一个答案。这一节每条都讲"为什么"，而不是罗列技巧。

### 原则一：指令清晰 —— 把"要什么、不要什么"都写死

模型最怕的不是复杂，是**含糊**。看这个例子：

```ts
// 含糊：模型不知道你要"只翻译"还是"翻译+解释"
{ role: 'user', content: '处理一下这句话：你好' }

// 清晰：要什么、不要什么、格式，全都写死
{ role: 'user', content: '把"你好"翻译成英文。只输出译文本身，不要解释、不要原文、不要引号。' }
```

为什么含糊会翻车？因为"处理一下"有几十种理解（翻译、改写、摘要、润色……），模型只能挑一种，而它挑的未必是你想的。**你写提示词的每一秒，都在跟"模型的随机性"搏斗；写得越具体，随机性越小。**

### 原则二：few-shot —— 给示例，比描述更有效

这条最反直觉：**与其长篇描述"你要输出什么格式"，不如直接给一个输入输出的示例。** 因为模型本质是个"模仿者"，示例直接给了它一个可复制的模板，它照葫芦画瓢比照着抽象描述做，准确率高得多。

`examples/02-提示词与消息.mjs` 的 Part 3 有可运行对比：

```ts
// 只说"输出 JSON"，模型可能还是给你自然语言
{ role: 'system', content: '你是翻译助手，请输出 JSON。' },
{ role: 'user', content: '把"再见"翻译成英文，输出 JSON。' },

// 给了示例，模型就能照着格式输出
{ role: 'system', content: '你是翻译助手，输出 JSON，格式如下。' },
{ role: 'user', content: '把"你好"翻译成英文。' },
{ role: 'assistant', content: '{"原句": "你好", "译文": "Hello"}' }, // ← 这就是 few-shot 示例
{ role: 'user', content: '把"再见"翻译成英文。' },
```

```text
[无示例] 好的，再见翻译成英文是 Goodbye。          ← 没遵守 JSON
[有示例] {"原句": "再见", "译文": "Goodbye"}        ← 照示例格式输出
```

设计动机：**模型的训练方式就是"看大量输入→输出对"学出来的，few-shot 等于现场再教它一次。** 示例就是 prompt 里"信息密度最高"的部分——一个例子胜过十句描述。代价是示例也占 token，所以只给 1~3 个最能代表目标的例子，不要堆。

### 原则三：约束输出格式 —— 让输出能被代码消费

如果你的 Agent 要把模型输出喂给下一个代码环节（存数据库、调下一个工具），那输出必须是**结构化、可解析**的。自然语言"好的，翻译成英文是 Goodbye"没法让代码可靠地提取结果，但 `{"原句":"再见","译文":"Goodbye"}` 一个 `JSON.parse` 就搞定。

```ts
// 约束成 JSON，代码才能消费
const prompt = '输出严格的 JSON，格式：{"原句": string, "译文": string}，不要输出 JSON 以外的任何内容。';
const raw = (await llm.invoke(messages)).text;
const parsed = JSON.parse(raw);   // 能 parse 才能进下一步
```

设计动机：**模型默认输出"给人看的自然语言"，而工程需要"给机器看的结构"。** 约束格式，本质是把你和模型之间的接口从"文本"升级成"数据"。第 06 章会专门讲怎么可靠地拿到结构化输出。

> 一句话记住它：三条原则——指令清晰、few-shot、约束格式——都在做同一件事：把模型的随机性压到最低，让它"没有第二种答法"。

## 02.5 上下文如何组织：顺序、取舍、长度

结论先说：**上下文的组织，本质是在有限的窗口里，按"优先级"摆放信息，并果断舍弃没用的。** 模型是顺序读的，所以"放前面 = 更重要"；窗口有上限，所以"多塞 = 更贵更笨"。

先讲**顺序**。`messages` 的默认顺序就是时间顺序，但你可以、也应该主动调整"什么放最前面"：

```ts
const messages = [
  { role: 'system', content: '...' },   // 第 1：规则，最高优先级，永远最前
  // （可选）把关键约束、示例也往前放
  { role: 'user', content: '...' },     // 第 2：当前要解决的任务
  // 历史对话、工具结果，按时间顺序往后排
];
```

为什么顺序重要？两条经验：一是 **`system` 必须最前**（02.3 讲过）；二是 **越靠后的消息对模型"此刻"的影响越大**——模型通常最"关心"最后一条（它要回应这个）。所以当前任务放最后，历史放前面，是自然又合理的。

再讲**取舍**。这是 Agent 工程最现实的问题：上下文窗口有上限（几万到几百万 token 不等，但永远有限），而 Agent 每轮循环都在往 `messages` 里加东西。你不做取舍，数组就会滚雪球，直到：

- 超出窗口，最前面的 `system` 和早期历史被"挤掉"，模型开始失忆、忘规则。
- 每次调用把整段历史都发给模型，token 费用线性上涨。

取舍策略很简单：**只留"完成任务所需的最少信息"。** 工具返回一个 5000 行的文件？不要整个塞进去，先提取关键部分。历史对话太长？只保留最近 N 轮。这些是第 04 章"记忆与上下文管理"的主线，这里先建立这个意识。

一个"长度"的直觉：同一条信息，你写两遍，就是两倍的 token。**提示词要"惜字如金"——每个字要么在消除歧义，要么在传递必要信息，否则就该删。**

> 一句话记住它：上下文 = 按优先级排顺序（规则最前、任务最后）+ 只留必要信息（超窗就失忆、多塞就多花钱）。

## 02.6 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| role 拼错 | 程序不报错，但规则失效、回答风格飘 | 大小写/中文 role，模型不认，静默忽略 | role 只写 `system`/`user`/`assistant`/`tool` 四选一 |
| `tool` 消息位置错 | 模型答非所问、搞混工具结果 | `tool` 没紧跟对应 `assistant`，因果链断了 | 每次工具执行后立即 `push` `tool` 消息 |
| `tool` 由模型生成 | 模型"自己编"工具结果 | 误以为模型能执行工具 | 工具结果只能由代码执行后回填 |
| `system` 太含糊 | 模型行为不可控 | 只写了"你是助手"，没写规则和约束 | 写全"身份 + 规则 + 约束"三段 |
| 只描述格式不给示例 | 模型输出格式不对 | 抽象描述不如示例直观 | few-shot 给 1~3 个输入输出示例 |
| 把大文件整个塞进上下文 | 越跑越贵、模型开始忘事 | 没做取舍，窗口被撑爆 | 提取关键信息，只留最少必要内容 |
| 提示词冗余 | 花冤枉钱、还干扰模型 | 重复、废话太多 | 每个字要么消除歧义、要么传信息，否则删 |

> 一句话记住它：提示词相关的坑，一半是"role 和消息顺序没排对"，一半是"该说的没说清、不该说的说了一堆"。

## 02.7 本章小结

- 提示词的真相是**一个按顺序排列的消息数组**，模型逐条读完，每条都占窗口。
- 四种 role：`system`（规则）、`user`（提问）、`assistant`（模型回复）、`tool`（工具结果）。
- **`tool` 必须代码回填、紧跟对应 `assistant`**，模型自己不会、也不能生成它。
- role 拼错**不报错、静默失效**，比报错更难查。
- `system` = 身份 + 规则 + 约束，写到"没有第二种解释"。
- 提示词三条原则：**指令清晰、few-shot、约束输出格式**，共同动机是消除歧义、压住随机性。
- few-shot 的示例是 prompt 里信息密度最高的部分，**一个例子胜过十句描述**。
- 上下文组织 = 按优先级排顺序 + 只留必要信息，**超窗就失忆、多塞就多花钱**。

1. 下面这段代码的 `system` 写得有问题，请指出并改写：

   ```ts
   const messages = [
     { role: 'system', content: '你是一个助手。' },
     { role: 'user', content: '查一下北京天气。' },
   ];
   ```

   <details><summary>参考答案</summary>
   问题：只有"角色"没有"规则"和"约束"，模型不知道要调工具、不知道输出什么格式，行为不可控。改写示例：`你是天气助手。用户问天气时必须先调用 get_weather 工具拿到结果再回答，回答控制在 50 字以内。`
   </details>

2. 模型要求调用 `get_weather`，你的工具执行返回了结果，但下一轮模型却"像没看到结果一样"又要求调一次。最可能的原因是什么？

   <details><summary>参考答案</summary>
   工具结果没有作为 `role: 'tool'` 的消息 `push` 回 `messages`（或者 push 成了错误的 role）。模型每轮只看得见你传给它的数组，结果不在数组里，它就等于没看到。正确做法：执行后立刻 `messages.push({ role: 'tool', content: result })`。
   </details>

3. 你要让模型把一段中文摘要输出成 JSON，写了 "请输出 JSON"，结果它经常给你自然语言。除了把指令写得更严，还有什么更有效的办法？

   <details><summary>参考答案</summary>
   用 few-shot：在 `messages` 里给 1~3 组"输入 → JSON 输出"的示例（`user` 问 + `assistant` 答出正确 JSON）。模型是模仿者，示例直接给了它要复制的模板，比抽象描述"输出 JSON"有效得多。
   </details>
