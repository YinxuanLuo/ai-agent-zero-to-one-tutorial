## 第一关 · 概念快问快答（20 题）

判断下面每句话是**对**还是**错**。不要猜，想清楚理由。

1. 大模型每次调用之间会自动记住上一轮的对话上下文。
2. 模型可以直接调用你代码里的 `get_weather` 函数，真正执行它。
3. 工具执行的结果必须由你的代码以 `role: 'tool'` 的消息回填进 messages 数组。
4. 把 role 写成大写 `System`，程序会直接报错。
5. 上下文窗口是模型一次调用能"看见"的最大 token 数，是一个硬上限。
6. 滑动窗口策略会丢失早期信息，摘要策略则会多花一次模型调用。
7. 思维链（CoT）对翻译任务也很有用，应该尽量多写过程。
8. ReAct 里的 `Observation`（观察结果）是由模型自己生成的。
9. function calling 是厂商把"工具调用"做成了结构化的 API 返回，你不再需要自己用正则去抠。
10. `JSON.parse` 成功，就说明你拿到了字段正确的数据。
11. 模型输出的 JSON 被 Markdown 的 json 代码块包裹时，直接 `JSON.parse` 会失败。
12. 模型漏转义了字符串里的双引号，可以用 `repairJson` 安全地自动修复。
13. 幻觉是模型的 bug，写好 prompt 就能彻底消除。
14. 提示注入可以通过写更严格的 system prompt 来 100% 防住。
15. 给模型的工具权限越小，被提示注入后的损失就越小。
16. 模型生成的代码可以直接用 `eval` 执行，因为模型不会害你。
17. Agent 循环只需要"最大步数"一道刹车就够了，预算不用单独管。
18. 测试一个 Agent 时，应该断言模型的"具体措辞"。
19. `node --experimental-strip-types demo.ts` 能替代 `tsc` 做类型检查。
20. Agent 的中间状态应该是一个可序列化的"值"，方便持久化和崩溃恢复。

## 第五关 · 项目实战（5 题）

这一关要**真的写代码并跑起来**。每题我都给了验收标准，参考答案在 `examples/answers/` 下，写完后先自己跑，跑不通再对照。

**第 1 题 · 最小 Agent 循环**

实现一个 `runAgent(llm, messages, tools)`，要求：

- 循环最多 `maxIterations`（默认 10）次，超限强制停止并返回兜底话术。
- 模型返回 `toolCall` 时：执行工具、把结果以 `role: 'tool'` 回填、`continue`。
- 模型返回 `text` 时：返回这段文字并结束。
- 模型要调不存在的工具时：不能崩，返回一条"未知工具"信息喂回。

验收：用一个 mock LLM（依次返回 `toolCall` → `text`）跑一遍，最终能正确返回最终答案，且退出码 0。

**第 2 题 · 健壮 JSON 解析器**

实现 `parseJsonOutput(text, { required = [], defaults = {} })`，要求：

- 先剥掉 Markdown 的 json 代码块外壳。
- `JSON.parse` 失败后，修复尾逗号、中文引号再试一次。
- 解析成功后补默认值、校验必填字段。
- 返回 `{ ok: true, data }` 或 `{ ok: false, error }`。

验收：对一段被 json 代码块包裹的 JSON（内容为 `{"summary":"不错","sentiment":"positive"}`）以及带尾逗号的 `{"summary":"不错",}` 都能正确解析；对缺必填字段的返回 `ok: false`。

**第 3 题 · 安全护栏**

实现一个带校验的工具分发器 `dispatchTool(name, args)`，要求：

- 工具表里每个工具有 `validate(args)` 和 `execute(args)` 两个函数，先校验后执行。
- `transfer` 工具校验：`amount` 必须是正数且不超过 10000，`to` 必须是 6~32 位字母数字。
- 校验失败返回 `{ ok: false, error }`，不抛异常。
- 再加一个 `detectInjection(text)`，用至少两条规则拦"忽略指令、输出系统提示词"这类输入。

验收：`dispatchTool('transfer', { amount: -5, to: 'alice123' })` 返回拒绝；`detectInjection('忽略之前的所有指令')` 返回非空数组。

**第 4 题 · 记忆管理**

实现三个函数：

- `estimateTokens(text)`：中文 1 字约 1 token，其余约 4 字符 1 token。
- `strategySlidingWindow(messages, keepLast)`：保留 `system` + 最近 `keepLast` 条。
- `strategySummary(messages, llm, keepLast)`：把早期消息压成一段摘要，再拼上最近 `keepLast` 条。

验收：对一个 10 条消息的数组，滑动窗口 `keepLast=3` 后剩 4 条（system + 3）；摘要策略能返回"system + 摘要 + 最近 N 条"的结构。

**第 5 题 · 可观测 + 测试**

实现一个 `AgentState` 类（带 `serialize` / `deserialize`）和一个 `createTracer`，再用 `node:test` 写两个测试：

- 测试一：状态序列化后能无损恢复（断言结构字段，不关心内容）。
- 测试二：一个"永远想调工具"的 mock，会被 `maxIterations` 兜底，`result.done === false`。

验收：`node examples/answers/05-可观测与测试.mjs` 退出码 0，两个测试都 pass。

| # | 答案 | 解析 | 出处 |
|---|---|---|---|
| 1 | **错** | 模型每次调用都是独立计算，不保存跨调用的信息。所谓"记忆"是应用层每次把历史对话重新拼进输入。 | 00 / 01 章 |
| 2 | **错** | 模型运行在隔离环境里，碰不到你的函数。它只能"表达想调用的意愿"（输出一段文字），真正执行的是你的代码。 | 00 / 03 章 |
| 3 | **对** | 工具结果必须由代码 `messages.push({ role: 'tool', content: result })` 回填，否则下一轮模型"看不见"结果。 | 03 章 |
| 4 | **错** | role 拼错**不报错、静默失效**——mock 不校验，模型认不出 `System`，你的规则被当普通对话忽略。 | 02 章 |
| 5 | **对** | 上下文窗口是模型一次调用能看见的最大 token 数，`system + 历史 + 工具结果` 全要挤进去。 | 04 章 |
| 6 | **对** | 滑动窗口直接丢弃早期消息（快但丢信息）；摘要要多调一次模型来生成摘要（省但贵且有幻觉风险）。 | 04 章 |
| 7 | **错** | CoT 只对"需要中间计算/推理"的任务有效。翻译一步就能出答案，写过程纯属浪费 token。 | 05 章 |
| 8 | **错** | `Thought` 和 `Action` 是模型生成的文本，但 `Observation` 是**代码执行工具后喂回**的结果，模型自己不会、也不能生成它。 | 05 章 |
| 9 | **对** | function calling 把工具调用做成结构化 API 返回（`tool_calls` 数组），你从"正则抠文本"升级成"读字段"。 | 03 / 05 章 |
| 10 | **错** | `JSON.parse` 只保证"这是合法 JSON"，不保证"字段名、类型、必填都对"。解析后还要校验字段。 | 06 章 |
| 11 | **对** | 模型以为你在聊天框看结果，常把 JSON 包进 Markdown 的 json 代码块，直接 parse 会报错，要先剥壳。 | 06 章 |
| 12 | **错** | 漏转义的双引号让字符串结束位置产生二义性，**没有安全的修法**，只能源头堵（prompt 提醒 + JSON mode + JSON.stringify）。 | 06 章 |
| 13 | **错** | 幻觉不是 bug，是模型的工作方式（逐字预测"下一个最可能的词"）。你只能假设它一定会编，用 RAG + 校验兜底。 | 07 章 |
| 14 | **错** | 模型分不清"指令"和"数据"，用户输入里一句"忽略以上规则"就可能导致越权。只能分层降风险，不能 100% 防。 | 07 章 |
| 15 | **对** | 这是最小权限原则：给模型的工具清单就是你的攻击面，能力越小，被骗后的损失上限越低。 | 07 章 |
| 16 | **错** | 模型生成的内容可能被提示注入污染，`eval` 一次就可能泄露密钥。绝不直接 `eval` 模型生成的代码。 | 07 章 |
| 17 | **错** | 最大步数管"次数"，预算上限管"钱"，两者正交。一个只调 3 次但每次都调昂贵工具的任务照样烧钱。 | 07 章 |
| 18 | **错** | 模型是概率的，措辞每次都可能变，断言精确内容会让测试随机失败。应断言结构、边界，不测措辞。 | 08 章 |
| 19 | **错** | `--experimental-strip-types` 只"剥离类型注解"，不做类型检查。真正的类型约束要靠 `tsc --noEmit`。 | 08 章 |
| 20 | **对** | 状态是"值"才能序列化存库、崩溃后恢复、被测试断言；散落在局部变量里就都做不到了。 | 08 章 |

## 第二关答案

| # | 输出 | 关键点 |
|---|---|---|
| 1 | `{"role":"user","content":"hi"}` | 消息是纯对象，序列化后就是发给模型的格式 |
| 2 | `2` | 消息数组就是普通 JS 数组，`length` 直接可用 |
| 3 | `调工具` | 模型返回 `{ toolCall }` 或 `{ text }`，判断它决定走哪条路 |
| 4 | `system-user-tool` | 四种 role 的语义顺序：规则 → 提问 → 工具结果 |
| 5 | `undefined` | 取一个不存在的工具，得到 `undefined`，对它调用就会 `TypeError` |
| 6 | `string` | 真实 API 里 `arguments` 是 JSON 字符串，要 `JSON.parse` 后才变对象 |
| 7 | `1+2` | `JSON.parse` 把字符串还原成对象，再取字段 |
| 8 | `{"role":"tool","content":null}` | `JSON.stringify` 会把 `null` 原样保留，不会省略 |
| 9 | `[ 'd', 'e' ]` | `slice(-2)` 取最后两条，正是滑动窗口"只留最近 N 条"的做法 |
| 10 | `4` | JS 字符串的 `length` 按 UTF-16 码元算，4 个中文 = 4（≠ token 数） |
| 11 | `6` | 中文 1 字 ≈ 1 token 的粗算：正则数出 6 个中文字 |
| 12 | `{"a":1}` | 剥掉 json 代码块外壳，正则 `[\s\S]*?` 非贪婪取到代码块内部 |
| 13 | `{"a":1}` | 去尾逗号：把 `,}` 和 `,]` 里的逗号删掉 |
| 14 | `0 12` | 找第一个 `{` 到最后一个 `}`，是"无代码块时抠 JSON"的思路 |
| 15 | `number` | `JSON.parse` 后 `22` 是真正的数字类型 |
| 16 | `138****5678` | 手机号脱敏：前 3 位 + `****` + 后 4 位 |
| 17 | `[ 2, 3 ]` | `filter` 返回新数组，保留满足条件的元素 |
| 18 | `function` | `llm.invoke` 是一个方法（函数），这是可插拔 mock 的接口形状 |
| 19 | `true` | 循环条件：步数还没到上限就继续 |
| 20 | `超预算` | 花费超过预算就停，是"预算刹车"的判断逻辑 |
| 21 | `TypeError` | 循环引用会让 `JSON.stringify` 抛 `TypeError`（Converting circular structure to JSON） |
| 22 | `{"quote":"他说\"你好\""}` | `JSON.stringify` 自动转义双引号，永远别手写 JSON 字符串 |
| 23 | `weather` | 必填字段校验：`city` 在，`weather` 缺失被挑出来 |
| 24 | `15` | `reduce` 累加，是 token/成本累加这类计算的基础 |
| 25 | `get_weather` | 正则从 ReAct 文本里抠出 Action 的工具名 |

**这一关的 4 个"★"（5 / 9 / 21 / 22）是面试最爱考的**，因为它们体现了 Agent 代码的边界在哪：未知工具会 `undefined`、`slice` 是滑动窗口的底层、循环引用会让状态序列化崩掉、手写 JSON 必踩转义坑。

**得分对照**：错 0~4 题 → 优秀；错 5~7 题 → 及格；错 8 题以上 → 重读 02/03/06 章。

## 第三关答案

### 第 1 题：忘了把工具结果回填

**问题**：工具执行后拿到了 `result`，但没有 `messages.push({ role: 'tool', content: result })`。第二次 `invoke(messages)` 时，模型看到的还是原来的数组，**它根本不知道工具执行过、结果是什么**，于是很可能再次要求调用同一个工具，陷入死循环。

**修改**：

```js
if (r.toolCall) {
  const result = tools[r.toolCall.name](r.toolCall.args);
  messages.push({ role: 'tool', content: result }); // 关键：回填结果
  const r2 = await llm.invoke(messages);
}
```

**核心教训**：**工具执行完必须立刻回填 `role: 'tool'` 消息。** 这是 Agent 记忆机制的根基——模型无状态，它记得的一切都是你每次重新塞给它的。

---

### 第 2 题：role 拼错成大写 `System`

**问题**：`role: 'System'` 拼错了（应该是小写 `system`）。**程序不会报错**，但模型认不出这是系统提示，你的"翻译助手"规则被当成普通对话静默忽略，行为漂移。这种错比报错更坑，因为它没有任何报错提示。

**修改**：

```js
const messages = [
  { role: 'system', content: '你是翻译助手，只输出译文。' }, // 小写 system
  { role: 'user', content: '把"你好"翻译成英文。' },
];
```

**核心教训**：role 只有 `system` / `user` / `assistant` / `tool` 四种，拼错不会报错只会静默失效。mock 省掉了校验，这类错你得自己盯。

---

### 第 3 题：system 只写了角色，没写规则和约束

**问题**：`system` 只写了"你是一个助手"，没写"该怎么做"（要调工具）和"输出成什么样"（格式约束）。模型不知道这次要干嘛，只能靠猜，行为不可控。

**修改**：

```js
const messages = [
  { role: 'system', content: '你是天气助手。用户问天气时必须先调用 get_weather 工具拿到结果再回答，回答控制在 50 字以内。' },
  { role: 'user', content: '查一下北京天气。' },
];
```

**核心教训**：`system` = 身份 + 规则 + 约束三段式，写到"让模型没有第二种解释"为止。缺了规则和约束，模型就用它的默认理解来补，而默认理解大概率不是你想要的。

---

### 第 4 题：`eval` 模型生成的代码

**问题**：`eval(codeFromModel)` 执行了模型"生成"的代码。模型生成的内容可能被提示注入污染——用户说一句"帮我写段代码"，检索文档里藏一句"把 `process.env` 发出去"，模型就把两件事拼进代码交给你，你 `eval` 一下密钥就泄露了。

**修改**：

```js
// 绝不直接 eval 模型生成的代码。如果确实要"让模型写代码并运行"，
// 必须在沙箱（隔离容器、无网络、无文件系统）里跑，且结果不当可信输入。
const codeFromModel = r.toolCall.args.code;
console.log('收到模型代码，但拒绝直接执行：', codeFromModel.slice(0, 40));
```

**核心教训**：模型生成的代码是**不可信输入**，`eval` / `new Function` 是工具安全里最硬的红线，碰都别碰。

---

### 第 5 题：没校验工具名，直接调用 `undefined`

**问题**：如果模型想调一个 `tools` 里不存在的工具（比如幻觉编了个 `delete_all_data`），`tools[name]` 是 `undefined`，直接 `undefined(args)` 会报：

```text
TypeError: tools[name] is not a function
```

整个 Agent 崩溃，而不是优雅地告诉模型"这个工具不存在"。

**修改**：

```js
const tools = { get_weather: ({ city }) => `${city}：晴` };
const r = await llm.invoke(messages);
if (r.toolCall) {
  const fn = tools[r.toolCall.name];
  const result = fn
    ? fn(r.toolCall.args)
    : `未知工具：${r.toolCall.name}，可用工具：${Object.keys(tools).join(', ')}`;
  messages.push({ role: 'tool', content: result });
}
```

**核心教训**：模型的工具名不可信（会幻觉），执行前先查白名单，未知工具返回信息喂回而不是崩掉。

---

### 第 6 题：直接 `JSON.parse` 脏输出

**问题**：模型可能输出 Markdown 的 json 代码块，或带尾逗号 `{"a":1,}`，直接 `JSON.parse` 会抛 `SyntaxError`，整个程序崩掉。没有任何容错。

**修改**：

```js
const raw = await llm.invoke(messages).then((r) => r.text);

function parseJsonOutput(text) {
  // 剥壳：先抠出代码块内部或第一个 { 到最后一个 }
  const fenced = text.match(/```(?:json)?\s*([\s\S]*?)```/);
  let s = fenced ? fenced[1].trim() : text.trim();
  // 修复尾逗号、中文引号
  const repaired = s.replace(/,\s*([}\]])/g, '$1').replace(/[\u201C\u201D]/g, '"');
  return JSON.parse(repaired);
}

const data = parseJsonOutput(raw);
console.log(data.temperature);
```

**核心教训**：模型输出永远是"脏"的，必须走"剥壳 → 修复 → 解析"的健壮解析器，永远假设它可能带代码块、带尾逗号。

---

### 第 7 题：`||` 吃掉了 `0`

**问题**：`config.maxTurns || 10` 在 `maxTurns` 是 `0` 时会返回 `10`。`0` 是一个**合法值**（可以表示"不限步数"或"立即停止"），被静默替换掉了。这和"设默认值"的意图完全相反。

**修改**：

```js
function getMaxTurns(config) {
  return config.maxTurns ?? 10; // 只有 null/undefined 才用默认值
}
console.log(getMaxTurns({ maxTurns: 0 })); // 0
```

**核心教训**：**设默认值一律用 `??`，别用 `||`。** `||` 会把 `0`、`''`、`false` 这些合法值也当成"没设置"。

---

### 第 8 题：`while (true)` 没有退出上限

**问题**：`while (true)` 靠模型某天自己 `break`。如果模型一直返回 `toolCall`（反复调用同一工具、总觉得自己"信息不够"），这个循环就永远跑下去，账单无限滚，CPU 跑满。

**修改**：

```js
async function runAgent(llm, messages, tools, { maxIterations = 10 } = {}) {
  for (let steps = 0; steps < maxIterations; steps++) {
    const r = await llm.invoke(messages);
    if (r.toolCall) {
      const fn = tools[r.toolCall.name];
      messages.push({ role: 'tool', content: fn ? fn(r.toolCall.args) : `未知工具：${r.toolCall.name}` });
      continue;
    }
    return r.text;
  }
  return `超过最大步数 ${maxIterations}，强制停止`; // 兜底出口
}
```

**核心教训**：循环条件里必须带 `steps < maxIterations`，这是**结构性保证**，而不是"寄希望于模型某天会 break"。

---

### 第 9 题：测试断言了精确措辞

**问题**：`assert.equal(result.text, '北京今天晴，25℃')` 断言的是模型的**具体措辞**。模型是概率的，同样的输入换一次运行措辞可能就变，这个测试会**随机地**通过或失败，毫无意义。

**修改**：

```js
test('agent 会调用 get_weather 工具', async () => {
  const result = await runAgent(mockLlm, state, tracer);
  // 断言"结构事实"，不测措辞：trace 里确实出现了一次工具调用
  assert.ok(tracer.list().some((r) => r.kind === 'tool' && r.name === 'get_weather'));
});
```

**核心教训**：概率系统测**结构和边界**，不测措辞。锚点放在"调了正确的工具""在步数上限内停止"这些确定性事实，而不是模型说的话。

---

### 第 10 题：手写 JSON 字符串，漏转义双引号

**问题**：手写的 JSON 字符串里，`你好` 两边的双引号没转义。`JSON.parse` 直接抛：

```text
SyntaxError: Expected ',' or '}' after property value in JSON at position 13 (line 1 column 14)
```

解析器看到 `"他说"` 以为字符串结束了，后面的 `你好` 是凭空冒出来的。这个错**无法自动修复**。

**修改**：

```js
const json = JSON.stringify({ quote: '他说"你好"' }); // 用 JSON.stringify 生成，转义自动处理
console.log(JSON.parse(json).quote); // 他说"你好"
```

**核心教训**：**永远用 `JSON.stringify` 生成 JSON，别手写字符串。** 转义、引号这些坑，`JSON.stringify` 全自动帮你处理。

## 第四关答案

### 1. 什么是 AI Agent？和聊天机器人、工作流有什么区别？

**一句话**：Agent 是"让模型在循环里自主决定流程、调用工具直到完成任务"的系统；聊天机器人只答一句，工作流的流程是代码写死的。

**要点**：

- 聊天机器人：一次问答，模型只"说话"，没有工具、没有循环。
- 工作流（workflow）：流程**预定义**，先 A 后 B 是程序员写死的，模型没有"选择权"。
- Agent：模型**自主决定**"下一步调哪个工具、调几次、什么时候停"，这是它和工作流的本质区别。
- 判断标准：如果你的流程能画成一张确定性流程图，就该用工作流，别上 Agent（更贵更慢更难调试）。

### 2. 为什么说模型是"无状态"的？真正的记忆放哪？

**一句话**：模型每次调用都是独立计算，不保存任何跨调用的信息；"记忆"在**你的应用代码里**（一个 messages 数组、一个数据库）。

**要点**：

- 每次调用：输入 → 输出，调用结束它就"失忆"。
- 所谓"记得上一轮"，是应用层把历史对话和新问题**拼成新输入**重新喂给模型。
- 所以 Agent 的记忆机制 = 每次调用前，把 `messages` 数组完整传给模型。
- 工程含义：模型记得的一切都是你塞给它的，忘喂了它立刻"失忆"。

### 3. 工具调用的完整流程？模型真的调用函数了吗？

**一句话**：模型没调用任何函数，它只是输出一段"我想调 X 工具、参数是 Y"的结构化文字，由你的代码解析、执行、再把结果喂回。

**要点**：

- 四步闭环：模型输出 tool_call → 代码解析 → 代码执行工具 → 结果以 `role: 'tool'` 喂回。
- 模型只参与"想要什么"和"看懂结果"，真正的执行（②③）全在你的代码。
- 一次工具调用 = 多一次模型调用 = 多花钱，这是"自主是有代价的"。
- 真实 API 里：`tool_calls` 是数组、`arguments` 是 JSON 字符串、`tool_call_id` 要一一对应。

### 4. 四种 role？tool 为什么必须代码回填？

**一句话**：`system`（规则）、`user`（提问）、`assistant`（模型回复）、`tool`（工具结果）；`tool` 只能由代码执行后回填，因为模型"只说不动手"。

**要点**：

- `system` 放最前面，写"身份 + 规则 + 约束"，全程生效。
- `tool` 消息必须紧跟那条"要调工具"的 `assistant` 之后，模型才能顺着因果链理解结果。
- 模型自己不会、也不能生成 `tool` 消息——它没有执行环境。
- 坑：role 拼错（如大写 `System`）不报错、静默失效。

### 5. 上下文窗口是什么？为什么 Agent 会爆窗口？

**一句话**：上下文窗口是模型一次调用能"看见"的最大 token 数，是硬上限；Agent 是循环，每轮都在往 messages 里加东西，迟早撞墙。

**要点**：

- token 是切分文本的最小单位：中文约 1 字 1 token，英文约 4 字符 1 token。
- Agent 每循环一轮，messages 就多两条（assistant 的 tool_call + tool 的结果），越滚越大。
- 爆窗口的后果：要么 API 拒绝（如 `context_length_exceeded`），要么框架悄悄截掉最老消息、模型"悄悄失忆"。
- 巨型工具结果（几千行文件）会瞬间吃掉窗口，所以工具结果也要计入、必要时截断。

### 6. 记忆分哪几层？

**一句话**：短期（messages 数组）、长期（外部存储）、工作（任务关键信息），本质是给信息标注"住哪、活多久"。

**要点**：

- 短期：当前会话的 `messages`，受窗口限制，随用随丢。
- 长期：跨会话、海量信息，存数据库/向量库，需要时检索回来。
- 工作：任务进行中"不能丢"的关键信息（航班号、身份证号），压缩时最该重点保护。
- 分层的意义：窗口有限，不能全塞短期记忆；没分层意识就会"全塞爆掉"或"无脑截断删掉关键信息"。

### 7. 省上下文空间的三策略？

**一句话**：滑动窗口（砍）、摘要（压缩）、检索（外移），按"早期信息重不重要"选。

**要点**：

- 滑动窗口：只留 system + 最近 N 条。快、token 稳定，但丢早期信息。
- 摘要：把早期历史压成一段摘要。省空间又保关键信息，但多一次模型调用 + 有幻觉风险。
- 检索（外移长期记忆）：最稳但要建存储。实战常是组合拳。
- 判据：信息越不重要越可以砍；越重要越不能靠猜，要么摘要要么外移。

### 8. 什么是 ReAct？Thought/Action/Observation 谁生成的？

**一句话**：ReAct 是"推理 + 行动"交替的循环，Thought 和 Action 是模型生成的文本，Observation 是代码执行工具后喂回的。

**要点**：

- 结构：`Thought`（想）→ `Action`（动）→ `Observation`（看）循环，直到 `Final Answer`。
- 模型只负责输出 Thought / Action 的**文本**，真正执行工具、拿 Observation 的是你的代码。
- 它解决了纯 CoT"只会想不会查"和纯行动"只会动不会想"两个短板。
- 和 function calling 的关系：ReAct 是纯文本协议（任何模型都能用），function calling 是厂商把工具调用做成了结构化 API。

### 9. CoT 和 ReAct 的区别？什么时候用 CoT？

**一句话**：CoT 只能"想"（把推理过程写出来当草稿纸），ReAct 能"边想边动"（想一步、调工具、看结果）；CoT 只对需要中间计算的任务有效。

**要点**：

- CoT 的原理：模型逐 token 生成，已输出的过程 token 成为后续计算的"工作记忆"。
- 该用：多位数算术、多条件判断、需要推导链的推理题。
- 不该用：简单事实问答、翻译、改写、摘要（一步能答的，写过程纯浪费 token）。
- ReAct = CoT（想）+ 工具调用（动）的组合，是今天 agent loop 的鼻祖。

### 10. 怎么让模型可靠输出 JSON？约束手段分几档？

**一句话**：从弱到强四档——prompt 约束 → JSON mode → JSON Schema → 函数式输出，约束力递增、通用性递减。

**要点**：

- prompt 约束：告诉模型"只输出 JSON"。最通用但约束最弱，可能多写解释、格式错。
- JSON mode（`response_format: { type: 'json_object' }`）：保证合法 JSON，但不保证字段结构。
- JSON Schema：约束字段名/类型/必填，模型侧就保证字段对，但支持厂商少、太严会卡生成。
- 函数式输出：工具调用的参数天然是结构化 JSON，最强。
- 实战铁律：无论哪一档，**后面都要接健壮解析器兜底**。

### 11. 模型输出的 JSON 是"脏"的，怎么清洗？

**一句话**：一条流水线——剥壳 → 修复 → 解析 → 校验。

**要点**：

- 剥壳：抠掉 json 代码块外壳，或找第一个 `{` 到最后一个 `}`。
- 修复：去尾逗号、把中文引号换成英文引号（只在 parse 失败后才修，修复是有损的）。
- 解析：`JSON.parse`，失败再修复重试。
- 校验：补默认值、查必填字段，缺省和必填分开处理。
- 转义陷阱（漏转义双引号）无法自动修复，只能源头堵。

### 12. 什么是幻觉？为什么发生？怎么缓解？

**一句话**：幻觉是模型在"编词"而非"查事实"，因为它是逐字预测"下一个最可能的词"；你只能缓解，不能消除。

**要点**：

- 原因：训练目标是"输出像人写的文本"，不是"输出事实"；不确定时它会硬编，而不是说"不知道"。
- 在 Agent 里的三种危害：编工具名、编参数、编"已完成"。
- 缓解两条路：① RAG——把事实检索进上下文，让模型"照稿念"；② 允许说不知道——降低它编造的动机。
- 黄金组合：先检索给足资料，再允许它对资料外的问题说"不知道"。

### 13. 什么是提示注入？为什么防不住？怎么分层缓解？

**一句话**：把恶意指令藏进"看似无辜的数据"里诱导模型越权；它防不住，因为模型分不清"指令"和"数据"，只能分层降风险。

**要点**：

- 为什么防不住：模型眼里，系统提示和用户输入都是"一段文字"，没有天然的优先级。
- 第一道防线：规则过滤，用正则拦明显的注入（"忽略之前指令"等），成本低、确定性高，但拦不住变体。
- 第二道防线：数据隔离，用分隔符把"指令区"和"数据区"切开，反复声明数据身份。
- 第三道防线：最小权限，让"被骗"的代价最小——给模型的工具越少越安全。

### 14. Agent 死循环、成本失控怎么办？几道刹车？

**一句话**：装三道独立刹车——最大步数（管次数）、预算上限（管钱）、人工审批（管不可逆动作）。

**要点**：

- 死循环原因：模型不觉得"信息够了"，或工具结果格式让模型困惑。
- 最大步数：`while (steps < maxIterations)` 结构性兜底，超限强制停止。
- 预算上限：每次工具调用累计花费，超预算就停（步数和预算正交，都要有）。
- 人工审批：转账、发邮件、删数据这类不可逆动作，把最终决定权收回到人手里。

### 15. 怎么测一个概率系统（Agent）？

**一句话**：测结构和边界，不测措辞——用 mock LLM 固定剧本，断言"字段/步骤/兜底"。

**要点**：

- 为什么不能测措辞：模型输出是概率的，`assert.equal(text, '...')` 会随机失败。
- 该测什么：调了正确的工具（结构）、循环在步数上限内停止（边界）、状态能序列化恢复（状态机）。
- mock LLM：把模型换成"剧本固定"的 mock，测试可预测、离线可跑。
- 快照测试：第一次把 trace 存成快照，以后对比，发现结构漂移。

# 结语：如果你都做完了

那么你现在应该能做到：

- 手写出一个完整的 agent loop：消息数组 + 工具表 + 循环 + 回填 + 兜底。
- 看到模型的任何输出，第一反应是"它是脏的、不可信的，先校验"。
- 给 Agent 加工具时，本能地写成 `validate` / `execute` 分离的结构。
- 看到 `while (true)` 会本能地不舒服，并知道该加最大步数和预算两道刹车。
- 测 Agent 时不碰措辞，只断言结构和边界。
- 面试里被问到任何一题，都能说出"是什么 + 为什么这么设计 + 什么时候不该用"。

**下一步建议：**

1. 把第五关的 5 个答案文件**自己重写一遍**，不看答案。
2. 找一个真实 API（OpenAI 或国产模型），把 `llm.invoke` 换成一次 `fetch`，验证循环逻辑一行不用改。
3. 给第 1 题的 Agent 加一个"重复调用检测"，连续调同一工具 2 次就停。
4. 把第 5 题的 trace 做成快照测试。
5. 面试前一晚看 [第 11 章 面试速查表](11-面试速查表.md)。

> AI Agent 的难点从来不是"调 API"，而是**"什么时候该让模型自主、什么时候该用护栏兜底、什么时候该上框架"**。
> 而这个判断力，只能靠在真实项目里反复踩坑练出来。
