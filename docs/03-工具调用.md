# 第 03 章 · 工具调用：给模型装上"手"

> 上一章你知道了模型只能"说话"不能"动手"。这一章解决的就是怎么让它"动手"。
> 本章你需要记住的就一件事：**工具调用（function calling）不是模型去调用函数，而是模型输出一段"我想调用 X 工具、参数是 Y"的结构化文字，由你的代码解析、执行、再把结果以 `role: 'tool'` 喂回去，如此循环。**

---

## 03.1 模型没有"手"：工具调用的完整闭环

先破除一个流传很广的误解：**模型并不能"调用"任何函数**。它运行在一个隔离的推理环境里，碰不到你的文件系统、数据库、网络，更没有你的 `calculator` 函数。

那"工具调用"到底发生了什么？它是一段**四步循环**：

```text
① 模型输出 tool_call（一段结构化文字）
   例：{ name: "calculator", args: { expression: "1 + 2 * 3" } }

② 你的代码解析这段文字，取出工具名和参数

③ 你的代码真正去执行工具（这才是"动手"）
   calculator("1 + 2 * 3") → 7

④ 把结果以 role: "tool" 喂回给模型，让它决定下一步
   模型看到结果 7，然后给最终文字答案
```

四步里，模型只参与了 ① 和 ④——它负责"想要什么"和"看懂结果"，真正的执行（②③）完全在你的代码里。这就是第 00 章说的「模型负责想，代码负责动」。

把它写成一个能跑的循环，就是整个 agent loop 的核心。完整可运行版在 `examples/03-工具调用.mjs`，这里看骨架：

```js
async function runAgent(llm, userInput) {
  const messages = [
    { role: 'system', content: '你是助手，会用 calculator 工具来回答数学问题。' },
    { role: 'user', content: userInput },
  ];

  for (let i = 0; i < 10; i++) {          // 兜底：最多循环 10 次
    const reply = await llm.invoke(messages);

    if (reply.toolCall) {                 // ① 模型想调工具
      const { name, args } = reply.toolCall;
      messages.push({ role: 'assistant', content: null, toolCall: reply.toolCall });
      const result = runTool(name, args); // ②③ 你的代码执行工具
      messages.push({ role: 'tool', content: result.content }); // ④ 结果喂回
      continue;                            // 回到循环顶部，再问模型
    }

    return reply.text;                     // 模型给了最终答案，结束
  }
  throw new Error('达到最大循环次数 10，强制停止');
}
```

运行 `examples/03-工具调用.mjs`，你会看到一次真实的多轮工具调用（剧本预置了 5 轮响应）：

```text
=== 工具调用循环开始 ===
[第1轮] 模型想调用工具: calculator {"expression":"1 + 2 * 3"}
          执行结果: 7
[第2轮] 模型想调用工具: calculator {"expression":12345}
          执行出错: TypeError: 参数 expression 必须是字符串，但收到 number
[第3轮] 模型想调用工具: calculator {"expression":"100 / 0"}
          执行出错: Error: 计算失败：100 / 0 = Infinity（可能是除零）
[第4轮] 模型想调用工具: calculator {"expression":"100 / 4"}
          执行结果: 25
[第5轮] 模型最终回答: 1 + 2 * 3 = 7，100 / 4 = 25。
=== 循环结束 ===
共调用模型 5 次，调用工具 4 次，其中 2 次出错被喂回修正。
```

注意这个循环的**代价**：每调用一次工具，就要**多调用一次模型**。5 轮循环 = 5 次模型调用。这就是第 00 章说的"自主是要付出代价的"——工具调用次数 = 你的账单。

> 一句话记住它：工具调用 = 「模型输出 tool_call → 代码执行 → 结果以 role:tool 喂回」的循环，模型只负责"想"，代码才负责"动"，而每一次"动"都要多付一次模型调用的钱。

## 03.2 工具描述（schema）：模型的"说明书"

**结论先说：模型根本不认识你的工具，它唯一的信息来源就是你写的那段描述（schema）。schema 写得烂，模型就会瞎调。**

模型训练时没见过你的 `calculator` 函数，它怎么知道这个工具能干嘛、该传什么参数？答案是你每次调用模型时，把工具的"说明书"一起发给它。这份说明书通常长这样：

```js
const tools = {
  calculator: {
    description:
      '计算一个数学表达式，支持 + - * / 和括号。' +
      '入参 expression 必须是字符串，例如 "1 + 2 * 3"。返回数值结果。',
    parameters: {
      type: 'object',
      properties: {
        expression: {
          type: 'string',
          description: '要计算的算术表达式，例如 "1 + 2 * 3"',
        },
      },
      required: ['expression'],
    },
    execute(args) { /* 真正干活的代码，模型永远碰不到 */ },
  },
};
```

这份 schema 有两个作用，缺一不可：

1. **`description` 告诉模型"什么时候该用我"**。写"计算数学表达式"和写"把温度从摄氏转华氏"，模型的行为会完全不同——前者是通用计算器，后者只在单位换算时才触发。
2. **`parameters` 告诉模型"该怎么用我"**。`type: 'string'` 约束了类型，`required` 声明了必填项，`properties.expression.description` 解释了参数含义。

这套 `parameters` 的格式叫 **JSON Schema**，是描述"一段 JSON 长什么样"的通用标准。你写工具的套路就是：**用 JSON Schema 描述入参，用一句话描述能力**。

**为什么 description 要这么讲究？** 因为模型对工具的"理解"完全来自文字。它不会看你的 `execute` 函数体，只看你写的描述。三个实战技巧：

- **写清单位和边界**。写"查询天气，city 是城市中文名"，别只写"查天气"——模型不知道 city 该填"北京"还是"Beijing"还是经纬度。
- **给一个参数示例**。`例如 "1 + 2 * 3"` 这种，能让模型少猜一半。
- **描述要专一**。一个工具只做一件事。如果你让一个 `run_code` 工具既能算数又能读文件又能发邮件，模型反而不知道该不该调它。

一个反例：如果你把 description 写成 `"处理事情"`，模型大概率在无关场景也调它，或者在真正需要时犹豫。**工具描述的模糊度 = 模型的决策出错率**。

> 一句话记住它：模型对工具的"认知"100% 来自你的 schema，`description` 决定"什么时候用"，`parameters`（JSON Schema）决定"怎么用"，写清楚单位和示例是性价比最高的优化。

## 03.3 参数校验：模型给的参数不可信

**结论先说：模型输出是概率采样，它给的参数可能是错的类型、缺的字段、越界的值。你必须在执行前校验，否则轻则崩程序，重则执行危险操作。**

回想上一节的输出：模型第二次调用传了 `{"expression":12345}`——一个数字，不是字符串。如果你不做校验，直接 `expression.split('')` 或者更糟地拼进命令，程序就崩了，或者被注入。

真实的校验应该分层，逐层拦截。`examples/03-工具调用.mjs` 里的 `safeCalculate` 就是例子，它把"模型参数"当成不可信的外部输入来防：

```js
function safeCalculate(expression) {
  // 校验 1：类型必须是字符串（模型可能传数字、对象、null）
  if (typeof expression !== 'string') {
    throw new TypeError(`参数 expression 必须是字符串，但收到 ${typeof expression}`);
  }
  // 校验 2：白名单，只允许数字、四则运算、括号、小数点、空白
  if (!/^[0-9+\-*/().\s]+$/.test(expression)) {
    throw new Error(`表达式包含非法字符："${expression}"，只允许数字和 + - * / ( )`);
  }
  // 校验 3：禁止注释符号，防止把 "//" 或 "/*" 注入进 eval
  if (/\/\/|\/\*|\*\//.test(expression)) {
    throw new Error(`表达式包含注释符号："${expression}"`);
  }
  // 校验 4：至少有一个数字，否则是空表达式
  if (!/[0-9]/.test(expression)) {
    throw new Error(`表达式里没有数字："${expression}"`);
  }
  // 已通过白名单，这里只用算术字符构造函数，是"受限的 eval"
  const value = Function('"use strict"; return (' + expression + ')')();
  if (typeof value !== 'number' || !Number.isFinite(value)) {
    throw new Error(`计算失败：${expression} = ${value}（可能是除零）`);
  }
  return value;
}
```

为什么要分这么多层？因为**每一层拦一种不同的错误**，错误信息要足够具体，模型才能看懂并修正（下一节讲）。实测几种非法输入的真实报错：

```text
safeCalculate(undefined)   → TypeError: 参数 expression 必须是字符串，但收到 undefined
safeCalculate("1; process.exit()") → Error: 表达式包含非法字符："1; process.exit()"，只允许数字和 + - * / ( )
safeCalculate("1//2")      → Error: 表达式包含注释符号："1//2"
safeCalculate("()")        → Error: 表达式里没有数字："()"
safeCalculate("100/0")     → Error: 计算失败：100/0 = Infinity（可能是除零）
```

注意校验 2 和 3 这两个"白名单 + 禁注释"的组合拳。很多人直接用 `eval(expression)` 图省事，结果用户（或模型被诱导）传进 `"process.exit()"`、`"1 // 后面的都被当注释"` 这类字符串，就构成了**代码注入**。受限 eval 的思路是：**先让输入通过一个白名单正则，只放行算术字符，再交给 `Function` 执行**。这样危险字符在进 eval 之前就被拦掉了。

> 一句话记住它：模型给的参数是不可信输入，执行前必须校验；校验要分层、报错要具体（带错误名），这是"不可靠的可靠系统"的第一个落地动作。

## 03.4 工具出错：把错误喂回，让模型自我修正

**结论先说：工具执行出错，不要 `throw` 让整个程序崩掉，而是把错误信息塞进 `role: 'tool'` 的 content 喂回给模型，模型能看懂错误并自己修正。**

这是 function calling 里最反直觉、也最有价值的一个设计。传统代码里，函数抛异常我们就 `try/catch`、打日志、返回错误码给用户。但 Agent 里，**错误对模型来说不是"灾难"，是"信息"**。

看 `examples/03-工具调用.mjs` 里 `runTool` 的处理：

```js
function runTool(name, args) {
  const tool = tools[name];
  if (!tool) {
    return { ok: false, content: `未知工具：${name}，可用工具：${Object.keys(tools).join(', ')}` };
  }
  try {
    const value = tool.execute(args);
    return { ok: true, content: JSON.stringify(value) };
  } catch (err) {
    // 关键：把错误名 + 错误信息喂回，而不是让它崩掉
    return { ok: false, content: `${err.name}: ${err.message}` };
  }
}
```

喂回的错误长这样（就是上面示例真实输出的第 2、3 轮）：

```text
[第2轮] 执行出错: TypeError: 参数 expression 必须是字符串，但收到 number
[第3轮] 执行出错: Error: 计算失败：100 / 0 = Infinity（可能是除零）
```

模型看到 `TypeError: ...但收到 number`，下一轮就知道"哦，我传错类型了，应该传字符串"，于是换成 `"100 / 4"`；看到 `除零`，就知道换一个除数。**这就是"自我修正"**——它不需要你写任何 if-else 去分类错误，模型自己读得懂自然语言错误信息。

**为什么这么设计，而不是直接终止？** 因为 Agent 的价值就在于"自主"：如果工具一报错就停下来等人工，那它跟一段会崩溃的普通脚本没区别。把错误喂回，等于把"重试一次"的判断权交给了模型——它可能修正参数重试，也可能换个工具，也可能承认失败给用户解释。三种结果都是合理的，而你只用一段代码就全都支持了。

但要注意**成本**：错误喂回 = 多一轮模型调用 = 多花钱。如果同一个错误反复喂回、模型反复犯同样的错，就会陷入死循环。所以必须配合两个兜底：

1. **最大循环次数**（上面 loop 里的 `i < 10`），超了强制停。
2. **错误次数统计**：如果同一工具连续报错 N 次，主动终止并降级（给用户一个"我搞不定"的兜底话术），别让账单无限滚。

> 一句话记住它：工具报错不崩溃，把 `错误名: 错误信息` 当普通结果喂回给模型，让它自己决定重试还是换路；但必须用"最大次数"和"连续报错计数"兜底，防止烧钱死循环。

## 03.5 接真实 API：从 mock 到 function calling

**结论先说：mock 和真实 OpenAI function calling 的差异只有两点——字段名不同、`arguments` 是字符串且要带 `tool_call_id` 对应。核心循环逻辑一模一样。**

前面所有示例为了离线可跑，用的是 `llm-mock.mjs` 的简化格式。真实接 OpenAI 时，消息结构要换成官方格式。对照看：

```js
// mock 简化格式（examples 里用的）
messages.push({ role: 'assistant', content: null, toolCall: { name: 'calculator', args: { expression: '1+2' } } });
messages.push({ role: 'tool', content: '7' });

// OpenAI 真实 function calling 格式
messages.push({
  role: 'assistant',
  content: null,
  tool_calls: [
    {
      id: 'call_abc123',                 // 每个 tool_call 有唯一 id
      type: 'function',
      function: {
        name: 'calculator',
        arguments: JSON.stringify({ expression: '1+2' }), // 注意：是 JSON 字符串
      },
    },
  ],
});
messages.push({ role: 'tool', tool_call_id: 'call_abc123', content: '7' }); // id 要和上面对应
```

三个必须记住的差异：

1. `toolCall` → `tool_calls`，而且是**数组**（模型一次可能想调多个工具）。
2. `args` → `function.arguments`，是 **JSON 字符串**，不是对象，你拿到后要 `JSON.parse`。
3. `role: 'tool'` 消息必须带 `tool_call_id`，跟 assistant 的 `tool_calls[].id` 一一对应，否则 API 报 400。

真正发起调用的代码（这段不能离线跑，需要 API key，注释里写清楚就好）：

```js
// 这段需要真实 OpenAI API key，离线环境跑不通，仅作对照。
// 离线请跑 examples/03-工具调用.mjs（用 mock）。
const resp = await fetch('https://api.openai.com/v1/chat/completions', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${API_KEY}`,
  },
  body: JSON.stringify({
    model: 'gpt-4o',
    messages,                       // 就是上面拼出来的消息数组
    tools: buildOpenAiTools(tools), // 把 03.2 的 schema 转成 OpenAI 的 tools 格式
  }),
});
const data = await resp.json();
// data.choices[0].message.tool_calls 就是模型想调用的工具（可能为 undefined 表示直接文字回答）
// data.choices[0].message.content 就是最终文字答案
```

`buildOpenAiTools` 做的是把我们的 `{ description, parameters }` 转成 OpenAI 要求的 `{ type: 'function', function: { name, description, parameters } }`。国内模型（通义、DeepSeek、Kimi、文心等）的格式**基本照抄 OpenAI**，字段名几乎一致，你学会这一套就通用了。

**为什么教程坚持用 mock？** 因为模型调用是概率性的、要花钱、要联网。教程的核心是让你理解"循环"和"为什么这么设计"，这些用确定性 mock 反而讲得更清楚——每一轮的输入输出都可预测。等你理解了机制，把 `llm.invoke` 换成上面这段 `fetch`，逻辑一行都不用改。这就是第 00 章说的"可插拔"。

> 一句话记住它：真实 API 和 mock 的循环逻辑完全一致，差异只在消息字段名（`tool_calls` 数组 + `arguments` 字符串 + `tool_call_id` 对应）；把 mock 的 `invoke` 换成一次 `fetch` 就接上了真实模型。

## 03.6 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 把工具结果忘了喂回 | 模型反复调用同一工具，或给不出答案 | `role: 'tool'` 消息没 push 进 messages，模型"看不见"工具结果 | 执行完工具必须 push `{ role: 'tool', content }` 再循环 |
| `tool_call_id` 对不上 | 真实 API 返回 400 | assistant 的 `tool_calls[].id` 和 tool 消息的 `tool_call_id` 不一致 | 用 assistant 返回的那个 id 原样填进 tool 消息 |
| 把 `arguments` 当对象用 | 取不到参数 | OpenAI 的 `function.arguments` 是 JSON 字符串 | `JSON.parse(toolCall.function.arguments)` |
| 用 `eval` 直接执行模型输入 | 代码注入 / 崩溃 | 模型参数不可信，可能传 `process.exit()` | 白名单校验后再受限执行，危险字符进 eval 前拦掉 |
| 工具报错就 throw | 整个 agent 崩溃 | 没把错误当成可喂回的信息 | `try/catch` 后把 `错误名: 信息` 塞进 role:tool 喂回 |
| 循环不设最大次数 | 死循环 + 账单爆掉 | 模型可能反复犯同样错误 | 设 `maxIterations`，连续报错 N 次强制停止 |

## 03.7 本章小结

- 工具调用是「**模型输出 tool_call → 代码执行 → role:tool 喂回**」的循环，模型只"想"、代码才"动"。
- 模型**不认识**你的工具，它唯一的认知来源是 schema：`description` 决定何时用，`parameters`（JSON Schema）决定怎么用。
- 模型参数是**概率采样**，类型错、缺字段、越界都会发生，执行前必须分层校验。
- 工具报错**不要崩溃**，把 `错误名: 错误信息` 喂回，模型能自我修正。
- 自我修正有成本，必须用**最大循环次数 + 连续报错计数**兜底。
- 真实 OpenAI function calling 与 mock 的差异只有：`tool_calls` 数组、`arguments` 是字符串、`tool_call_id` 对应。
- 换真实模型只需把 mock 的 `invoke` 换成一次 `fetch`，循环逻辑不变。

## 03.8 动手练习

1. `examples/03-工具调用.mjs` 的剧本里，如果把最后一条 `{ content: '...' }` 删掉，会发生什么？为什么？

   <details><summary>参考答案</summary>
   循环会一直走到 `maxIterations = 10`，然后 `throw new Error('达到最大循环次数 10，强制停止')`。因为剧本耗尽后 mock 返回兜底文字 `[mock] 剧本耗尽，无更多响应`——但注意：剧本耗尽返回的是 `{ text }` 而不是 `{ toolCall }`，所以其实第 5 轮会直接返回这个兜底文字结束循环。真正要触发"死循环"得让 mock 一直返回 `toolCall`。改法：给 `createMockLlm` 传 10 个以上重复的 `toolCall`，让它永远调工具，就会触发最大循环次数兜底。
   </details>

2. 模型传了 `{ expression: "100/0" }`，`safeCalculate` 抛出的错误是什么？为什么这个错误能被模型"看懂"并修正？

   <details><summary>参考答案</summary>
   抛出 `Error: 计算失败：100/0 = Infinity（可能是除零）`。因为它用自然语言把"结果不是有限数、可能是除零"这件事说清楚了，还带上了错误名 `Error`。模型读得懂"除零"这个自然语言信息，下一轮就会换一个不为 0 的除数，或改问用户。
   </details>

3. 为什么 `arguments` 在真实 API 里是字符串而不是对象？你在代码里要做什么？

   <details><summary>参考答案</summary>
   因为模型每次只输出**文本**，所谓"结构化参数"其实是模型生成的一段 JSON 文本，OpenAI 只是把它原样塞进 `arguments` 字段。你的代码要 `JSON.parse(toolCall.function.arguments)` 把它转回对象，并且要 try/catch 解析失败的情况（模型可能生成非法 JSON）。
   </details>

4. 如果一个工具连续 3 次都返回同一个错误，你该怎么处理？为什么不无限重试？

   <details><summary>参考答案</summary>
   统计同一工具的连续报错次数，达到阈值（如 3 次）就强制停止，给用户一个兜底话术（如"我暂时处理不了这个问题"）。因为每次重试都要多付一次模型调用，无限重试 = 死循环 = 烧钱，且大概率模型就是搞不定，重试没意义。
   </details>
